# git لمطوّر فردي

كل ما هنا قابل للتنفيذ من تطبيق GitHub على الجوال أو من Claude Code. لا يوجد جهاز محلي، فالفرضية: **المستودع البعيد هو النسخة الوحيدة**. أي عمل لم يُدفع إلى GitHub غير موجود.

## نموذج الفروع: main + فرع لكل مهمة

GitFlow (develop + release/* + hotfix/*) صُمّم لفِرَق تُصدر إصدارات مُجمّعة كل ربع سنة. لمطوّر واحد يُصدر متى شاء، كلفته أعلى من عائده: أربعة فروع طويلة تحتاج مزامنة مستمرة، ونصف تعارضاتك ستأتي من مزامنة `develop` مع `main` لا من الكود نفسه.

النموذج الصحيح: `main` محمي دائماً قابل للبناء، وكل مهمة فرع قصير العمر يُدمج ويُحذف.

| القاعدة | القيمة |
|---|---|
| عمر الفرع الأقصى | 3 أيام — بعدها يتراكم التباعد ويصعب الدمج |
| حجم الـ PR المستهدف | أقل من 400 سطر مُغيَّر |
| عدد الفروع المفتوحة معاً | 1–2 لا أكثر |
| مصدر كل فرع | `main` مباشرة، لا فرع من فرع |

فعّل حماية `main` من Settings ← Branches: منع الدفع المباشر، اشتراط PR، اشتراط نجاح فحوص CI. الحماية ليست بيروقراطية — هي ما يمنعك من دفع كود مكسور في الثالثة فجراً من الجوال بلا مراجعة.

## تسمية الفروع

`<type>/<scope>-<وصف-قصير>` بحروف صغيرة وشرطات فقط:

```
feat/orders-cash-on-delivery
fix/rtl-date-picker-mirror
chore/bump-supabase-flutter
docs/readme-setup
```

لا مسافات، لا حروف عربية، لا `#` أو `:` (تكسر بعض الأدوات). أضف رقم المسألة إن وُجد: `fix/142-login-timeout`.

## الالتزامات: صغيرة وتشرح السبب

الالتزام الجيد **وحدة منطقية واحدة قابلة للرجوع عنها وحدها**. القياس العملي: إن احتجت "و" في وصف ما فعله، فهو التزامان.

صيغة Conventional Commits:

```
<type>(<scope>): <ملخّص بصيغة الأمر، أقل من 72 محرفاً>

<الجسم: لماذا لا ماذا. الكود يقول ماذا.>

Refs: #142
BREAKING CHANGE: <إن وُجد كسر توافق>
```

الأنواع: `feat` ميزة، `fix` إصلاح، `refactor` إعادة هيكلة بلا تغيير سلوك، `perf` أداء، `test` اختبارات، `docs` توثيق، `build` تبعيات ونظام بناء، `ci` ملفات سير العمل، `chore` صيانة، `revert` تراجع.

```
fix(auth): إعادة المحاولة عند انقطاع الشبكة أثناء تحديث الجلسة

كان انقطاع الشبكة أثناء refresh يُخرج المستخدم نهائياً لأن الاستثناء
يُفسَّر كجلسة منتهية. الآن نميّز خطأ الشبكة عن 401 ونعيد المحاولة مرتين.

Refs: #87
```

الملخّص بالعربية أو الإنجليزية — اختر واحدة والتزم بها في المستودع كله. `type` و`scope` تبقى إنجليزية لأن أدوات التوليد الآلي للـ changelog تقرؤها.

**الخطأ الأكثر شيوعاً**: رسائل مثل `update`, `fix bug`, `تعديلات`, `wip`. بعد شهرين تصبح `git log` عديمة القيمة، ويستحيل معرفة أي التزام أدخل العطل.

## ماذا يدخل الالتزام وماذا لا

| يدخل | لا يدخل |
|---|---|
| كود المصدر والاختبارات | ملفات البناء المولّدة (`build/`, `dist/`, `.dart_tool/`) |
| ملفات القفل (`pubspec.lock`, `package-lock.json`) للتطبيقات | التبعيات نفسها (`node_modules/`) |
| ملفات إعداد المشروع وسير العمل | إعدادات المحرّر الشخصية |
| هجرات القاعدة | `.env` وأي مفتاح أو شهادة |
| `.env.example` بقيم وهمية | ملفات النظام (`.DS_Store`, `Thumbs.db`) |

ملف القفل يُلتزَم في التطبيقات ولا يُلتزَم في الحزم المنشورة. تنسيق تلقائي لملف كامل + تغيير منطقي في التزام واحد = مراجعة مستحيلة؛ افصلهما.

## .gitignore

```gitignore
# أسرار — أولاً دائماً
.env
.env.*
!.env.example
*.pem
*.key
*.jks
*.keystore
*-service-account*.json

# مخرجات البناء
build/
dist/
.next/
coverage/

# تبعيات
node_modules/
.dart_tool/
.packages

# نظام ومحرّر
.DS_Store
Thumbs.db
*.log
.idea/
.vscode/
```

`.gitignore` **لا يؤثر على ملف متتبَّع بالفعل**: إن أضفت ملفاً ثم تجاهلته، يبقى متتبَّعاً حتى تُخرجه صراحةً من التتبّع مع إبقائه على القرص — لذا أنشئه **قبل** أول التزام لا بعده.

## rebase مقابل merge

| الحالة | الأداة |
|---|---|
| تحديث فرعك بما جدّ على `main` | `rebase` |
| ترتيب التزاماتك الفوضوية قبل الـ PR | `rebase -i` |
| إدخال الفرع إلى `main` | `merge` عبر PR (أو squash) |
| فرع دُفع وشاركه أحد | **لا rebase** أبداً |

القاعدة الذهبية: **لا تُعد كتابة تاريخ دُفع وبُني عليه غيرك**. وحدك على المستودع؟ إعادة كتابة فرعك الخاص آمنة، لكن لا تفعلها مع `main` مطلقاً.

في زر الدمج على GitHub ثلاثة خيارات: **Squash and merge** هو الافتراضي الصحيح لك — كل PR يصير التزاماً واحداً نظيفاً على `main`، والتاريخ يبقى مقروءاً. **Merge commit** يُبقي كل التزامات الفرع (مفيد فقط لفرع التزاماته مُرتّبة أصلاً)، و**Rebase and merge** يسطّح بلا التزام دمج ويصعّب تتبّع أصل المجموعة.

بعد الدمج احذف الفرع فوراً من نفس الصفحة. فعّل حذف الفرع تلقائياً بعد الدمج في إعدادات المستودع.

## التعارضات

التعارض حين يعدّل جانبان نفس الأسطر. GitHub يحلّ التعارضات البسيطة في المتصفّح والجوال عبر محرّر التعارض. العلامات:

```
<<<<<<< HEAD          ← ما في الفرع الهدف (main)
=======
>>>>>>> feature-x     ← ما في فرعك
```

احذف العلامات الثلاث كلها بعد الاختيار، وافحص الملف كاملاً بعدها لا موضع التعارض وحده. **الخطأ الأكثر شيوعاً**: اختيار جانب دون قراءة الآخر، فتضيع تعديلات صامتة تظهر كعطل بعد أسبوع.

تعارض ملف القفل: لا تحلّه يدوياً أبداً — خذ نسخة `main` ثم أعد توليده بأمر مدير الحزم. والوقاية أفضل: فروع قصيرة، وسحب `main` إلى فرعك يومياً.

## استرجاع العمل الضائع

`git reflog` يسجّل كل موضع أشار إليه HEAD خلال آخر 90 يوماً — حتى بعد reset أو حذف فرع أو rebase فاشل. ما دام الالتزام أُنشئ يوماً، فهو موجود ويمكن الرجوع إليه بمعرّفه من الـ reflog، ثم إنشاء فرع جديد عنده لإنقاذه.

الاستثناء الوحيد: عمل لم يُلتزم أصلاً. لا شيء يسترجعه. لذا التزم مبكراً وكثيراً — الالتزام الفوضوي القابل للترتيب لاحقاً أفضل من عمل غير موجود.

## الوسوم والإصدار الدلالي

`MAJOR.MINOR.PATCH`:

| الجزء | متى يزيد |
|---|---|
| MAJOR | كسر توافق: تغيير عقد API، حذف حقل، هجرة تكسر عملاء قدامى |
| MINOR | ميزة جديدة متوافقة مع ما قبلها |
| PATCH | إصلاح عطل بلا تغيير في السلوك المتوقَّع |

استعمل وسماً مُعلَّقاً (annotated) لا خفيفاً — المُعلَّق يحمل المؤلّف والتاريخ والرسالة، والخفيف مجرّد مؤشّر. الصيغة `v1.4.0` بحرف `v` بادئ (المتعارف عليه في GitHub Releases وفي محفّزات سير العمل). الوسم يُوضع على `main` فقط بعد نجاح CI، وعلى الجوال: صفحة Releases ← Draft a new release ← اختر الوسم واسم الفرع.

قبل 1.0.0 عدّ نفسك حرّاً في الكسر. بعدها الرقم عقد مع مستخدميك.

> إصدارات المتاجر وترقيم `pubspec.yaml` ورمز البناء: مهارة flutter-build-release.

## إذا دخل سرّ إلى التاريخ

الترتيب إجباري ولا يُعكَس:

1. **دوّر السرّ فوراً** — ألغِ المفتاح وأنشئ بديلاً. هذه الخطوة وحدها هي التي تُوقف الضرر.
2. أزل السرّ من الكود وضعه في GitHub Secrets، ثم ادفع.
3. نظّف التاريخ لو كان المستودع عاماً أو سيصير عاماً، بأداة مخصّصة مثل `git filter-repo` أو BFG — تعيد كتابة كل الالتزامات ويجب دفعها بالقوة، وكل نسخة موجودة عند أي شخص تصير غير متوافقة.
4. إن كان المستودع عاماً، افترض أن السرّ التُقط خلال دقائق. بوتات تفحص دفعات GitHub العامة لحظياً.

اعتبر التنظيف تخفيف ضرر لا علاجاً: نسخ GitHub المخبّأة و forks و caches قد تحتفظ بالالتزام. **التدوير هو العلاج الوحيد**.

> تصنيف الأسرار وتخزينها وفحص المستودع: مهارة ops-secrets.

## قائمة تحقق

- [ ] `main` محمي: لا دفع مباشر، PR إجباري، فحوص CI إجبارية
- [ ] كل مهمة في فرع من `main` عمره أقل من 3 أيام ويُحذف بعد الدمج
- [ ] أسماء الفروع `<type>/<وصف>` بحروف صغيرة وشرطات
- [ ] رسائل الالتزام بصيغة Conventional Commits وجسمها يشرح السبب
- [ ] لا التزام يخلط تنسيقاً آلياً مع تغيير منطقي
- [ ] `.gitignore` أُنشئ قبل أول التزام ويغطّي `.env` والمفاتيح ومخرجات البناء
- [ ] Squash and merge هو خيار الدمج الافتراضي، والحذف التلقائي للفرع مفعّل
- [ ] لا rebase على `main` ولا على أي فرع دُفع وشاركه غيرك
- [ ] الإصدارات موسومة `vX.Y.Z` بوسم مُعلَّق على `main` بعد نجاح CI
- [ ] عند تسريب سرّ: التدوير أولاً، ثم الإزالة، ثم تنظيف التاريخ
