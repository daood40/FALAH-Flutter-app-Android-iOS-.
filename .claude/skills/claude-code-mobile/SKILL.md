# كلود كود من الجوال فقط

المستخدم يعمل من الهاتف على مستودعات GitHub. هذه ليست نسخة ناقصة من العمل على الكمبيوتر — هي طريقة عمل مختلفة: **المستودع هو بيئتك، وGitHub Actions هو جهازك.**

## ما يعمل وما لا يعمل

| القدرة | جلسة الجوال/الويب |
|---|---|
| قراءة وتعديل الملفات، commit، push، فتح Pull Request | ✅ كامل |
| وضع التخطيط (Plan) | ✅ من قائمة الوضع في الواجهة |
| الوكلاء الفرعيون والعمل المتوازي | ✅ |
| `/clear` و`/compact` و`/context` و`/cost` | ✅ |
| التفكير الموسّع و`ultrathink` | ✅ |
| إرفاق صور ولقطات شاشة | ✅ — استعملها كثيراً |
| المهارات في `.claude/skills/` وملف `CLAUDE.md` | ✅ تُقرأ تلقائياً من المستودع |
| المهام في الخلفية | ✅ لكن لا تضمن البقاء عبر إعادة تشغيل البيئة |
| `/plugin` وسوق الإضافات | ❌ سطر الأوامر فقط |
| `/rewind` (التراجع بالنقاط) | ❌ — اعتمد على git والفروع |
| الـ hooks وملفات الإعدادات المحلية | ⚠️ محدودة — لا تعتمد عليها |
| MCP من إعدادات المستخدم | ⚠️ يعمل `.mcp.json` داخل المستودع فقط |
| `flutter build` / `flutter test` محلياً | ❌ لا توجد بيئة Flutter في جلسة الويب |

**النتيجة العملية:** كل ما يحتاج تنفيذاً فعلياً — بناء، اختبار، نشر — يُنقل إلى GitHub Actions.

## GitHub Actions هو جهازك

القاعدة: **لا تطلب من كلود أن يقول «تم البناء» وهو لم يبنِ شيئاً.** بدلاً من ذلك، اجعل كل push يبني ويختبر ويرفع النتيجة، ثم اقرأ النتيجة.

### ١. فحص واختبار على كل push (الأساس — لا يستغني عنه مشروع)

```yaml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2
        with: { channel: stable, cache: true }
      - run: flutter pub get
      - run: dart format --set-exit-if-changed .
      - run: flutter analyze --fatal-infos
      - run: flutter test
```

### ٢. بناء APK قابل للتحميل على الهاتف

```yaml
name: build-apk
on:
  workflow_dispatch:          # زر تشغيل يدوي من تطبيق GitHub
  push:
    tags: ['v*']
jobs:
  apk:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: zulu, java-version: '17' }
      - uses: subosito/flutter-action@v2
        with: { channel: stable, cache: true }
      - run: flutter pub get
      - run: flutter build apk --release --build-number=${{ github.run_number }}
      - uses: actions/upload-artifact@v4
        with:
          name: app-release
          path: build/app/outputs/flutter-apk/app-release.apk
```

`workflow_dispatch` يعني زر «Run workflow» في تطبيق GitHub على جوالك. النتيجة ملف APK تحمّله وتثبّته على نفس الهاتف وتجرّب التطبيق فعلياً.

### ٣. نشر نسخة الويب لتجربتها فوراً

انظر مهارة النشر على الويب في المستودع؛ الفكرة أن كل push إلى `main` ينشر على GitHub Pages فتفتح الرابط من الجوال وتجرّب خلال دقائق.

### ٤. مساعدة كلود داخل GitHub نفسه

يمكن تفعيل `anthropics/claude-code-action` بحيث تكتب `@claude` في تعليق على Issue أو Pull Request فيستجيب ويعدّل ويرفع commit. هذا يجعلك تعمل من تطبيق GitHub مباشرة دون فتح جلسة.

يحتاج سراً في إعدادات المستودع (`ANTHROPIC_API_KEY` أو رمز OAuth). لا تضع المفتاح في ملف الـ workflow أبداً.

## قراءة نتيجة البناء من الجوال

عند فشل CI:

1. افتح تبويب Actions في تطبيق GitHub، انسخ **نص الخطأ كاملاً**.
2. الصقه في جلسة كلود كود مع الطلب:
   > «فشل CI بهذا الخطأ. شخّص السبب أولاً قبل أي تعديل، ثم أصلحه وارفع commit».
3. لا تقبل إصلاحاً بلا تشخيص — «جرّب هذا» يهدر دورة CI كاملة.

اطلب من كلود أن يقرأ ملف الـ workflow نفسه قبل التشخيص؛ كثير من الأعطال سببها إعداد CI لا الكود.

## سير العمل الموصى به للفروع

بما أن `/rewind` غير متاح، الفرع هو شبكة الأمان:

```
فرع لكل مهمة  ←  commit صغير بعد كل خطوة  ←  push  ←  CI أخضر  ←  Pull Request  ←  دمج من تطبيق GitHub
```

اطلب صراحة: «اعمل فرعاً باسم `claude/<المهمة>` قبل البدء». وإن ساءت الأمور: تُغلق الـ PR ويُحذف الفرع، ولا يتأثر `main` إطلاقاً.

## اللقطة أسرع من ألف كلمة

أرفق لقطة شاشة عند:
- خلل في الشكل (تداخل، اتجاه معكوس، نص مقصوص)
- شاشة خطأ حمراء من Flutter
- صفحة نتيجة CI
- تصميم تريد تنفيذه

هذا أدق وأسرع من وصف المشكلة بالكلمات، وهو من أقوى ما يميز العمل من الهاتف.

## المهام المجدولة

يمكن جدولة عمل يتكرر (تحديث التبعيات أسبوعياً، تقرير حالة، فحص أمني) عبر `schedule` في GitHub Actions:

```yaml
on:
  schedule:
    - cron: '0 6 * * 1'      # كل اثنين 6 صباحاً بتوقيت UTC
```

هكذا يعمل المشروع وأنت نائم، وتقرأ النتيجة صباحاً من الهاتف.

## ما لا تحاول فعله من الجوال

- **بناء iOS ونشره** يحتاج macOS — استعمل `macos-latest` في GitHub Actions أو خدمة مثل Codemagic؛ لا يمكن من الجلسة مباشرة.
- **تصحيح تفاعلي مباشر** (breakpoints، DevTools) غير ممكن — عوّضه بسجلات مطبوعة مؤقتة وباختبارات.
- **أوامر تحتاج جهازك** (`adb`، محاكي، Xcode) — كلها تُنقل إلى CI أو تُلغى.

عندما يطلب المستخدم شيئاً من هذه، قل ذلك مباشرة واعرض البديل عبر CI بدل محاولة تنفيذ أمر سيفشل.

## قائمة تحقق لتجهيز أي مستودع للعمل من الجوال

- [ ] `ci.yml` يشغّل format و analyze و test على كل push
- [ ] `build-apk.yml` فيه `workflow_dispatch` لبناء نسخة تجريبية بضغطة
- [ ] نشر تلقائي لنسخة الويب إن كان المشروع يدعمها
- [ ] `CLAUDE.md` فيه قاعدة: «لا تدّعِ نجاح بناء لم يُشغَّل؛ اعتمد على CI»
- [ ] الأسرار كلها في Repository Secrets، ولا مفتاح داخل أي ملف
- [ ] العمل دائماً على فرع، والدمج عبر Pull Request
