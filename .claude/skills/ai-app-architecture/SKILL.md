# معمارية تطبيق ذكاء اصطناعي

الموضوع هنا هو **ما بين التطبيق والمزوّد**: نقطة النهاية، الحالة، الحدود، والفشل. القرار الأهم يُتخذ في اليوم الأول ولا يُتراجع عنه بسهولة.

> استهلاك البثّ وعرضه في Flutter: مهارة flutter-ai-integration.

## الطبقات الثلاث

```
تطبيق Flutter ──(HTTPS + JWT المستخدم)──▶ وسيط على الخادم ──(مفتاح API)──▶ مزوّد النموذج
                                              │
                                     Postgres: محادثات، حصص، سجلات، تخزين مؤقت
```

الوسيط عندك عملياً: Supabase Edge Function (Deno) أو خادم Node صغير. مسؤولياته الست، ولا شيء منها يمكن نقله للعميل: حمل مفتاح المزوّد، والتحقق من هوية المستخدم وصلاحيته، وفرض الحصة قبل إنفاق أي شيء، وبناء المطالبة النهائية (مطالبة نظام مخزّنة + سياق من القاعدة + مدخل المستخدم)، واختيار النموذج والمعاملات، والتسجيل والقياس.

## لماذا لا يتصل العميل بالمزوّد أبداً

ليست مسألة أفضلية بل خط أحمر:

- **المفتاح مكشوف حتماً.** ملف APK يُفكّك في دقائق؛ `--dart-define` و`.env` والتشويش كلها تُستخرج. مفتاح واحد مسرّب = فاتورة مفتوحة على حسابك حتى تكتشفها.
- **لا حدّ ممكن.** أي حدّ في العميل يُتجاوَز بتعديل التطبيق أو بطلب HTTP مباشر.
- **لا تغيير بلا تحديث.** المطالبة والنموذج في العميل يعني أن إصلاح مطالبة سيئة ينتظر مراجعة المتجر أسبوعاً، وأن نسخة قديمة على هاتف شخص ما تستعمل مطالبة خاطئة للأبد.
- **لا قياس ولا سجل.** لا تعرف تكلفة أي ميزة ولا سبب أي شكوى.

الاستثناء الوحيد المقبول: نموذج يعمل على الجهاز نفسه بلا مفتاح ولا فاتورة. عندها لا يوجد مزوّد أصلاً.

## نقطة النهاية والبثّ

نقطتان لا أكثر في البداية:

| المسار | الغرض | الشكل |
|---|---|---|
| `POST /chat` | رسالة داخل محادثة | بثّ SSE |
| `POST /task` | مهمة قصيرة محدّدة (تصنيف، تلخيص، استخراج) | JSON دفعة واحدة |

البثّ لازم فقط حين ينتظر المستخدم نصاً طويلاً يقرأه أثناء توليده. للتصنيف والاستخراج البثّ تعقيد بلا فائدة — رد بجسم واحد أبسط وأسهل في التخزين المؤقت والتحقق.

شكل SSE عملي: أحداث مسمّاة بدل نص خام، فيمكنك إضافة معلومات جانبية بلا كسر العميل.

```
event: meta
data: {"message_id":"m_01J...","model":"...","request_id":"req_01J..."}

event: delta
data: {"text":"مرحبا "}

event: usage
data: {"input_tokens":1240,"output_tokens":86}

event: done
data: {"finish_reason":"end_turn"}
```

قواعد:
- أرسل `event: meta` **فوراً** قبل استدعاء المزوّد. يمنحك العميل شيئاً يعرضه ويثبّت `request_id` للتشخيص حتى لو فشل الباقي.
- الخطأ في منتصف البثّ يُرسل كـ`event: error` بجسم JSON، لا بقطع الاتصال — القطع يظهر للمستخدم كتعليق غامض.
- عطّل التخزين الوسيط: `Content-Type: text/event-stream`، `Cache-Control: no-cache`، `X-Accel-Buffering: no`. بدونها يحتجز الوكيل الأحداث ويصلها دفعة واحدة، فيضيع الغرض كله.
- خزّن الرد المتراكم في القاعدة **عند انتهاء البثّ** لا بعد كل قطعة، وسجّل الردود المقطوعة بحالة `partial` لتعرف نسبتها.
- أرسل نبضة تعليق (`: ping`) كل 15 ثانية إن كان النموذج قد يصمت طويلاً قبل أول رمز، وإلا أغلقت وسائط الشبكة الاتصال.

## إدارة المحادثة والذاكرة

النموذج بلا ذاكرة: كل طلب يحمل كامل ما يحتاجه. المحادثة حالة **تملكها أنت** في القاعدة.

```sql
create table conversations (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  title text,
  summary text,                 -- الملخّص المتدحرج للرسائل المطويّة
  summarized_upto_seq int not null default 0,
  created_at timestamptz not null default now()
);

create table messages (
  id uuid primary key default gen_random_uuid(),
  conversation_id uuid not null references conversations(id) on delete cascade,
  seq int not null,             -- ترتيب حتمي، لا تعتمد على الوقت
  role text not null check (role in ('user','assistant')),
  content text not null,
  input_tokens int, output_tokens int, model text,
  created_at timestamptz not null default now(),
  unique (conversation_id, seq)
);
create index on messages (conversation_id, seq desc);
```

**النافذة المتحركة + الملخّص المتدحرج**: احتفظ بآخر N رسالة كاملة، ولخّص ما قبلها في حقل `summary` يُحدَّث بشكل تراكمي.

| المعامل | قيمة ابتدائية معقولة |
|---|---|
| رسائل كاملة محفوظة | آخر 8–12 رسالة |
| عتبة التلخيص | حين يتجاوز مجموع رموز المحادثة 3000–4000 |
| طول الملخّص | 150–300 رمز، سقف صارم |
| النموذج المستعمل للتلخيص | الأصغر المتاح دائماً |

التلخيص يُشغَّل **بعد** إرسال الرد للمستخدم لا قبله، وإلا أضفت ثانيتين لكل رسالة. والملخّص يُبنى من (الملخّص السابق + الرسائل الجديدة) لا من المحادثة كاملة، وإلا كبرت تكلفته مع الزمن.

الخطأ الأكثر شيوعاً: إرسال المحادثة كاملة في كل طلب. بعد 30 رسالة صار كل سؤال يكلّف عشرة أضعاف الأول، بلا تحسّن في الجودة — بل بتدهور، لأن السياق المتضخّم يُضعف اتباع التعليمات. وقاعدة تكميلية: **لا تخزّن رسائل النظام في جدول الرسائل**. مطالبة النظام تُبنى وقت الطلب من الملف الحالي، فتستفيد كل محادثة قديمة من التحسينات الجديدة فوراً.

## الحدود والحصص

يُفرض على الخادم قبل استدعاء المزوّد، وبطبقتين:

| الطبقة | الغرض | مثال |
|---|---|---|
| معدّل قصير | يمنع الحلقات والضغط | 10 طلبات/دقيقة لكل مستخدم |
| حصة يومية/شهرية | يحمي الفاتورة | 50 رسالة/يوم للمجاني، 1000/شهر للمدفوع |

نفّذها بجدول عدّاد بمفتاح `(user_id, feature, window_start)` وزيادة ذرّية داخل نفس المعاملة، لا بعدّ سجلات في كل طلب. وعند التجاوز أرجع `429` مع `Retry-After` ورمز خطأ ثابت (`quota_exceeded`) يترجمه التطبيق محلياً — لا رسالة نصية. واحسب الحصة بالرموز لا بالطلبات إن اختلفت أطوال المهام كثيراً؛ طلب واحد بسياق 20 ألف رمز يعادل 40 طلباً قصيراً. وحدّ `max_tokens` لكل مسار هو خط دفاعك الأخير.

> تفصيل الحصص والتكلفة: مهارة ai-cost-optimization. تحديد المعدّل كنمط عام: مهارة data-api-design.

## التخزين المؤقت

ثلاثة أنواع مختلفة، لا تخلطها:

1. **تخزين النتائج**: مفتاحه `hash(prompt_version + model + normalized_input)`، وقيمته الرد الكامل. يصلح فقط للمهام الحتمية عند حرارة 0 (تصنيف، ترجمة قصيرة، وصف منتج ثابت). لا يصلح لمحادثة. TTL معقول: ساعات إلى أيام، ويُبطَل فوراً عند تغيير إصدار المطالبة — لهذا `prompt_version` جزء من المفتاح.
2. **تخزين مطالبة المزوّد**: بادئة ثابتة طويلة (مطالبة نظام + تعليمات + أمثلة) تُعلَّم للتخزين لدى المزوّد فتُحسب بجزء بسيط من سعرها في الطلبات التالية. الشرط: البادئة **متطابقة بايت ببايت** ومستقرة. لذلك رتّب الطلب: [الثابت الطويل] ثم [المتغيّر]. وضع تاريخ اليوم أو اسم المستخدم في أول المطالبة يُبطل التخزين كلياً — من أشيع الأخطاء.
3. **تخزين التضمينات**: التضمين لنص لا يتغير أبداً — خزّنه ولا تعِد حسابه. وقِس نسبة الإصابة (cache hit rate): تخزين بنسبة إصابة تحت 10% تعقيد بلا مقابل، احذفه.

## الفشل والمهل وإعادة المحاولة

| الحالة | التصرف |
|---|---|
| `429` من المزوّد | إعادة محاولة مع تراجع أسّي + عشوائية: 1s، 2s، 4s وتوقف |
| `5xx` أو انقطاع شبكة | نفس الشيء، حد أقصى محاولتان إضافيتان |
| `400` (مطالبة أو مخطط خاطئ) | **لا تعيد المحاولة** — الخطأ عندك وسيتكرر |
| تجاوز حد السياق | اقطع السياق (ألغِ رسائل قديمة) وأعد مرة واحدة |
| مهلة | ألغِ واسقط للبديل |

مهل عملية: **مهلة الاتصال 10 ثوانٍ**، **مهلة أول رمز 20–30 ثانية** (بعدها المشكلة ليست بطئاً بل تعليقاً)، **مهلة كلية 60–120 ثانية** حسب طول المخرج. أطول من ذلك يعني أن المهمة تنتمي لطابور خلفي لا لطلب متزامن.

اجعل الطلب idempotent بمفتاح يولّده العميل مرة لكل رسالة: انقطاع الشبكة بعد نجاح النموذج شائع جداً على الجوال في ليبيا، وبلا مفتاح ستدفع مرتين وتخزّن الرسالة مرتين. والخطأ الشائع هنا إعادة المحاولة على كل خطأ: إعادتها على `400` تضاعف الضغط بلا أمل، وإعادتها بلا عشوائية تُنتج موجة متزامنة من كل الأجهزة بعد انقطاع.

## السقوط الآمن

رتّب البدائل صراحة، ولا تترك المستخدم أمام شاشة فارغة:

1. النموذج الأساسي، ثم نموذج أصغر/أسرع من نفس المزوّد (يكفي لأغلب المهام القصيرة).
2. مزوّد ثانٍ إن كانت الميزة حرجة — يتطلب اختبار مطالبتك عليه مسبقاً، فالمطالبة ليست محمولة تلقائياً.
3. رد ثابت مفيد أو مسار غير ذكي (بحث بالكلمات المفتاحية، قائمة أسئلة شائعة).

الشرط: يُوسَم الرد بالنموذج الذي أنتجه في السجل، وإلا لن تفهم لماذا تدهورت الجودة يوم الثلاثاء. وللمهام غير الحوارية (تصنيف، توسيم) ابدأ بالأصغر واصعد فقط عند ثقة منخفضة، لا العكس.

## التسجيل والخصوصية

سجّل لكل استدعاء: `request_id`, `user_id`, `feature`, `prompt_version`, `model`, `input_tokens`, `output_tokens`, `latency_ms`, `ttft_ms`, `finish_reason`, `cache_hit`, `error_code`. هذا الحد الأدنى الذي بدونه لا تحسين ولا تحكم في التكلفة.

محتوى النص أصعب: مفيد للتحسين، وحسّاس. القاعدة العملية:

- خزّن نص المحادثة في جدول المستخدم نفسه محكوماً بـRLS ولا تنسخه إلى جدول سجلات مفتوح؛ وسجلات التشخيص تحمل **أطوالاً وتجزئات ورموز أخطاء** لا نصوصاً كاملة، افتراضياً.
- الاحتفاظ محدود: 30–90 يوماً للسجلات التفصيلية ثم حذف تلقائي بمهمة مجدولة، واستعمال المحادثات لتحسين المطالبات يحتاج موافقة صريحة وواجهة حذف تعمل فعلاً.
- لا ترسل أرقام هوية أو بطاقات إلى المزوّد؛ نظّفها قبل البناء لا بعده.

> السياسات والـRLS: مهارة data-auth-patterns. النسخ الاحتياطي والاحتفاظ: مهارة data-backup-recovery.

## القياس: زمن أول رمز مقابل الزمن الكلي

| المقياس | ما يعنيه | هدف عملي |
|---|---|---|
| TTFT (أول رمز) | إحساس المستخدم بالاستجابة | < 1.5s وسيط، < 3s عند p95 |
| الزمن الكلي | اكتمال المهمة | حسب الطول |
| زمن الوسيط وحده | ما تتحكم به أنت | < 150ms قبل استدعاء المزوّد |

TTFT هو المقياس الذي يحدّد الإحساس بالجودة، والزمن الكلي يحدّد الإحساس بالطول. أي عمل تفعله قبل استدعاء المزوّد (بحث في القاعدة، تلخيص، جلب سياق) يُضاف كاملاً إلى TTFT — لهذا يُنفَّذ التلخيص بعد الرد لا قبله، وتُجلب أجزاء السياق بالتوازي لا بالتسلسل. وقِس دائماً على **p95 لا المتوسط**؛ المتوسط يخفي أن واحداً من كل عشرين مستخدماً ينتظر عشر ثوانٍ. وقِس من الهاتف على شبكة حقيقية: زمن الشبكة في ليبيا يضيف 200–600ms قبل أن تبدأ أنت.

## قائمة تحقق

- [ ] لا يوجد مفتاح مزوّد في العميل بأي شكل، وكل استدعاء يمرّ بوسيط
- [ ] الوسيط يتحقق من الهوية ويفرض الحصة **قبل** استدعاء المزوّد
- [ ] المطالبات ونموذج التشغيل يُقرآن من إعداد الخادم، فيتغيّران بلا تحديث تطبيق
- [ ] البثّ SSE بأحداث مسمّاة، مع `meta` فوراً و`error` كحدث لا كقطع
- [ ] ترويسات منع التخزين الوسيط مضبوطة، ونبضة تعليق دورية
- [ ] المحادثة مخزّنة بـ`seq` حتمي، ولا تُرسل كاملة أبداً
- [ ] نافذة آخر 8–12 رسالة + ملخّص متدحرج بسقف 300 رمز يُبنى تراكمياً وبعد الرد
- [ ] حصة قصيرة وحصة يومية بعدّاد ذرّي، و`429` برمز خطأ ثابت و`Retry-After`
- [ ] `max_tokens` مضبوطة لكل مسار
- [ ] البادئة الثابتة أول المطالبة ولا شيء متغيّر قبلها (لأجل تخزين المطالبة)
- [ ] إعادة المحاولة فقط على 429/5xx بتراجع أسّي وعشوائية، ولا إعادة على 400
- [ ] مفتاح idempotency لكل رسالة يولّده العميل مرة واحدة
- [ ] سلسلة سقوط معرّفة ومختبرة، والنموذج المستعمل مسجّل مع كل رد
- [ ] سجل بالحقول الأساسية لكل استدعاء، بلا نصوص كاملة في سجلات التشخيص
- [ ] TTFT والزمن الكلي مقاسان عند p95، وزمن الوسيط وحده مفصول
