# الاستضافة والنشر

القرار الأول ليس "أي منصّة" بل "أي نموذج". النموذج يحدّد الكلفة والتعقيد وسقف النمو.

## النماذج الأربعة

| النموذج | ما يعمل | يناسب | لا يناسب |
|---|---|---|---|
| استضافة ثابتة | ملفات مبنيّة مسبقاً تُخدَم من CDN | مواقع تعريفية، مدوّنات، SPA، تطبيقات تتحدّث لـ Supabase مباشرة | أي منطق يحتاج سرّاً على الخادم |
| بلا خادم (serverless / edge) | دالة تعمل عند الطلب وتموت | webhooks، وسيط لإخفاء مفتاح API، مهام قصيرة | عمليات طويلة، اتصال دائم، حالة في الذاكرة |
| خادم مستأجر (VPS / PaaS) | عملية تعمل باستمرار | WebSocket، طوابير، أعباء ثقيلة | مشروع بحركة متقطّعة يدفع 24 ساعة |
| حاويات | صورة Docker على منصّة تشغيل | بيئة معقّدة أو تشغيل متعدّد الخدمات | مشروع فردي يريد أقل عمل تشغيلي |

القاعدة العملية: **ابدأ ثابتاً**. أغلب ما يُظنّ أنه يحتاج خادماً يحتاج فعلياً موقعاً ثابتاً + Supabase. أضف دوال بلا خادم عند أول حاجة لسرّ على الخادم. لا تنتقل إلى VPS إلا مع اتصال دائم أو عملية تتجاوز حدود المهلة.

حدود الدوال بلا خادم التي تُسقط المشاريع: **البدء البارد** (زيادة 200–800 ms على أول نداء بعد خمول)، **سقف زمن التنفيذ** (بضع عشرات من الثواني على الخطط المجانية)، و**انعدام الحالة** — لا شيء يبقى في الذاكرة بين نداءين.

## المنصّات الشائعة

| المنصّة | النموذج | الخطة المجانية (تقريبية) | ملاحظة حاسمة |
|---|---|---|---|
| GitHub Pages | ثابتة | موقع حتى 1 GB، حركة ~100 GB/شهر | لا دوال، لا إعادة توجيه من الخادم، لا ترويسات مخصّصة |
| Cloudflare Pages | ثابتة + Workers | حركة بلا سقف، ~500 بناء/شهر | الأسخى للحركة، وشبكة الحافة الأقرب لشمال أفريقيا |
| Netlify | ثابتة + دوال | ~100 GB حركة، ~300 دقيقة بناء/شهر | معاينة لكل PR، أبسط إعداد على الإطلاق |
| Vercel | ثابتة + دوال حافة | ~100 GB حركة | الخطة المجانية **غير تجارية**؛ الأفضل لـ Next.js |
| Supabase | قاعدة + تخزين + دوال | 500 MB قاعدة، ~1 GB ملفات، ~5 GB خروج | المشروع الخامل يُوقَف بعد أسبوع على المجاني |
| Fly.io | حاويات/خادم | لا خطة مجانية دائمة، دفع بالاستهلاك | مناطق قريبة، جيد لعملية دائمة |
| Railway | خادم/حاويات | تجربة ثم اشتراك شهري أدنى | أسهل PaaS لبدء خادم |

الأرقام تتغيّر — تحقّق من صفحة الأسعار قبل الاعتماد، واعتبر ما هنا ترتيباً نسبياً لا عقداً.

**التركيبة المناسبة لمشروع فردي عربي**: Cloudflare Pages أو Netlify للواجهة + Supabase للقاعدة والمصادقة والتخزين + دالة حافة واحدة أو دالتان لما يحتاج سرّاً. الكلفة صفر حتى حركة معتبرة، والنشر آلي من GitHub بلا أي جهاز.

> نشر واجهة Flutter Web تحديداً: مهارة flutter-web-deploy.

## النطاقات وسجلات DNS

| السجلّ | يشير إلى | يُستعمل لـ |
|---|---|---|
| `A` | عنوان IPv4 | الجذر `example.com` |
| `AAAA` | عنوان IPv6 | الجذر، مع IPv6 |
| `CNAME` | اسم نطاق آخر | نطاق فرعي `www` |
| `ALIAS` / `ANAME` / CNAME flattening | اسم نطاق آخر عند الجذر | الجذر على منصّة تعطيك اسماً لا IP |
| `TXT` | نص | إثبات الملكية، SPF/DKIM |
| `MX` | خادم بريد | البريد — **لا تحذفه عند نقل الاستضافة** |

`CNAME` **ممنوع على الجذر** بمعيار DNS. المخرج: `ALIAS`/`ANAME` أو CNAME flattening (Cloudflare يوفّره)، أو سجلات `A` تعطيك إياها المنصّة. GitHub Pages مثلاً يوثّق أربعة عناوين `A` ثابتة للجذر و`CNAME` نحو `<user>.github.io` لـ `www`.

اضبط `TTL` على 300 ثانية **قبل** أي نقل بيوم، ثم أعده إلى 3600 بعد استقرار النقل. النقل بـ TTL يساوي يوماً يعني يوماً كاملاً من مستخدمين يرون الموقع القديم.

اختر جذراً واحداً قانونياً (`example.com` أو `www.example.com`) وحوّل الآخر إليه بـ 301 — لا نسختين مفهرستين.

## شهادات TLS

كل المنصّات المذكورة تُصدر شهادة Let's Encrypt مجاناً وتجدّدها تلقائياً (عمر الشهادة 90 يوماً). ما تحتاج فعله: تصحيح سجلّ DNS ثم الانتظار من دقائق إلى ساعة.

الأعطال الثلاثة الشائعة:

| العرَض | السبب |
|---|---|
| الشهادة لا تُصدَر | DNS لم ينتشر بعد، أو سجلّ `CAA` يمنع المُصدِر |
| تحذير في المتصفّح بعد النقل | سجلّ قديم يشير للمضيف السابق |
| يعمل على `www` ولا يعمل على الجذر | الشهادة صدرت لاسم واحد فقط |

فعّل HSTS وإعادة التوجيه الإجبارية من HTTP إلى HTTPS من إعدادات المنصّة. وانتبه: HSTS بمدّة طويلة قرار صعب التراجع عنه — ابدأ بمدّة قصيرة.

## شبكة التوزيع وزمن الوصول من شمال أفريقيا

الحركة من ليبيا وتونس والجزائر تخرج غالباً عبر كابلات المتوسط إلى مرسيليا وميلانو، ثم إلى فرانكفورت وأمستردام. النتيجة العملية:

| الوجهة | زمن ذهاب وإياب تقريبي |
|---|---|
| نقطة حافة في شمال أفريقيا أو مرسيليا | 20–50 ms |
| فرانكفورت / أمستردام | 60–110 ms |
| شرق الولايات المتحدة | 130–200 ms |
| غرب الولايات المتحدة أو سنغافورة | 250–350 ms |

الأثر: صفحة فيها 6 نداءات API متسلسلة إلى `us-east-1` تدفع 6 × 160 ms = ثانية كاملة من الشبكة وحدها قبل أي معالجة. لذلك:

1. **اختر أقرب منطقة للقاعدة**: منطقة أوروبية (مثل `eu-central` أو `eu-west`) لا أمريكية. منطقة مشروع Supabase تُحدَّد عند الإنشاء و**لا تُغيَّر بعده** — القرار نهائي.
2. الملفات الثابتة تُخدَم من CDN فتصل من نقطة قريبة تلقائياً — هذا مجاني ولا يحتاج جهداً.
3. قلّل عدد الرحلات لا حجمها: نداء واحد يجلب 40 KB أسرع بكثير من ستة نداءات تجلب 5 KB.
4. اجعل الشبكات البطيئة هي الافتراض: صور محسّنة، تحميل كسول، ومهلة نداء 15–20 ثانية مع إعادة محاولة واحدة.

## متغيّرات البيئة في كل منصّة

| المنصّة | الموضع | النطاق |
|---|---|---|
| Netlify | Site settings ← Environment variables | لكل سياق: production / deploy-preview / branch |
| Vercel | Project ← Settings ← Environment Variables | Production / Preview / Development |
| Cloudflare Pages | Settings ← Environment variables | Production / Preview |
| GitHub Actions | Repository secrets & variables | التشغيل فقط |

مبدأ لا يُخرق: **أي متغيّر يصل إلى حزمة العميل ليس سرّاً**. البادئات (`NEXT_PUBLIC_`, `VITE_`) ليست مجرّد عرف — هي إعلان صريح بأن القيمة ستُطبع داخل ملف JS يفتحه أي زائر. مفتاح `anon` من Supabase يُقصد به أن يكون عاماً (وحمايته RLS)، و`service_role` لا يقترب من العميل إطلاقاً.

وتذكّر: متغيّرات البناء تُحقَن **وقت البناء** لا وقت التشغيل — تغييرها في اللوحة لا يغيّر شيئاً حتى تعيد النشر.

> تصنيف الأسرار والتدوير بعد التسريب: مهارة ops-secrets.

## إعادة التوجيه لتطبيقات الصفحة الواحدة

المشكلة: SPA يوجّه المسارات في المتصفّح، لكن فتح `/orders/42` مباشرة أو تحديث الصفحة يطلب من الخادم ملفاً غير موجود ← 404.

الحل: توجيه كل مسار غير مطابق لملف إلى `index.html` بحالة **200** لا 301.

```
# Netlify و Cloudflare Pages: ملف _redirects في جذر مجلّد البناء
/api/*  https://example.supabase.co/rest/v1/:splat  200
/*      /index.html                                 200
```

الترتيب مهم: القواعد تُقيَّم من أعلى لأسفل، وقاعدة `/*` تبتلع كل ما تحتها. وعلى Vercel يُكتب المكافئ في `vercel.json` عبر `rewrites`.

GitHub Pages **لا يدعم إعادة توجيه من الخادم أصلاً**. الحيلتان: نسخ `index.html` إلى `404.html` (يعمل لكن الحالة تبقى 404 وهو سيّئ للفهرسة)، أو استعمال توجيه بالـ hash. وإن كنت تنشر تحت مسار فرعي `/<repo>/` فاضبط `base` في أداة البناء وإلا كُسرت كل مسارات الأصول.

فحص سريع بعد كل نشر: افتح مساراً عميقاً مباشرة من شريط العنوان، وحدّث الصفحة، وارجع بزر الرجوع.

## التكلفة الحقيقية عند النمو

المجاني ينتهي من ثلاثة أبواب، بهذا الترتيب غالباً:

| البند | متى يعضّ |
|---|---|
| **الخروج (egress)** | أول من ينفد. صور وملفات غير محسّنة تستهلك حصّة القاعدة بسرعة مذهلة |
| دقائق البناء | مع نشر متكرّر ومصفوفات بناء |
| تخزين القاعدة والملفات | متأخّراً عادةً |
| استدعاءات الدوال | مع webhook كثيف أو استقصاء متكرّر |

أخطاء تُضاعف الفاتورة بلا مقابل: تقديم صور بأبعادها الأصلية بدل نسخ مصغّرة؛ استقصاء (polling) كل بضع ثوانٍ بدل اشتراك أو webhook؛ جلب أعمدة لا تُعرض؛ غياب صفحات في القوائم فتُجلب آلاف الصفوف؛ وترك بيئة staging تعمل بأحمال إنتاج.

نصيحة تسعير خاصة بالمنطقة: القدرة الشرائية في ليبيا والمنطقة العربية مختلفة، والدفع بالبطاقات الدولية محدود. فاتورة 20$/شهر ليست صغيرة، واحتساب حدّ إنفاق وتنبيه على 70% من كل حصّة قبل النمو أرخص من مفاجأة. راقب الاستهلاك شهرياً لا عند وصول الفاتورة.

## قائمة تحقق

- [ ] النموذج مُختار عن قصد: ثابت ما لم يوجد سبب صريح لغيره
- [ ] النشر آلي من GitHub، ولا رفع يدوي لأي ملف
- [ ] منطقة القاعدة أوروبية قريبة (قرار نهائي لا يُغيَّر لاحقاً)
- [ ] جذر واحد قانوني والآخر يُحوَّل إليه بـ 301
- [ ] `TTL` خُفض إلى 300 قبل النقل وأُعيد إلى 3600 بعده، وسجلات `MX` سليمة
- [ ] HTTPS إجباري والشهادة تُجدَّد تلقائياً على الجذر و`www` معاً
- [ ] قاعدة `/* → /index.html 200` موجودة، ومسار عميق مُختبَر بالتحديث المباشر
- [ ] لا سرّ في أي متغيّر ببادئة عامة، و`service_role` غير موجود في أي بناء عميل
- [ ] متغيّرات البيئة مضبوطة لكل سياق (production / preview) على حدة
- [ ] تنبيه على 70% من حصّة الخروج ودقائق البناء، وحدّ إنفاق مضبوط
