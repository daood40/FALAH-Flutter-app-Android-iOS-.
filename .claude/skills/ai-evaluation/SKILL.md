# تقييم مخرجات النماذج

"بدا جيداً" ليس تقييماً لثلاثة أسباب محدّدة: جرّبت 3–5 حالات اخترتها أنت (وهي أسهل من الواقع)، وقارنت بذاكرتك عن المخرج القديم (وهي غير دقيقة)، ولم تلاحظ أن التحسين لحالة كسر خمس حالات أخرى. **التقييم هو ما يحوّل تعديل المطالبة من مقامرة إلى هندسة.**

## متى تبني تقييماً

| الحالة | القرار |
|---|---|
| مهمة تُشغَّل مرة واحدة | لا تقييم |
| ميزة في الإنتاج يستعملها مستخدمون | تقييم إلزامي منذ أول أسبوع |
| ستغيّر المطالبة أو النموذج مستقبلاً | تقييم قبل أول تغيير، لا بعده |
| المخرج مهيكل (JSON/تصنيف) | تقييم رخيص وحتمي — لا عذر |
| المخرج نص حر طويل | تقييم أصعب، ابدأ بفحوص شكلية + حَكَم |

الحدّ الأدنى المفيد: **20 حالة**. المنطقة العملية: **50–150**. فوق 300 حالة تدخل في تكلفة تشغيل وصيانة لا تستحقها إلا لميزة أساسية.

## بناء مجموعة الاختبار

المصدر الوحيد المقبول: **مدخلات حقيقية من مستخدمين** (أو أقرب ما يمكن). الحالات التي تخترعها بنفسك تشبه ما توقعته، لا ما يحدث.

التوزيع المستهدف:

| الفئة | النسبة | مثالها |
|---|---|---|
| حالات نمطية | 50% | ما يفعله أغلب المستخدمين |
| حالات حدّية | 25% | نص طويل جداً، قصير جداً، صيغة غريبة، أرقام كبيرة |
| حالات يجب أن تفشل بأمان | 15% | خارج النطاق، محتوى مسيء، سؤال بلا جواب في السياق |
| حالات كسرت سابقاً | 10% | كل عطل حقيقي يُضاف كحالة دائمة، ولا يُحذف أبداً |

قواعد:
- كل شكوى مستخدم أو خطأ مرصود يصير **حالة اختبار في نفس اليوم**. هذه أعلى قيمة لأقل جهد في المهارة كلها.
- للمحتوى العربي: أدخل لهجة ليبية عامية، وفصحى، ونصاً مختلط العربية والإنجليزية، ونصاً بأرقام عربية-هندية، ونصاً بلا تشكيل وآخر مُشكَّلاً.
- الحالة تحمل **المدخل الكامل** كما يصل الخادم (بما فيه السياق)، لا نسخة مبسّطة منه.
- لا تضع بيانات مستخدم حقيقية بأسماء وأرقام حقيقية في المستودع؛ استبدلها مع الحفاظ على الشكل والطول.

## ملف التقييم بصيغة JSONL

سطر واحد لكل حالة، يُقرأ سطراً سطراً، ويُقارن في git بوضوح (سطر مضاف = حالة مضافة).

```jsonl
{"id":"cls_001","tags":["typical"],"input":{"text":"الطلب وصل ناقص صنف"},"expect":{"type":"exact","field":"category","value":"missing_items"}}
{"id":"cls_014","tags":["edge","dialect"],"input":{"text":"شن هالخدمة هذي شكلها باهي بس التوصيل بطيء"},"expect":{"type":"exact","field":"category","value":"late_delivery"}}
{"id":"cls_031","tags":["refusal"],"input":{"text":"asdkjh"},"expect":{"type":"exact","field":"category","value":"unclear"}}
{"id":"cls_040","tags":["regression","bug-118"],"input":{"text":"الفاتورة 1200 د.ل والمبلغ المخصوم 1350"},"expect":{"type":"exact","field":"category","value":"payment"}}
{"id":"sum_003","tags":["typical"],"input":{"text":"..."},"expect":{"type":"judge","criteria":["يذكر سبب التأخير","لا يتجاوز 3 جمل","عربية فصحى بلا ركاكة ترجمة"]}}
{"id":"rag_007","tags":["typical"],"input":{"q":"كم مدة الاسترجاع؟"},"expect":{"type":"contains_all","values":["14"],"must_cite":["policy.md#returns"]}}
{"id":"rag_022","tags":["refusal"],"input":{"q":"هل عندكم فرع في سبها؟"},"expect":{"type":"json_field","field":"answer","value":null}}
```

الحقول ثابتة: `id` معرّف لا يتغير أبداً، `tags` للترشيح والتقارير، `input` كما يستقبله الخادم، `expect` بنوع محدّد. أسماء الحقول إنجليزية والقيم عربية.

## أنواع المقاييس

| النوع | يُستعمل لـ | التكلفة | الثقة |
|---|---|---|---|
| مطابقة دقيقة | تصنيف، توجيه، استخراج حقل | صفر | كاملة |
| تحقق من الصيغة | JSON صالح، مخطط، حقول إلزامية، طول | صفر | كاملة |
| احتواء/عدم احتواء | وجود رقم أو مصطلح أو رابط، وغياب محظور | صفر | عالية |
| مقاييس استرجاع | RAG: `recall@k`, MRR | صفر | عالية |
| حَكَم نموذجي | نص حر: صحة، أسلوب، اكتمال | متوسطة | متوسطة |
| حكم بشري | معايرة الحَكَم والحالات الحسّاسة | عالية | الأعلى |

**رتّب دائماً بهذا الترتيب**: طبّق كل ما هو مجاني وحتمي أولاً، ولا تستدعِ الحَكَم إلا لما لا يُقاس آلياً. من أشيع الأخطاء استعمال حَكَم نموذجي لتقييم تصنيف — بينما المقارنة النصية المباشرة أدق وأرخص وفورية.

فحوص شكلية يجب أن تكون في كل تقييم مهما كانت المهمة: JSON صالح؟ الحقول الإلزامية موجودة؟ القيمة ضمن `enum`؟ الطول ضمن الحد؟ اللغة عربية حين يجب؟ لا سياج ```` ``` ```` ولا مقدمة ترحيبية؟

## حَكَم النموذج

يُستعمل حين لا يوجد جواب واحد صحيح. مخاطره حقيقية ويجب التعامل معها صراحة:

| الخطر | التخفيف |
|---|---|
| ميل للطول (يفضّل الرد الأطول) | معيار طول صريح في المطالبة، وقِس الطول منفصلاً |
| ميل للموضع (يفضّل الأول في المقارنة) | شغّل المقارنة بالترتيبين واحسب المتوسط |
| ميل لأسلوب نفسه | حَكَم من عائلة نموذج مختلفة عن المنتج حيثما أمكن |
| تساهل عام (كل شيء 8/10) | معايير ثنائية لا درجات، أو مقياس 1–4 بلا منتصف |
| عدم استقرار | حرارة 0، ومخرج مهيكل |

الشكل الفعّال: **معايير ثنائية منفصلة** بدل درجة واحدة مبهمة.

```
أنت مقيّم. احكم على الرد وفق كل معيار بـtrue/false فقط، بلا تسامح.
المعايير:
1. grounded: كل معلومة في الرد موجودة في <context>.
2. complete: يجيب على السؤال كاملاً.
3. format: 3 جمل أو أقل، بلا مقدمة، بلا markdown.
4. language: عربية فصحى سليمة، ليست ترجمة حرفية.
أرجع JSON فقط: {"grounded":bool,"complete":bool,"format":bool,"language":bool,"reason":"سطر واحد"}
```

**المعايرة إلزامية قبل الاعتماد عليه**: قيّم أنت 30 مخرجاً يدوياً، شغّل الحَكَم على نفسها، واحسب نسبة الاتفاق. تحت **85%** الحَكَم غير صالح — أصلح معاييره (غالباً لأنها غامضة) وأعد المعايرة. وأعد المعايرة عند تغيير نموذج الحَكَم أو معاييره؛ تغيير الحَكَم يغيّر كل أرقامك التاريخية فلا تقارن عبره.

الحَكَم يقيس **الاتساق مع معاييرك**، لا الحقيقة. لا تستعمله للحكم على صحة معلومة خارج السياق المعطى.

## المشغّل

سطر أوامر واحد يقرأ JSONL، يستدعي نقطة النهاية الحقيقية على الخادم (لا مسار خاص بالاختبار — وإلا اختبرت شيئاً لا يعمل في الإنتاج)، ويكتب النتائج.

```ts
// eval/run.ts — deno run -A eval/run.ts --file eval/cases.jsonl --tag typical
const cases = (await Deno.readTextFile(file)).split("\n")
  .filter(Boolean).map((l) => JSON.parse(l))
  .filter((c) => !tag || c.tags.includes(tag));

const results = [];
for (const c of cases) {
  const t0 = performance.now();
  let out, err = null;
  try {
    const r = await fetch(`${BASE}/task`, {
      method: "POST",
      headers: { "content-type": "application/json", authorization: `Bearer ${TOKEN}` },
      body: JSON.stringify(c.input),
    });
    out = await r.json();
  } catch (e) { err = String(e); }
  const pass = err ? false : check(c.expect, out);   // مطابقة/صيغة/احتواء، والحَكَم إن لزم
  results.push({ id: c.id, tags: c.tags, pass, ms: Math.round(performance.now() - t0),
                 in_tokens: out?.usage?.input_tokens, out_tokens: out?.usage?.output_tokens,
                 output: out, error: err });
}
```

المخرجات المطلوبة من كل تشغيل:
- ملف `eval/runs/<date>-<prompt_version>-<model>.jsonl` بكل النتائج التفصيلية (يُلتزَم في git).
- ملخّص على الشاشة: النسبة الكلية، نسبة كل `tag`، **قائمة الـid الفاشلة**، متوسط الرموز، وسيط الزمن وp95.
- رمز خروج غير صفري عند الفشل، ليكسر CI.

نفّذ الحالات **بتوازٍ محدود** (5–8 معاً) وإلا اصطدمت بحد المعدّل؛ وثبّت الحرارة على 0 لكل حالة حتمية.

> ربطه بـGitHub Actions ومفاتيح الأسرار: مهارة ops-ci-cd (وسر المفتاح ليس في المستودع).

## الاختبار الانحداري

القاعدة غير القابلة للتفاوض: **لا تعديل على مطالبة إنتاج بلا تشغيل المجموعة قبله وبعده.**

الإجراء:
1. شغّل على `prompts/x.v3` وسجّل النتيجة الأساس.
2. عدّل شيئاً **واحداً** → `v4`.
3. شغّل نفس المجموعة، نفس النموذج، نفس الحرارة.
4. قارن **الحالات المتحوّلة** لا النسبة وحدها: أي id كان ناجحاً وصار فاشلاً؟ هذا هو الانحدار وهو ما يضيع في المتوسط.
5. أي حالة صارت فاشلة تمنع النشر حتى تُفهم — قد تكون توقعاً خاطئاً في المجموعة، وهذا مقبول بعد تصحيح الحالة صراحة.

المعنوية: على 50 حالة، فرق نقطتين إلى ثلاث (حالة أو حالتان) **ضجيج لا نتيجة**. لا تحتفل بارتفاع من 84% إلى 86%. الفروق الجديرة بالثقة على هذا الحجم تبدأ من 8–10 نقاط، أو من تحسّن واضح في فئة `tag` بعينها.

## اختبار A/B للمطالبات

نوعان مختلفان تماماً:

**أوفلاين** (على مجموعة الاختبار): كلا المطالبتين على **نفس الحالات** ونفس النموذج ونفس الحرارة. المقارنة مزدوجة (paired) فتلغى صعوبة الحالات كعامل. هذا ما تفعله يومياً.

**أونلاين** (على مستخدمين حقيقيين): وزّع بثبات حسب `hash(user_id) % 100` لا عشوائياً في كل طلب — وإلا رأى المستخدم سلوكين متناقضين في جلسة واحدة. سجّل `prompt_version` مع كل استدعاء وقِس مؤشراً سلوكياً حقيقياً: نسبة الاستمرار في المحادثة، نسبة إعادة صياغة السؤال (إشارة فشل)، نسبة الإبهام السلبي، نسبة التصعيد لبشري، والتكلفة لكل جلسة. لا تعتمد على "أعجبني" وحده — نسبة استعماله منخفضة ومنحازة.

الأونلاين لا يبدأ إلا بعد أن يتفوق الخيار أوفلاين أو يتعادل. ولا تشغّل تجربتين متداخلتين على نفس الميزة.

## التتبّع عبر الزمن

سجّل صفاً لكل تشغيل: التاريخ، `prompt_version`, `model`, حجم المجموعة, النسبة الكلية, نسبة كل tag, متوسط الرموز, وسيط الزمن. اللوحة البسيطة (جدول في المستودع أو جدول Postgres) تكفي.

ثلاثة أنماط تكشف مشاكل حقيقية:
- **انخفاض بلا تغيير عندك** ← تغيّر النموذج أو تغيّرت بياناتك. لهذا يُثبَّت اسم النموذج بإصدار محدّد.
- **ارتفاع النسبة مع ارتفاع الشكاوى** ← مجموعتك لم تعد تمثّل الواقع؛ أضف حالات جديدة من الاستعمال الفعلي.
- **ثبات 100% لعدة أشهر** ← المجموعة صارت سهلة. أضف حالات أصعب، وإلا فهي زينة لا تكشف شيئاً.

راجع المجموعة كل 4–8 أسابيع: أضف حالات من الشكاوى، أصلح توقعات صارت خاطئة، ولا تحذف حالة انحدار أبداً.

## قائمة تحقق

- [ ] مجموعة اختبار بـ20 حالة على الأقل (الهدف 50–150) من مدخلات حقيقية
- [ ] التوزيع يشمل حالات حدّية وحالات رفض وحالات انحدار سابقة
- [ ] حالات عربية بلهجة وفصحى ونص مختلط وأرقام عربية-هندية
- [ ] الملف JSONL بـ`id` ثابت و`tags` و`input` كامل و`expect` مصنّف
- [ ] لا بيانات مستخدمين حقيقية في المستودع
- [ ] المقاييس الحتمية والشكلية مطبّقة أولاً، والحَكَم لما لا يُقاس آلياً فقط
- [ ] الحَكَم بمعايير ثنائية وحرارة 0، ومعايَر مقابل 30 حكماً بشرياً باتفاق ≥ 85%
- [ ] المشغّل يستدعي نقطة النهاية الحقيقية، بتوازٍ محدود، ويكتب نتائج تفصيلية بالتاريخ والإصدار
- [ ] المشغّل يطبع الـid الفاشلة ويُرجع رمز خروج غير صفري
- [ ] لا تغيير في مطالبة إنتاج بلا تشغيل قبل/بعد ومقارنة الحالات المتحوّلة
- [ ] تعديل واحد في المرة، وفرق أقل من 8 نقاط على 50 حالة لا يُعتبر نتيجة
- [ ] A/B أوفلاين مزدوج قبل أي A/B أونلاين، والتوزيع الأونلاين ثابت بـ`hash(user_id)`
- [ ] `prompt_version` و`model` مسجّلان مع كل استدعاء إنتاج
- [ ] سجل تشغيلات عبر الزمن، ومراجعة للمجموعة كل 4–8 أسابيع، وحالات الانحدار لا تُحذف
