# اختبار قاعدة البيانات

القاعدة الحاكمة: **قيد لم تحاول كسره ليس قيداً — هو تعليق في ملف SQL.** وسياسة RLS لم تُختبر بمستخدم آخر تُعتبر معطّلة.

> كتابة الهجرات وتصميم المخطط: افتح مهارة data-migrations ومهارة data-schema-design.

## البيئة التي تختبر عليها

قاعدة فارغة محلية تصلح لاختبار القيود فقط. اختبار الهجرات يحتاج نسخة تشبه الإنتاج. والإنتاج نفسه لا يُختبر عليه أبداً.

معيار "تشبه الإنتاج": عدد سطور الجداول الكبيرة ضمن نفس رتبة الحجم (إن كان الإنتاج 500k سطر فلا تختبر على 100 سطر)، ونفس الفهارس، ونفس السياسات. هجرة تستغرق 40ms على 100 سطر قد تستغرق 90 ثانية على 500k وتقفل الجدول.

## اختبار الهجرة

لكل ملف هجرة، أربعة أسئلة بأجوبة رقمية:

| السؤال | كيف تقيسه | معيار الفشل |
|---|---|---|
| هل تُطبَّق أصلاً؟ | تشغيلها على نسخة الإنتاج | أي خطأ SQL |
| كم تستغرق؟ | `\timing` أو زمن الوظيفة في CI | > 5 ثوانٍ على جدول حيّ = يحتاج خطة |
| ماذا تقفل؟ | فحص `pg_locks` أثناء التشغيل | `ACCESS EXCLUSIVE` على جدول كبير |
| هل تُطبَّق مرتين بلا ضرر؟ | تشغيلها مجدداً | خطأ يمنع إعادة المحاولة |

```sql
\timing on
\i supabase/migrations/20260909_add_status.sql
-- من جلسة ثانية أثناء التنفيذ: الأقفال والانتظار
select relation::regclass, mode, granted from pg_locks where relation is not null and mode like '%Exclusive%';
select pid, wait_event_type, state, left(query,60) from pg_stat_activity where state='active' and wait_event_type='Lock';
```

اختبار التراجع الحقيقي: طبّق الهجرة، ثم طبّق **هجرة التصحيح الأمامية** وتحقّق أن القاعدة عادت لحالة يعمل معها الإصدار المنشور من التطبيق. سكربت `down` غير مختبر لا قيمة له.

اختبار التوافق مع الإصدار القديم: بعد تطبيق الهجرة على نسخة الاختبار، شغّل عليها **الإصدار السابق من التطبيق**. إن انكسر فالهجرة كاسرة، ومستخدمو المتاجر لم يحدّثوا بعد.

## كسر القيود عمداً

لكل جدول، شغّل هذه المحاولات. كل واحدة **يجب أن تفشل**؛ النجاح هو العطل.

```sql
begin;
insert into orders (user_id, total) values (null, 10);            -- NOT NULL: violates not-null constraint
insert into profiles (user_id, username) values (gen_random_uuid(), 'daood');
insert into profiles (user_id, username) values (gen_random_uuid(), 'daood');  -- UNIQUE: duplicate key
insert into orders (user_id, total) values ('00000000-0000-0000-0000-000000000000', 10);  -- FK: violates foreign key
insert into orders (user_id, total) values (auth.uid(), -5);      -- CHECK: violates check constraint
insert into profiles (username) values (repeat('ا', 5000));       -- الطول: value too long
update orders set status = 'ملغي_جزئياً' where id = '...';         -- enum: invalid input value
rollback;
```

`begin; ... rollback;` يجعل الاختبار غير مدمّر. سجّل النتيجة كجدول: **القيد × المحاولة × نجحت المحاولة (فشل) / رُفضت (نجاح)**.

الخطأ الأكثر شيوعاً هنا: الاعتماد على تحقّق العميل في Flutter فقط. تحقّق العميل تجربة استخدام؛ قيد القاعدة هو الحماية. إن مرّت قيمة سالبة من طلب curl مباشر فالقيد غائب.

## العلاقات والحذف

اختبر سلوك الحذف صراحة لكل مفتاح خارجي، لأن الافتراضي `NO ACTION` وليس ما تتوقعه غالباً:

`on delete cascade`: احذف الأب ثم عُدّ الأبناء — يجب أن يكون 0. `on delete restrict`: احذف أباً له أبناء — يجب أن يفشل الحذف. `on delete set null`: العمود = null والصف باقٍ.

اختبار اليتامى بعد كل هجرة أو استيراد:

```sql
select count(*) from orders o left join auth.users u on u.id = o.user_id where u.id is null;  -- يجب أن يكون 0
```

## اختبار RLS — أهم اختبار في مشروع Supabase

سياسة RLS تُختبر بانتحال شخصية مستخدم داخل معاملة، لا بقراءة نص السياسة.

```sql
-- A = 1111...1111 (أنت)   B = 2222...2222 (الضحية)
begin;
select set_config('request.jwt.claims', '{"sub":"11111111-1111-1111-1111-111111111111","role":"authenticated"}', true);
set local role authenticated;
select count(*) from notes;                                        -- = عدد ملاحظات A فقط
insert into notes (user_id, body) values ('22222222-2222-2222-2222-222222222222','x');  -- violates RLS policy
update notes set body = 'اختُرقت' where user_id = '22222222-2222-2222-2222-222222222222';  -- 0 rows
delete from notes where user_id = '22222222-2222-2222-2222-222222222222';                  -- 0 rows
rollback;

begin; set local role anon; select count(*) from notes; rollback;  -- المتوقع: 0
```

فحوص RLS الإجبارية قبل أي إطلاق:

```sql
-- 1) كل جدول عام عليه RLS مفعّلة
select tablename from pg_tables t
where schemaname = 'public'
and not exists (select 1 from pg_class c
  where c.relname = t.tablename and c.relrowsecurity);
-- المتوقع: صفر سطور

-- 2) كل جدول عليه RLS له سياسة فعلياً (RLS بلا سياسة = منع الكل، عطل صامت)
select c.relname from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname='public' and c.relrowsecurity
and not exists (select 1 from pg_policies p where p.tablename = c.relname);

-- 3) لا سياسة مفتوحة للجميع
select tablename, policyname, roles, qual from pg_policies
where schemaname='public' and (qual = 'true' or qual is null);
```

معيار الحكم ثنائي: **أي سطر في الاستعلام الأول أو الثالث = FAIL ومنع الإصدار.** ولكل جدول جديد يجب أن تُضاف أربع حالات (select/insert/update/delete بمستخدم آخر) قبل دمج الـ PR.

ملاحظة مهمة: دالة `security definer` تتجاوز RLS. اختبر كل دالة RPC بمستخدم عادي وتأكد أنها لا تعيد بيانات مستخدم آخر — الدالة هي الثغرة الأشيع بعد الجدول المكشوف.

## المعاملات والتزامن

- **تحديث ضائع**: شغّل جلستين تقرآن نفس الرصيد ثم تكتبانه. النتيجة الصحيحة تعكس العمليتين، لا واحدة. الحكم: الرصيد النهائي = المتوقع حسابياً.
- **جمود (deadlock)**: جلستان تقفلان صفّين بترتيب معكوس. المتوقع: Postgres يقتل واحدة بخطأ `deadlock detected` — والتطبيق يجب أن يعيد المحاولة لا أن ينهار.
- **حجز مخزون**: 20 طلباً متزامناً على آخر قطعة. المتوقع: طلب واحد ينجح و19 يفشلان برسالة واضحة. أي بيع قطعتين = فشل.
- **معاملة نصف مكتملة**: أوقف العملية بين خطوتين. المتوقع: لا صف يتيم؛ إما الكل أو لا شيء.

## صحّة البيانات بعد الهجرة

بعد كل هجرة تغيّر بيانات، شغّل تحقّقاً رقمياً — لا نظرة بصرية:

```sql
select count(*) from orders;                            -- طابق العدد قبل الهجرة
select count(*) from orders where status is null;       -- 0
select count(*) from orders where total < 0;            -- 0
select count(*) from orders where created_at > now();   -- 0
select status, count(*) from orders group by 1;         -- كل القيم ضمن المسموح
select count(*) from profiles where username <> btrim(username);  -- مسافات زائدة
```

سجّل الأعداد **قبل** الهجرة في التقرير، وقارنها بعدها. "العدد نفسه" جملة قابلة للتحقق؛ "تبدو سليمة" ليست.

## اختبار النسخ الاحتياطي بالاستعادة

نسخة احتياطية لم تُستعَد ليست نسخة احتياطية.

مرة كل شهر على الأقل: خذ آخر نسخة، استعدها إلى قاعدة جديدة فارغة، ثم قِس:

الاستعادة تنجح بلا أخطاء؛ زمنها مُسجَّل بالدقائق (هذا هو RTO الحقيقي)؛ عمر أحدث صف ≤ هدف فقدان البيانات المعلن؛ عدد السطور ضمن الفارق المتوقع؛ السياسات والدوال والفهارس موجودة بعد الاستعادة؛ والتطبيق يعمل على النسخة المستعادة.

> سياسة النسخ والاحتفاظ: افتح مهارة data-backup-recovery.

## التشغيل من الهاتف

اجعل كل ما سبق ملفات SQL في `supabase/tests/` تُشغَّل بوظيفة GitHub Actions على قاعدة اختبار: الهجرات ثم فحوص RLS الثلاثة ثم محاولات كسر القيود ثم تحقّق البيانات. الوظيفة تفشل إن أعاد أي فحص سطراً غير متوقّع. لا شيء يُشغَّل يدوياً على الإنتاج.

## قائمة تحقق

- [ ] الهجرات مُطبَّقة على نسخة بحجم الإنتاج، لا على قاعدة فارغة
- [ ] زمن كل هجرة مقيس ومسجَّل، والأقفال مفحوصة
- [ ] الهجرة قابلة لإعادة التشغيل، وهجرة التصحيح الأمامية مُختبَرة
- [ ] الإصدار السابق من التطبيق يعمل بعد الهجرة
- [ ] محاولة كسر لكل قيد: NOT NULL، UNIQUE، FK، CHECK، الطول، enum
- [ ] كل محاولة كسر رُفضت (نجاحها = عطل)
- [ ] سلوك الحذف المتسلسل مُختبَر لكل مفتاح خارجي
- [ ] لا صفوف يتيمة (العدد = 0)
- [ ] كل جدول عام عليه RLS مفعّلة — الاستعلام يعيد صفر سطور
- [ ] كل جدول عليه RLS له سياسة فعلية
- [ ] لا سياسة `qual = true` مفتوحة
- [ ] لكل جدول أربع حالات RLS بمستخدم آخر + حالة anon
- [ ] كل دالة security definer مُختبَرة بمستخدم عادي
- [ ] التحديث الضائع والجمود والحجز المتزامن مُختبَرة
- [ ] أعداد السطور قبل وبعد الهجرة مسجَّلة ومتطابقة
- [ ] النسخة الاحتياطية استُعيدت فعلياً خلال آخر 30 يوماً وزمنها مسجَّل
- [ ] كل الفحوص تعمل في GitHub Actions وتفشل الوظيفة عند أي سطر غير متوقّع
