# اختبار واجهات HTTP

هذه المهارة عن **ماذا تُختبر وكيف يُحكم على النتيجة**، لا عن تصميم الواجهة.

> تصميم الواجهة نفسها: افتح مهارة data-api-design.

القاعدة الحاكمة: **نقطة نهاية لم تُختبر بحساب مستخدم آخر تُعتبر مكشوفة حتى يثبت العكس.** أغلب الثغرات في تطبيقات Supabase ليست في الكود بل في نقطة نهاية تعمل بشكل صحيح تماماً — لكن لأي شخص.

## الحد الأدنى لكل نقطة نهاية

لكل نقطة نهاية سبع حالات إجبارية. أقل من ذلك = غير مختبرة.

| # | الحالة | معيار النجاح |
|---|---|---|
| 1 | طلب صحيح كامل | 200/201 + جسم مطابق للعقد |
| 2 | حقل إلزامي ناقص | 400 أو 422، لا 500 |
| 3 | نوع خاطئ (نص مكان رقم) | 400/422، لا 500 |
| 4 | بلا رمز مصادقة | 401 |
| 5 | برمز مستخدم آخر | 403 أو 404، وبلا أي تسريب |
| 6 | معرّف غير موجود | 404، لا 200 بجسم فارغ |
| 7 | قيمة حدّية (0، سالب، نص طويل جداً) | مرفوضة بوضوح، لا انهيار |

`500` في أي حالة من 2–7 فشل مباشر. الخادم لا يجوز أن ينهار من مدخل؛ ينهار من عطل داخلي فقط.

## اختبار العقد: شكل الجسم

لا يكفي رمز الحالة؛ تحقّق من:

- وجود كل حقل إلزامي في الاستجابة (لا `null` مكان قيمة).
- نوع كل حقل: `id` نص أم رقم؟ ثبّته. تغيّر النوع بين إصدارين يكسر العميل صامتاً.
- `created_at` بصيغة ISO 8601 مع منطقة زمنية (`2026-09-09T14:03:00Z`) لا بتوقيت محلي بلا لاحقة.
- الأرقام أرقام لا نصوص. `"price": "25.00"` مقابل `"price": 25.00` فرق يكسر الحساب في Dart.
- **لا حقول زائدة**: استجابة المستخدم يجب ألا تحوي `password_hash` ولا `email` لمستخدم غير صاحب الحساب.

معيار الفشل: أي اختلاف عن العقد المسجّل = فشل، حتى لو "التطبيق يعمل" — العميل المنشور على المتاجر لن يُحدَّث في نفس اليوم.

## اختبار التفويض — أهم جزء

جهّز ثلاثة حسابات ثابتة في بيئة الاختبار: `user_a`، `user_b`، `admin`، واحفظ رموزها في أسرار المستودع. ثم شغّل هذه المصفوفة كاملة لكل مورد يملكه مستخدم:

| المحاولة | المتوقع | الفشل يعني |
|---|---|---|
| user_a يقرأ مورد user_a | 200 | — |
| user_a يقرأ مورد user_b | 403/404 | خرق قراءة |
| user_a يعدّل مورد user_b | 403/404 | خرق كتابة (أخطر) |
| user_a يحذف مورد user_b | 403/404 | خرق حذف |
| بلا رمز | 401 | نقطة مفتوحة |
| رمز منتهي الصلاحية | 401 | التحقق من الانتهاء معطّل |
| رمز مشوّه (حرف مُغيَّر) | 401 | التوقيع غير مُتحقَّق منه |
| رمز صحيح لكن مشروع آخر | 401 | `aud`/`iss` غير مفحوص |
| user_a على نقطة إدارة | 403 | تصعيد صلاحية |
| admin على نقطة إدارة | 200 | — |

اختبار عملي: أنشئ صفاً بحساب user_a، خذ `id` من الاستجابة، ثم كرّر الطلب نفسه برمز user_b وبدّل المعرّف فقط. هذا اختبار IDOR وهو الاختبار الأعلى قيمة في المجموعة كلها.

```bash
ID=$(curl -s -X POST "$API/notes" -H "Authorization: Bearer $TOKEN_A" \
  -H "Content-Type: application/json" -d '{"body":"سرّي"}' | jq -r .id)
# الاثنان يجب ألا يعيدا 200
curl -s -o /dev/null -w "%{http_code}\n" "$API/notes/$ID" -H "Authorization: Bearer $TOKEN_B"
curl -s -o /dev/null -w "%{http_code}\n" -X DELETE "$API/notes/$ID" -H "Authorization: Bearer $TOKEN_B"
```

ملاحظة على 403 مقابل 404: إعادة 404 لمورد موجود لا يملكه المستخدم أفضل أمنياً (لا تؤكد وجوده). المهم أن تختار واحدة وتوحّدها، ثم تختبر عليها.

## اختبار المدخلات والحمولات الخبيثة

أرسل هذه القيم في كل حقل نصي وراقب السلوك:

| الحمولة | المتوقع |
|---|---|
| `' OR 1=1 --` | تُخزَّن كنص عادي أو تُرفض — لا تغيّر نتيجة الاستعلام |
| `<script>alert(1)</script>` | تُخزَّن كنص، وتُهرَّب عند العرض في الويب |
| نص 100000 حرف | 413 أو 422، لا تعليق ولا 500 |
| `null` صريحة في حقل إلزامي | 422 |
| `-1` في حقل كمية | 422 |
| `999999999999999999999` في عدد صحيح | 422 لا overflow |
| مصفوفة مكان نص | 422 |
| رموز تشكيل عربية وإيموجي | تُخزَّن وتُعاد كما هي (UTF-8 سليم) |
| مسار `../../etc/passwd` في اسم ملف | مرفوض |
| رأس `Content-Type` خاطئ | 415 |

اختبار العربية ليس ترفاً: تكسّر الترميز يظهر عادة أول ما يظهر في واجهة HTTP لا في التطبيق.

## شكل الأخطاء موحّد

اختبر أن **كل** خطأ يعيد نفس البنية، وإلا فمعالجة الأخطاء في العميل ستحتاج حالات خاصة:

```json
{ "error": { "code": "validation_failed", "message": "الكمية يجب أن تكون أكبر من صفر", "field": "quantity" } }
```

معايير الفشل هنا: رسالة خطأ تحوي أثر المكدّس (stack trace)، أو اسم جدول، أو استعلام SQL، أو مسار ملف على الخادم — كلها فشل أمني لا مجرد فشل شكل. ورسالة الخطأ الموجّهة للمستخدم عربية؛ و`code` إنجليزي ثابت لأن العميل يفرّع عليه.

## الترقيم والترشيح والترتيب

| الاختبار | معيار النجاح |
|---|---|
| صفحة أولى بلا معطيات | حجم افتراضي محدّد (مثلاً 20)، لا الجدول كاملاً |
| `limit=100000` | يُقصّ إلى الحد الأقصى، لا يُنفَّذ |
| `limit=-1` أو `limit=abc` | 422 |
| صفحة أبعد من النهاية | 200 بمصفوفة فارغة، لا 404 ولا 500 |
| مجموع صفحتين | لا تكرار ولا سطر مفقود |
| ترتيب بعمود غير موجود | 422، لا حقن في `ORDER BY` |
| ترشيح بقيمة لا تطابق شيئاً | 200 بمصفوفة فارغة |

اختبار التكرار مهم: مع ترقيم بالإزاحة (offset) وإدراج متزامن، قد يظهر عنصر مرتين. اجمع صفحتين وتحقّق أن عدد المعرّفات الفريدة = عدد السطور.

## تحديد المعدّل والطلبات المتكرّرة

- أرسل 100 طلب متتالٍ لنقطة تسجيل الدخول. المتوقع: 429 قبل الطلب المئة، مع رأس `Retry-After`.
- بعد انقضاء النافذة يعود 200. حدّ لا يُفتح ثانية = عطل.
- **الطلب المكرّر (idempotency)**: أرسل نفس طلب الإنشاء مرتين بنفس مفتاح `Idempotency-Key`. المتوقع: صفّ واحد فقط في القاعدة. هذا يحاكي ضغط المستخدم مرتين على شبكة بطيئة — وهو أكثر أعطال الدفع شيوعاً.
- أرسل طلبين متزامنين يعدّلان نفس الصف. المتوقع: نتيجة متّسقة، لا فقدان تحديث صامت.

## أوامر جاهزة

```bash
H="Authorization: Bearer $TOKEN"

curl -s -o /dev/null -w "code=%{http_code} time=%{time_total}s\n" "$API/items" -H "$H"   # الحالة والزمن
curl -s "$API/items/1" -H "$H" | jq -e '.price | type == "number"'                      # نوع الحقل
curl -s "$API/profile" -H "$H" | jq -e 'has("password_hash") | not'                      # غياب حقل حسّاس

python3 -c "print('{\"name\":\"'+'ا'*100000+'\"}')" > /tmp/big.json                       # نص طويل
curl -s -o /dev/null -w "%{http_code}\n" -X POST "$API/items" -H "Content-Type: application/json" --data @/tmp/big.json

for i in $(seq 1 100); do curl -s -o /dev/null -w "%{http_code} " -X POST "$API/auth/login" \
  -H "Content-Type: application/json" -d '{"email":"x@y.z","password":"wrong"}'; done; echo   # تحديد المعدّل
```

`jq -e` يعيد رمز خروج غير صفري عند الفشل، فيصلح مباشرةً كتأكيد داخل سكربت CI.

## التشغيل في CI

من الهاتف لا تشغّل الحزمة محلياً — اجعلها وظيفة في GitHub Actions تعمل على كل PR وقبل كل وسم إصدار. اجعل الحزمة تخرج برمز غير صفري عند أول فشل تفويض، واعتبرها بوابة تمنع الدمج. رموز الاختبار في أسرار المستودع، وبيئة الاختبار قاعدة منفصلة عن الإنتاج — لا تشغّل اختبار حذف على بيانات حقيقية أبداً.

> إعداد سير العمل: افتح مهارة ops-github-actions.

## قائمة تحقق

- [ ] لكل نقطة نهاية الحالات السبع الإجبارية مغطّاة
- [ ] ثلاثة حسابات اختبار ثابتة (user_a, user_b, admin) ورموزها في الأسرار
- [ ] مصفوفة التفويض كاملة لكل مورد يملكه مستخدم
- [ ] اختبار IDOR: تبديل المعرّف برمز مستخدم آخر
- [ ] رمز منتهٍ ورمز مشوّه يعيدان 401
- [ ] لا حقول حسّاسة زائدة في أي استجابة
- [ ] الحمولات الخبيثة العشر مُرسلة في كل حقل نصي
- [ ] لا 500 في أي حالة مدخلات
- [ ] لا أثر مكدّس ولا اسم جدول في أي رسالة خطأ
- [ ] شكل الخطأ موحّد في كل النقاط ورسالته عربية
- [ ] الترقيم: لا تكرار ولا سطر مفقود بين صفحتين
- [ ] `limit` مقصوص عند حدّ أقصى
- [ ] 429 يظهر ثم تُفتح النافذة
- [ ] الطلب المكرّر ينتج صفاً واحداً
- [ ] الأحرف العربية والإيموجي تعود سليمة
- [ ] الحزمة تعمل في GitHub Actions على كل PR وتمنع الدمج عند الفشل
