# تصميم واجهات البرمجة

مهارة جانب الخادم: شكل العقد الذي يوقّعه الخادم مع العملاء. القيد الحاكم في حالتك: تطبيق منشور في Google Play وApp Store لا تستطيع إجبار المستخدم على تحديثه. **كل قرار هنا يُقاس بأثره على نسخة قديمة تعمل الآن على هاتف شخص ما.**

> استهلاك هذه الواجهات من Flutter: مهارة flutter-networking-api.

## تسمية الموارد

| القاعدة | صواب | خطأ |
|---|---|---|
| أسماء لا أفعال | `/orders` | `/getOrders` |
| جمع دائماً | `/orders/{id}` | `/order/{id}` |
| تداخل بمستوى واحد فقط | `/orders/{id}/items` | `/users/{u}/orders/{o}/items/{i}` |
| شرطة لا شرطة سفلية | `/order-items` | `/order_items` |
| حروف صغيرة | `/invoices` | `/Invoices` |
| لا امتداد صيغة | `/orders` + `Accept` | `/orders.json` |

العلاقة العميقة تُختصر بمعرّف: `/order-items?order_id=123` بدل تداخل ثلاثي. والإجراءات التي ليست CRUD تصير مورداً فرعياً بفعل صريح، `POST /orders/{id}/cancel` — أوضح وأأمن من `PATCH {status:"cancelled"}` لأنه يسمح بقواعد وصلاحيات مستقلة. واستعمل `id` معتماً (uuid) في المسارات العامة؛ الأرقام المتسلسلة تكشف حجم عملك وتسمح بالتعداد.

## الأفعال ورموز الحالة

GET قراءة آمنة وidempotent، POST إنشاء أو إجراء وليس idempotent، PUT استبدال كامل وidempotent، PATCH تعديل جزئي وليس بالضرورة idempotent، DELETE حذف وidempotent.

| الرمز | متى بالضبط |
|---|---|
| 200 | نجاح مع جسم |
| 201 | إنشاء — مع ترويسة `Location` والمورد في الجسم |
| 202 | قُبل للمعالجة لاحقاً (طابور) |
| 204 | نجاح بلا جسم (DELETE) |
| 400 | جسم غير صالح شكلياً |
| 401 | لا هوية أو رمز منتهٍ |
| 403 | هوية صحيحة، صلاحية ناقصة |
| 404 | غير موجود — أو موجود ولا تملك رؤيته |
| 409 | تعارض حالة (SKU مكرر، طلب مُلغى مسبقاً) |
| 410 | كان موجوداً وأزيل نهائياً |
| 422 | صالح شكلياً، فاشل في قواعد العمل |
| 429 | تجاوز المعدّل — مع `Retry-After` |
| 5xx | خطأ الخادم — لا تُرجعه لخطأ مدخلات |

401 تعني "أعد تسجيل الدخول" و403 تعني "لا تحاول ثانية"؛ خلطهما يجعل العميل يمسح الجلسة بلا داعٍ. وأرجع 404 بدل 403 عندما مجرد معرفة وجود المورد تسريب (طلب مستخدم آخر). لا ترجع 200 مع `{"error": ...}` في الجسم — العميل يقرأ الرمز أولاً. وفي التحقق أرجع **كل** أخطاء الحقول دفعة واحدة في 422 لا أول خطأ فقط، وإلا أصلح المستخدم حقلاً واحداً في كل محاولة.

## الترقيم: offset مقابل cursor

| | offset/limit | cursor (keyset) |
|---|---|---|
| الاستعلام | `offset 10000 limit 20` | `where (created_at, id) < ($1,$2) limit 20` |
| التكلفة عند الصفحة 500 | يقرأ 10020 صفاً ويرمي 10000 | ثابتة |
| صفوف مكرّرة/مفقودة عند الإدراج | نعم، حتمي | لا |
| القفز لصفحة رقم N | ممكن | غير ممكن |
| عدد الصفحات الإجمالي | ممكن (بتكلفة) | غير عملي |

القرار: **cursor لكل قائمة يتصفّحها المستخدم في التطبيق** (تمرير لانهائي). offset فقط للوحات إدارية بجداول صغيرة تحتاج ترقيم صفحات مرئي.

السبب الحاسم ليس الأداء وحده: مع offset، إن أُدرج صف جديد بين طلب الصفحة 1 والصفحة 2، فالصف الأخير من الصفحة 1 يظهر مرة ثانية. المستخدم يرى عنصراً مكرراً في قائمته.

```sql
-- المفتاح المركّب يمنع التعادل ويجب أن يطابق فهرساً
select id, title, created_at from posts
where (created_at, id) < ($1::timestamptz, $2::uuid)
order by created_at desc, id desc
limit 20;
```
```json
{ "data": [ ... ],
  "page": { "next_cursor": "eyJjIjoiMjAyNi0wOS0wOVQxMDoxMjozM1oiLCJpIjoiOWY...", "has_more": true } }
```

المؤشّر معتم (base64 لمفتاح الترتيب): لا تسمح للعميل ببنائه ولا تعده جزءاً من العقد، وهو مرتبط بالترتيب والترشيح فإن غيّرهما العميل بدأ من الصفر. و`limit` له سقف صارم على الخادم (افتراضي 20، أقصى 100) — لا تثق بقيمة العميل. ولا تُرجع `total` مع cursor إلا بطلب صريح؛ `count(*)` على جدول كبير يهدم زمن الاستجابة.

## الترشيح والترتيب

```
GET /orders?status=open&created_after=2026-09-01&sort=-created_at&limit=20
```

الترشيح `field=value` للمساواة ولاحقة صريحة للنطاق (`price_min`, `price_max`, `created_after`) — تجنّب لغة استعلام مصغّرة داخل النص. والترتيب `sort=-created_at` بالبادئة `-` للتنازلي، مع **قائمة بيضاء** بأسماء الأعمدة؛ تمرير مدخل المستخدم إلى `ORDER BY` ثغرة حقن. وكل تركيبة ترشيح+ترتيب مسموحة يقابلها فهرس، وإن لم يوجد فلا تعرض الخيار. أما `?fields=id,title` فيقلّل حجم النقل على شبكات الجوال لكنه يعقّد التخزين المؤقت — ابدأ باستجابة واحدة مضبوطة.

## الإصدارات

| الأسلوب | الحكم |
|---|---|
| `/v1/orders` في المسار | الأوضح والأسهل للتوجيه والسجلات — الافتراضي |
| ترويسة `Accept: application/vnd.app.v2+json` | أنقى نظرياً، مؤلم عملياً على الجوال |
| `?version=2` | يُنسى في التخزين المؤقت — تجنّبه |

ارفع الإصدار الرئيسي **فقط** عند تغيير كاسر لا يمكن تجنّبه؛ رفعه يعني تشغيل نسختين معاً لأشهر، والحد الأدنى الواقعي لعمر إصدار 6–12 شهراً بعد إيقاف دعمه رسمياً. وأضف دائماً ترويسة `X-Client-Version` من التطبيق — بدونها لا تستطيع قياس نسبة الإصدارات القديمة ولا تعرف متى يجوز إسقاط شيء.

## أشكال الاستجابة والأخطاء

استجابة ناجحة موحّدة `{ "data": { ... } }`، وقائمة `{ "data": [ ... ], "page": { "next_cursor": null, "has_more": false } }`. وخطأ موحّد — اتبع نمط `application/problem+json` (RFC 9457) أو شكلاً ثابتاً مكافئاً:
```json
{
  "error": {
    "code": "insufficient_stock",
    "message": "الكمية المطلوبة غير متوفرة",
    "details": [
      { "field": "items[0].qty", "code": "max", "max": 3 }
    ],
    "request_id": "req_01J9X..."
  }
}
```

قواعد صارمة:
- `code` معرّف ثابت بالإنجليزية **لا يتغير أبداً** — عليه يبني العميل منطقه؛ و`message` نص للعرض قابل للتغيير. لا تعتمد على مطابقة نصه في العميل: أرسل `code` ودع التطبيق يترجمه محلياً (الأفضل للعمل بلا اتصال).
- `request_id` في كل استجابة خطأ وفي سجلات الخادم — الجسر الوحيد بين شكوى مستخدم وسطر سجل.
- لا تسرّب رسائل القاعدة الخام (`duplicate key value violates unique constraint "..."`)؛ حوّلها إلى `code` معروف.
- التواريخ ISO 8601 بـ UTC مع `Z` دائماً، والمال عدد صحيح بأصغر وحدة + `currency`: `{"amount_minor": 25000, "currency": "LYD"}` لا `"25.000 د.ل"`. التنسيق المحلي والأرقام العربية-الهندية قرار عرض لا يظهر في JSON إطلاقاً.

## Idempotency

الشبكة على الجوال في ليبيا تنقطع في منتصف الطلب باستمرار. العميل يعيد المحاولة، والنتيجة طلبان.

```
POST /orders
Idempotency-Key: 9c1f...ولّده العميل مرة واحدة لكل نية
```

آلية الخادم: جدول `idempotency_keys(key primary key, user_id, request_hash, status, response jsonb, created_at)`. عند الوصول حاول `insert ... on conflict do nothing`؛ فشل الإدراج يعني أن المفتاح مستعمل. إن كانت حالته `completed` أرجع الاستجابة المخزّنة بنفس رمز الحالة، وإن كانت `in_progress` أرجع 409 ليعيد العميل الطلب بعد قليل. وإن اختلف `request_hash` عن الأصلي بنفس المفتاح أرجع 422 — إعادة استعمال مفتاح لجسم مختلف خطأ برمجي. احتفظ بالمفاتيح 24–72 ساعة ثم احذفها بمهمة pg_cron.

المفتاح يُولَّد **مرة واحدة عند نية المستخدم** لا عند كل محاولة إرسال؛ توليده داخل دالة إعادة المحاولة يُبطل الغرض كله. وهو إلزامي على إنشاء طلب وتسجيل دفعة وتحويل رصيد وإرسال SMS مدفوعة. GET/PUT/DELETE idempotent بطبيعتها، والحاجة الحقيقية في POST.

## تحديد المعدّل

```
429 Too Many Requests
Retry-After: 30
RateLimit-Limit: 60
RateLimit-Remaining: 0
RateLimit-Reset: 30
```

| المسار | حد معقول |
|---|---|
| تسجيل الدخول / التسجيل | 5–10 لكل IP لكل 15 دقيقة |
| إرسال OTP | 3 لكل رقم لكل ساعة، و10 لكل IP يومياً |
| قراءة عامة | 60–120 لكل دقيقة لكل مستخدم |
| كتابة | 20–30 لكل دقيقة لكل مستخدم |
| بحث/ذكاء اصطناعي مكلف | 10 لكل دقيقة + سقف يومي |

الحد على المستخدم لا على IP وحده: في ليبيا يشترك عدد كبير من المستخدمين خلف NAT واحد، والحد على IP سيحجب أبرياء. والنافذة المنزلقة أعدل من الثابتة التي تسمح بضِعف الحد على حدّ النافذتين. أعد `Retry-After` دائماً مع 429 وإلا أعاد العميل المحاولة فوراً وضاعف الحمل. وOTP له تكلفة نقدية لكل رسالة — حدّه أضيق حدّ عندك.

## OpenAPI

ملف `openapi.yaml` واحد في المستودع يُراجَع في نفس الـ PR الذي يغيّر السلوك. الحد الأدنى المفيد: كل مسار، كل رمز حالة محتمل، مخططات الطلب والاستجابة والخطأ الموحّد، وقائمة `code` الكاملة. ولّد منه نماذج العميل واختبارات العقد والتوثيق — التوثيق المكتوب يدوياً يتقادم خلال أسابيع.

إن كانت واجهتك هي PostgREST من Supabase فهي تولّد OpenAPI تلقائياً، لكن هذا **ليس** عقداً عاماً: لأي واجهة يستهلكها طرف ثالث اكتب طبقة صريحة (Edge Function) وعقداً صريحاً، لأن كشف PostgREST مباشرة يربط شكل جداولك بعملائك للأبد.

## التوافق للخلف

القاعدة الحاكمة: افترض أن نسخة من تطبيقك عمرها سنة تعمل الآن ولن تُحدَّث.

**آمن دائماً (إضافي فقط):** إضافة حقل اختياري جديد في الاستجابة، إضافة معامل طلب اختياري قيمته الافتراضية = السلوك القديم، إضافة نقطة نهاية جديدة، وإضافة قيمة جديدة في enum **فقط** إن كان العميل يتعامل مع المجهول بأمان (شرط سبق ونشرته).

**كاسر دائماً:** حذف أو إعادة تسمية حقل، تغيير نوع حقل (`"12"` إلى `12`)، جعل حقل اختياري إلزامياً، تغيير رمز حالة لحالة قائمة، تغيير معنى `code` خطأ موجود، تغيير الترتيب الافتراضي لقائمة، وتشديد قاعدة تحقق (خفض حد أقصى لطول نص).

الحذف يمرّ بثلاث مراحل: أوقف الاستعمال في العميل الجديد → علّم الحقل `deprecated` في OpenAPI وراقب استعماله بـ `X-Client-Version` → احذفه بعد نزول الاستعمال تحت 1–2%. ولا تعِد استعمال اسم حقل قديم لمعنى جديد أبداً — أسوأ من الحذف لأنه يفشل بصمت.

أضف من اليوم الأول نقطة `GET /config` تُرجع الحد الأدنى المطلوب من الإصدار ورسالة تحديث؛ إن لم تنشرها في الإصدار الأول فلن تملك أبداً وسيلة لإجبار تحديث عند اضطرار حقيقي. عملياً كل تغيير كاسر يعني إما إصدار API جديد أو إجبار تحديث، والاثنان مكلفان — فصمّم الاستجابة الأولى بعناية أكبر مما تظن ضرورياً.

## قائمة تحقق

- [ ] المسارات أسماء بصيغة الجمع، بلا أفعال، بتداخل مستوى واحد
- [ ] كل نقطة نهاية تُرجع الرمز الصحيح، و401 و403 مفصولان بوضوح
- [ ] كل قائمة يتصفّحها المستخدم تستعمل cursor معتماً مبنياً على `(sort_col, id)` يقابله فهرس
- [ ] `limit` له سقف على الخادم؛ لا `count` إجمالي بلا طلب صريح
- [ ] أسماء أعمدة الترتيب من قائمة بيضاء، وكل تركيبة لها فهرس
- [ ] شكل استجابة موحّد + شكل خطأ موحّد فيه `code` ثابت و`request_id`
- [ ] لا رسائل قاعدة بيانات خام تصل للعميل
- [ ] التواريخ ISO 8601 UTC، والمال عدد صحيح + عملة
- [ ] `Idempotency-Key` مدعوم على كل POST يُنشئ أو يدفع، بمفتاح يُولَّد مرة لكل نية
- [ ] حدود معدّل على تسجيل الدخول وOTP والكتابة، مع `Retry-After`
- [ ] الحد على المستخدم لا على IP وحده
- [ ] `openapi.yaml` محدَّث في نفس الـ PR الذي يغيّر السلوك
- [ ] كل تغيير مُصنَّف "إضافي" أو "كاسر" قبل الدمج
- [ ] `X-Client-Version` مُسجَّل، و`GET /config` بالحد الأدنى للإصدار منشورة منذ الإصدار الأول
