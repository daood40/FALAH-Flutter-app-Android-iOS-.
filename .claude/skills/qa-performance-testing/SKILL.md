# قياس الأداء والحكم عليه

هذه المهارة **قياس وحكم**، لا إصلاح.

> إصلاح البطء في Flutter: افتح مهارة flutter-performance. وفي الويب: مهارة web-performance.

القاعدة الحاكمة: **لا قياس بلا هدف رقمي مكتوب مسبقاً.** "التطبيق سريع" ليست نتيجة اختبار. النتيجة: "الإقلاع البارد 1.8 ثانية، الهدف ≤ 2.5 — PASS".

## أولاً: اكتب الأهداف قبل أن تقيس

الهدف يُكتب في المستودع قبل القياس، وإلا فستفسّر أي رقم حصلت عليه بأنه مقبول. لكل هدف: **المقياس، القيمة، الجهاز، الشرط**.

مثال صالح: "زمن فتح شاشة الطلبات ≤ 800ms، على Redmi 9A، بشبكة 3G محاكاة، ببيانات 200 سطر".
مثال غير صالح: "الشاشة تفتح بسرعة".

## أهداف التطبيق — أرقام مرجعية

| المقياس | ممتاز | مقبول | فشل |
|---|---|---|---|
| إقلاع بارد (جهاز ضعيف) | ≤ 1.5s | ≤ 2.5s | > 3s |
| إقلاع دافئ | ≤ 0.8s | ≤ 1.5s | > 2s |
| فتح شاشة من نقرة | ≤ 300ms | ≤ 500ms | > 1s |
| استجابة نقرة مرئية | ≤ 100ms | ≤ 200ms | > 300ms |
| معدّل الإطارات أثناء التمرير | 60fps ثابت | ≥ 55fps متوسط | < 50fps |
| إطارات متأخرة في تمرير 10 ثوانٍ | 0 | ≤ 1% | > 5% |
| زمن الإطار (P99) | ≤ 16ms | ≤ 24ms | > 32ms |
| ذاكرة بعد 5 دقائق استخدام | ≤ 150MB | ≤ 250MB | > 400MB أو نمو مستمر |
| حجم AAB | ≤ 15MB | ≤ 30MB | > 60MB |
| استهلاك البطارية في 30 دقيقة | ≤ 3% | ≤ 6% | > 10% |

عتبة الإطار: عند 60Hz الميزانية 16.7ms؛ الإطار الذي يتجاوزها يُعدّ متأخراً. على شاشة 120Hz الميزانية 8.3ms — حدّد التردد في التقرير وإلا فالرقم بلا معنى.

اختبار الذاكرة الأهم: افتح شاشة ثقيلة وأغلقها 20 مرة. إن لم تعد الذاكرة قريباً من قيمتها الأولى فهناك تسريب — والحكم هنا **نمط لا رقم**: الخط الصاعد فشل حتى لو بقي تحت السقف.

## أهداف الويب

| المقياس | ممتاز | مقبول | فشل |
|---|---|---|---|
| LCP | ≤ 2.5s | ≤ 4.0s | > 4.0s |
| INP | ≤ 200ms | ≤ 500ms | > 500ms |
| CLS | ≤ 0.1 | ≤ 0.25 | > 0.25 |
| TTFB | ≤ 0.8s | ≤ 1.8s | > 1.8s |
| حجم JS المضغوط | ≤ 170KB | ≤ 300KB | > 500KB |
| عدد الطلبات في التحميل الأول | ≤ 30 | ≤ 50 | > 80 |

هذه القيم تُقاس عند **الشريحة 75** من المستخدمين الحقيقيين، لا على أفضل تحميل عندك. قياس المختبر (Lighthouse) مؤشّر ترتيب لا حكم نهائي؛ الحكم من بيانات الميدان.

ملاحظة للعربية: الخطوط العربية أثقل من اللاتينية، وتحميل خط عربي كامل قد يضيف 200–400KB ويؤخّر LCP. قِس LCP مع الخط الفعلي لا مع خط النظام.

## شروط القياس الصحيحة

هذه الشروط تُبطل النتيجة إن خُرقت:

| الشرط | لماذا |
|---|---|
| جهاز حقيقي ضعيف، لا محاكي | المحاكي يستعمل معالج الحاسوب — أرقامه لا تمثّل شيئاً |
| وضع `--profile` أو `--release` | وضع debug أبطأ 3–10 أضعاف، وقياسه هدر وقت |
| البطارية > 30% وغير موصول بشاحن | إدارة الطاقة تخفض التردد |
| لا تطبيقات ثقيلة في الخلفية | تشويش عشوائي |
| قياس أول بعد تثبيت نظيف | الإقلاع البارد الأول يشمل تهيئة لمرة واحدة |
| تكرار 3 مرات وأخذ **الوسيط** | القيمة الواحدة ضجيج |
| شبكة محدّدة ومذكورة | الشبكة تغيّر الأرقام أكثر من الكود |

الجهاز المرجعي: اختر جهازاً واحداً ضعيفاً يمثّل الشريحة الدنيا لمستخدميك (فئة 2–4GB RAM شائعة في السوق الليبي) وثبّته لكل القياسات. تغيير الجهاز بين إصدارين يجعل المقارنة بلا معنى.

الخطأ الأكثر شيوعاً: القياس على أحدث هاتف بشبكة WiFi سريعة، ثم إعلان أن الأداء ممتاز. أرقامك عندئذ تصف جهازك أنت لا مستخدميك.

## كيف تقيس عملياً

```bash
# إقلاع بارد على أندرويد — كرّر 3 مرات وخذ الوسيط
adb shell am force-stop com.example.app
adb shell am start-activity -W -n com.example.app/.MainActivity | grep TotalTime

# قياس بلا cache (بارد فعلاً)
adb shell pm clear com.example.app

# الذاكرة الآن
adb shell dumpsys meminfo com.example.app | grep TOTAL

# حجم الحزمة
ls -lh build/app/outputs/bundle/release/*.aab
```

لزمن الإطارات، شغّل التطبيق في وضع profile وسجّل جلسة تمرير محدّدة (نفس القائمة، نفس عدد العناصر، نفس مدّة التمرير) واستخرج عدد الإطارات التي تجاوزت الميزانية. المهم أن **تكرّر نفس السيناريو حرفياً** بين الإصدارات؛ سيناريو مختلف = مقارنة باطلة.

للويب: قِس LCP/INP/CLS بأداة قياس في المتصفّح على اتصال مخنوق (Slow 4G) ومعالج مبطّأ 4×، ثم تحقّق من بيانات المستخدمين الحقيقيين عبر مزوّد التحليلات لديك.

## خط الأساس والمقارنة

سجّل بعد كل إصدار ملف قياس في المستودع:

```
version: 1.4.0   date: 2026-09-09   device: Redmi 9A   mode: release   net: 4G
cold_start_ms: 1840        (median of 1790/1840/1910)
orders_screen_ms: 620
scroll_p99_frame_ms: 21
jank_pct: 0.9
mem_after_5min_mb: 178
aab_mb: 21.4
```

قاعدة الحكم على التراجع بين إصدارين:

| التغيّر مقابل خط الأساس | الحكم |
|---|---|
| تحسّن أو ثبات ±5% | PASS |
| تراجع 5–15% | تحذير — يُوثَّق ويُفتح عطل، الإصدار يمرّ |
| تراجع > 20% في مقياس رئيسي | **مانع للإصدار** |
| تجاوز عتبة "فشل" في الجدول المرجعي | **مانع للإصدار** بغضّ النظر عن التغيّر النسبي |
| نمو الذاكرة مستمر بلا استقرار | مانع للإصدار |
| زيادة حجم الحزمة > 20% بلا سبب معروف | تحذير + تفسير إلزامي |

هامش ±5% ليس تساهلاً: هو ضجيج القياس الطبيعي على جهاز حقيقي. ولهذا يُؤخذ الوسيط من ثلاث محاولات — لولا ذلك لصار كل إصدار "تراجعاً".

## القياس في CI

ما يمكن قياسه آلياً على GitHub Actions بلا جهاز:

- حجم الحزمة بعد كل بناء، مع مقارنة بخط الأساس وإفشال الوظيفة عند تجاوز حدّ مكتوب.
- حجم حزمة JS ومصاريف التبعيات في الويب.
- زمن البناء نفسه (مؤشر غير مباشر لكن مفيد).
- Lighthouse على النشر المؤقّت للويب، مع حدّ أدنى للنتيجة.

ما **لا** يُقاس آلياً بلا أجهزة حقيقية: زمن الإقلاع ومعدّل الإطارات والذاكرة. هذه تبقى قياساً يدوياً على جهازك المرجعي مرة قبل كل إصدار، وتُسجَّل في ملف القياس. لا تدّعِ أرقام إطارات من CI.

> إعداد الوظيفة: افتح مهارة ops-github-actions.

## قائمة تحقق

- [ ] الأهداف الرقمية مكتوبة في المستودع قبل القياس
- [ ] كل هدف يذكر المقياس والقيمة والجهاز والشرط
- [ ] القياس على جهاز حقيقي ضعيف مرجعي ثابت، لا على محاكي ولا على جهاز قوي
- [ ] الوضع release أو profile، لا debug أبداً
- [ ] البطارية فوق 30% وغير موصول بشاحن ولا تطبيقات ثقيلة تعمل
- [ ] كل قياس مكرّر 3 مرات والوسيط هو المسجَّل
- [ ] نفس السيناريو حرفياً بين الإصدارات
- [ ] الإقلاع البارد مقيس بعد مسح بيانات التطبيق
- [ ] تردّد الشاشة مذكور مع أرقام الإطارات
- [ ] اختبار التسريب: 20 فتح/إغلاق والذاكرة تستقر
- [ ] الشبكة المستعملة مذكورة في التقرير
- [ ] الويب: LCP وINP وCLS مقيسة على اتصال مخنوق ومعالج مبطّأ
- [ ] الويب: قيم الميدان عند الشريحة 75 لا قياس المختبر وحده
- [ ] LCP مقيس مع الخط العربي الفعلي
- [ ] ملف خط أساس محفوظ في المستودع لكل إصدار
- [ ] قاعدة التراجع مطبَّقة: > 20% أو تجاوز عتبة الفشل = منع الإصدار
- [ ] حجم الحزمة مقيس آلياً في CI مع حدّ يفشل الوظيفة
- [ ] لا أرقام إطارات أو ذاكرة مُدَّعاة من CI بلا جهاز حقيقي
