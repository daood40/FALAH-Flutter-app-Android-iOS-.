# إدارة الحالة في React

مسار الويب — ليس Flutter. الفكرة الحاسمة: **معظم "مشاكل إدارة الحالة" هي حالة خادم موضوعة في المكان الخطأ.** صنّف أولاً، ثم اختر الأداة.

## تصنيف الحالة قبل اختيار أي مكتبة

| النوع | أمثلة | مصدر الحقيقة | الأداة |
|---|---|---|---|
| **حالة خادم** | قائمة الطلبات، الملف الشخصي، المخزون | قاعدة البيانات | TanStack Query (أو استعلامات الإطار) |
| **حالة عميل** | فتح درج، خطوة معالج، الوضع الداكن | الذاكرة/المتصفح | `useState` / `useReducer` / Zustand |
| **حالة عنوان** | الفلاتر، البحث، الصفحة، التبويب | شريط العنوان | `URLSearchParams` / موجّه المسارات |
| **حالة نموذج** | قيم الحقول، الأخطاء، حالة الإرسال | مكوّن النموذج | `react-hook-form` |
| **مشتقّة** | العدد، الإجمالي، النتائج المفلترة | لا شيء — تُحسب | حساب أثناء الرسم |

قاعدة تشخيصية: إن كانت البيانات موجودة في قاعدة البيانات ويمكن أن يغيّرها شخص آخر، فهي **حالة خادم**. نسخها إلى `useState` يجعلها قديمة فوراً، ويولّد كل المشاكل المعروفة: تحميل مكرر، بيانات قديمة، `useEffect` متشابكة، مزامنة يدوية بين شاشات.

## useState مقابل useReducer

استعمل `useReducer` عندما يتحقق أحد هذه:

- 3+ قيم حالة تتغيّر معاً في نفس اللحظة.
- التحديث التالي يعتمد على عدة قيم سابقة.
- توجد انتقالات محظورة (لا تنتقل من `idle` إلى `success` مباشرة).
- تريد اختبار منطق التحديث بمعزل عن الواجهة.

```jsx
const initial = { status: "idle", items: [], error: null };

function reducer(state, action) {
  switch (action.type) {
    case "load":    return { ...state, status: "loading", error: null };
    case "success": return { status: "ready", items: action.items, error: null };
    case "fail":    return { ...state, status: "error", error: action.error };
    default:        return state;
  }
}
```

فائدة عملية: الحالة كـ **آلة حالات** تمنع التركيبات المستحيلة مثل `loading: true` و`error` معاً — وهي أكثر مصدر لواجهات مرتبكة (سبينر فوق رسالة خطأ).

## السياق (Context) ومتى يضرّ

`useContext` **آلية تمرير، لا آلية إدارة حالة**. لا يوجد فيه اشتراك انتقائي: أي تغيّر في القيمة يُعيد رسم **كل** المستهلكين.

| مناسب | غير مناسب |
|---|---|
| الثيم، اللغة/الاتجاه، المستخدم الحالي | بيانات تتغيّر كل ثانية |
| قيم نادرة التغيّر | حالة عامة كثيرة القراءة والكتابة |
| حقن اعتماديات (عميل API) | بديل عن مكتبة حالة خادم |

- إن كانت المشكلة "تمرير prop عبر مستويين"، فالحل التركيب (`children`) لا السياق.
- إن اضطررت للسياق مع بيانات متغيّرة، افصله إلى سياقين: واحد للقيمة وواحد للدوال (`dispatch`) — الدوال ثابتة فلا تُعيد رسم مستهلكيها.
- لا تضع كائناً حرفياً كقيمة: `value={{user, setUser}}` ينشئ مرجعاً جديداً كل رسمة ويُبطل كل شيء. استعمل `useMemo`.

## TanStack Query لحالة الخادم

هي الحل الافتراضي لكل ما يأتي من الشبكة. تعطيك مجاناً: تخزين مؤقت، إلغاء تكرار الطلبات، إعادة تحقق في الخلفية، إعادة محاولة، حالة تحميل/خطأ، ومزامنة بين المكوّنات.

```jsx
const { data, isPending, isError, error } = useQuery({
  queryKey: ["orders", { status, page }],
  queryFn: ({ signal }) => fetchOrders({ status, page, signal }),
  staleTime: 60_000,
});
```

مفاهيم لازمة:

| المفهوم | المعنى العملي |
|---|---|
| `queryKey` | هوية البيانات. كل متغيّر يؤثر في النتيجة يدخل فيه، وإلا عُرضت بيانات فلتر آخر |
| `staleTime` | كم تُعتبر البيانات طازجة قبل إعادة التحقق. `0` افتراضاً؛ ارفعها لـ 30–300 ثانية للبيانات شبه الثابتة |
| `gcTime` | كم تبقى في الذاكرة بعد آخر استعمال (5 دقائق افتراضاً) |
| `invalidateQueries` | "هذه البيانات تغيّرت، أعد جلبها" — تُستدعى بعد أي طفرة ناجحة |
| `useMutation` | عمليات الكتابة، مع `onSuccess`/`onError`/`onSettled` |

التحديث المتفائل (optimistic): حدّث الواجهة فوراً قبل رد الخادم، وتراجع عند الفشل. النمط: في `onMutate` ألغِ الاستعلامات الجارية، احفظ اللقطة السابقة، اكتب القيمة الجديدة في الذاكرة المؤقتة، وأعد اللقطة كسياق؛ في `onError` أرجعها؛ في `onSettled` أبطل الاستعلام ليعاد جلب الحقيقة من الخادم.

متى تستحق العناء: إعجاب، تبديل حالة، حذف عنصر من قائمة — تغييرات صغيرة عالية التكرار. لا تستعملها لعمليات مالية أو أي شيء قد يفشل بشكل ذي معنى للمستخدم.

سياق ليبيا/الشبكات الضعيفة: ارفع `staleTime`، فعّل `retry` بتراجع أسّي، وأظهر بيانات مخزّنة مع مؤشّر "يجري التحديث" بدل سبينر يمسح الشاشة.

## Zustand للحالة العامة البسيطة

عندما تحتاج حالة عميل مشتركة بين شاشات (سلة، تفضيلات، حالة درج جانبي) وتريد اشتراكاً انتقائياً بلا إعادة رسم شاملة.

```js
import { create } from "zustand";

export const useCart = create((set, get) => ({
  items: [],
  add: (item) => set(s => ({ items: [...s.items, item] })),
  clear: () => set({ items: [] }),
}));

// اشتراك انتقائي: هذا المكوّن يُعاد رسمه عند تغيّر العدد فقط
const count = useCart(s => s.items.length);
```

- اقرأ **شريحة** لا المخزن كله؛ قراءة الكائن كاملاً تلغي الفائدة.
- لا تضع بيانات خادم في المخزن؛ هذا خطأ الترحيل الأشهر من Redux.
- المتجر الواحد المسطّح أفضل من عشرة متاجر متشابكة؛ قسّم بالشرائح داخل متجر واحد إن كبر.
- Redux Toolkit يبقى خياراً معقولاً لفريق كبير يحتاج أدوات تتبّع صارمة، لكنه زائد لمشروع فردي.

## حالة العنوان كمصدر حقيقة

الفلاتر والبحث والصفحة والترتيب والتبويب المفتوح **يجب** أن تعيش في العنوان.

ما تربحه: الرابط قابل للمشاركة، زر الرجوع يعمل، التحديث لا يفقد السياق، والحالة تتزامن تلقائياً مع مفتاح الاستعلام.

```jsx
const [params, setParams] = useSearchParams();
const status = params.get("status") ?? "all";
const page = Number(params.get("page") ?? 1);

// التغيير يستبدل السجل عند الكتابة السريعة حتى لا يمتلئ التاريخ
setParams(p => { p.set("status", next); p.set("page", "1"); return p; },
          { replace: true });
```

قواعد: أعد ضبط الصفحة إلى 1 عند تغيّر أي فلتر، وأزل المعاملات ذات القيمة الافتراضية من العنوان حتى يبقى نظيفاً، وطبّق `debounce` بـ 300ms لحقل البحث قبل الكتابة في العنوان.

## متى لا تحتاج مكتبة أصلاً

- التطبيق كله شاشات مستقلة تقرأ من الخادم → مكتبة استعلام فقط، بلا أي مخزن عام.
- الحالة المشتركة قيمتان لا تتغيّران كثيراً → سياق واحد.
- كل الحالة داخل شاشة واحدة → `useState` و`useReducer`.

ترتيب التصعيد الصحيح: `useState` → رفع الحالة → `useReducer` → حالة عنوان → مكتبة استعلام لحالة الخادم → مخزن عام صغير. لا تقفز إلى الخطوة الأخيرة أولاً.

## أخطاء شائعة

- نسخ استجابة الخادم إلى `useState` عبر `useEffect` ثم مزامنتها يدوياً في كل شاشة.
- سياق واحد ضخم يحمل كل شيء فتُعاد رسمة التطبيق كله عند أي تغيير.
- `queryKey` ناقص لا يشمل الفلاتر، فتظهر بيانات فلتر سابق.
- تخزين نتائج الفلترة في الحالة بدل حسابها من البيانات + العنوان.
- تحديث متفائل بلا تراجع عند الفشل، فتبقى الواجهة كاذبة.
- وضع الفلاتر في الحالة المحلية فينكسر زر الرجوع ولا يمكن مشاركة الرابط.
- إدخال Redux لمشروع فردي فيه ثلاث شاشات.

## قائمة تحقق

- [ ] صنّفت كل حالة (خادم/عميل/عنوان/نموذج/مشتقّة) قبل اختيار الأداة
- [ ] لا بيانات خادم مخزَّنة في `useState` أو في مخزن عام
- [ ] `queryKey` يشمل كل متغيّر يؤثر في النتيجة
- [ ] `staleTime` مضبوط عمداً لكل استعلام، لا متروك على الافتراضي بلا تفكير
- [ ] كل طفرة تُتبع بـ `invalidateQueries` للمفاتيح المتأثرة
- [ ] التحديث المتفائل له تراجع في `onError` وإبطال في `onSettled`
- [ ] الفلاتر والبحث والصفحة في العنوان، والصفحة تُعاد إلى 1 عند تغيّر فلتر
- [ ] السياق مقتصر على قيم نادرة التغيّر، وقيمته داخل `useMemo`
- [ ] قراءات Zustand بشرائح انتقائية لا بالمخزن كله
- [ ] حالات التحميل والخطأ والفراغ معالَجة صراحة ولا تتداخل
- [ ] لم أضف مكتبة قبل استنفاد `useState` ورفع الحالة و`useReducer`
