# كتابة مواصفة قابلة للتنفيذ

المواصفة ليست وثيقة تسويقية ولا وصفاً للأحلام. هي **عقد قابل للاختبار** يحدّد ما سيُبنى، وما لن يُبنى، وكيف نعرف أنه اكتمل.

معيار الجودة الوحيد: **هل يستطيع منفّذ لم يحضر أي نقاش أن يبني منها بلا سؤالك؟** إن احتاج سؤالاً، المواصفة ناقصة في تلك النقطة تحديداً.

## المواصفة مقابل الوثيقة التسويقية

| المواصفة | الوثيقة التسويقية |
|---|---|
| «عند الضغط على حفظ والحقل فارغ، يظهر خطأ تحت الحقل ولا يُرسل الطلب» | «تجربة سلسة وخالية من الأخطاء» |
| «الحد الأقصى 500 حرف، والزائد يُمنع بالإدخال لا بالرسالة» | «مساحة كافية للكتابة» |
| «المزامنة كل 15 دقيقة أو عند فتح التطبيق، أيهما أسبق» | «تحديث فوري ومستمر» |
| أرقام، حدود، شروط، وحالات فشل | صفات وأفعال تفضيل |

أي جملة في المواصفة لا يمكن تحويلها إلى اختبار «صح/خطأ» → أعد كتابتها أو احذفها.

## هيكل المواصفة

الترتيب مقصود: المشكلة أولاً، المقاييس أخيراً، والنطاق مبكّراً حتى يُقرأ قبل التفاصيل.

1. **المشكلة** — جملة واحدة بلا ذكر الحل.
2. **المستخدم** — شريحة محددة، وحالته التقنية (جهاز، شبكة، لغة).
3. **النتيجة المرجوة** — ما يتغيّر في حياة المستخدم وفي أرقامك.
4. **النطاق / خارج النطاق** — قائمتان صريحتان.
5. **رحلات المستخدم** — المسار السعيد، ثم المسارات البديلة.
6. **قواعد العمل** — الأرقام والشروط والصلاحيات.
7. **نموذج البيانات المنطقي** — الكيانات والحقول والقيود (لا SQL).
8. **الحالات الحدّية والفشل** — جدول.
9. **معايير القبول** — لكل رحلة.
10. **المقاييس** — كيف نعرف أنها نجحت بعد الإطلاق.
11. **الافتراضات والأسئلة المفتوحة** — كل مجهول مكتوب صراحة.

الطول المستهدف لميزة متوسطة: **صفحة إلى ثلاث صفحات**. المواصفة الأطول من ذلك لميزة واحدة عادة تخفي نطاقاً متضخماً.

## كتابة معايير قبول قابلة للاختبار

الصيغة الثابتة:

```
Given  [حالة أولية محددة]
When   [فعل واحد من المستخدم]
Then   [نتيجة واحدة يمكن مشاهدتها]
```

قواعد:
- فعل واحد ونتيجة واحدة لكل معيار. المعيار الذي فيه «و» مرتين → قسّمه.
- لا تستخدم: «بشكل صحيح»، «بسرعة»، «بسهولة»، «مناسب». استبدلها بأرقام.
- كل معيار يذكر ما يراه المستخدم على الشاشة، لا ما يحدث داخلياً.
- لكل مسار سعيد ≥ معياران للفشل.

أمثلة:

```
Given  المستخدم مسجّل الدخول ولديه 0 عمليات اليوم
When   يفتح الشاشة الرئيسية
Then   يرى نصاً «لا توجد عمليات اليوم» وزر «إضافة عملية» فقط

Given  حقل المبلغ فارغ
When   يضغط «حفظ»
Then   يظهر «أدخل المبلغ» تحت الحقل، ولا يُغلق النموذج، ولا يُرسل طلب شبكة

Given  لا يوجد اتصال بالإنترنت
When   يحفظ عملية
Then   تُحفظ محلياً، وتظهر أيقونة «بانتظار المزامنة» بجانبها، ويبقى المجموع صحيحاً

Given  المبلغ المُدخل 0 أو سالب
When   يضغط «حفظ»
Then   يُرفض الإدخال مع رسالة «المبلغ يجب أن يكون أكبر من صفر»
```

معايير الأداء والقياس تُكتب برقم:

```
Then   تظهر النتائج خلال ≤ 400ms على شبكة 3G محاكاة، وقبلها هيكل عظمي لا دوّامة تحميل
```

## تغطية الحالات الحدّية والفشل

كل شاشة تُوثَّق بأربع حالات إجبارية: **تحميل، فارغ، خطأ، نجاح**. المواصفة التي تصف حالة النجاح فقط تُنتج تطبيقاً ينهار عند أول مشكلة.

جدول الحالات الحدّية — املأه لكل ميزة:

| الحالة | السلوك المطلوب |
|---|---|
| لا يوجد اتصال | حفظ محلي + وسم «بانتظار المزامنة» + إعادة محاولة تلقائية عند عودة الاتصال |
| اتصال بطيء (> 5 ثوانٍ) | هيكل عظمي، ثم زر «إعادة المحاولة» بعد 15 ثانية |
| خطأ من الخادم (5xx) | رسالة عربية واضحة + إعادة محاولة + عدم فقدان ما كتبه المستخدم |
| انتهاء الجلسة | إعادة توثيق صامتة إن أمكن، وإلا شاشة دخول مع العودة لنفس المكان بعدها |
| قائمة فارغة | نص يشرح + فعل واحد |
| قائمة كبيرة (> 1000 عنصر) | ترقيم/تحميل تدريجي بـ20–50 عنصراً، لا جلب كامل |
| نص طويل جداً | حد أقصى معلن بالحروف + قصّ بصري بثلاث نقاط |
| نص عربي + أرقام + إنجليزي مختلط | اتجاه صحيح RTL، والأرقام لاتينية |
| ضغط مزدوج على زر الإرسال | منع الإرسال المكرر (تعطيل الزر أثناء التنفيذ) |
| إغلاق التطبيق أثناء الإدخال | حفظ المسوّدة واستعادتها |
| صلاحيات: مستخدم يطلب بيانات غيره | يُرفض على مستوى قاعدة البيانات لا الواجهة فقط |
| قيمة صفر أو سالبة أو كسرية، وتاريخ خارج المدى | حدود وسلوك معلن لكل حالة |

الخطأ الأكثر شيوعاً هنا: كتابة المسار السعيد فقط، فيُترك قرار سلوك الفشل للمنفّذ في لحظة التنفيذ، فيختلف من شاشة لأخرى.

## مواصفة تصلح لتسليمها لكلود كود مباشرة

المواصفة الموجهة للتنفيذ تحتاج بنوداً إضافية:

- **حدود التغيير**: أي ملفات/وحدات يُسمح بلمسها، وما لا يُمس.
- **ما هو موجود مسبقاً**: أسماء الجداول والشاشات القائمة، حتى لا يُعاد بناؤها.
- **نموذج البيانات المنطقي**: اسم الكيان، الحقول، الأنواع، الإلزامي، القيود.
- **رسائل الواجهة النهائية بالعربية حرفياً** — لا تترك الصياغة للتخمين.
- **تعريف الانتهاء**: ماذا يعني «تم» (يبني، يمر الاختبار اليدوي، لا تحذيرات جديدة).
- **الأسئلة المفتوحة**: مكتوبة صراحة مع القرار الافتراضي إن لم يُجَب عنها.

مثال لنموذج بيانات منطقي داخل المواصفة (بلا SQL):

```yaml
Sale:
  id: uuid
  user_id: uuid            # إلزامي، مالك السجل
  amount: decimal(10,2)    # إلزامي، > 0
  note: text               # اختياري، ≤ 200 حرف
  created_at: timestamptz  # افتراضي: الآن
  synced: bool             # افتراضي false على الجهاز
  قيود:
    - المستخدم يقرأ ويكتب سجلاته فقط
    - الحذف ناعم (deleted_at) لا فعلي
    - فهرس على (user_id, created_at)
```

> بناء الجداول والسياسات فعلياً: افتح مهارة data-schema-design.

## قالب كامل جاهز للنسخ

```markdown
# [اسم الميزة]
## 1. المشكلة — [جملة واحدة، بلا ذكر الحل]
## 2. المستخدم — الشريحة: [محددة] | السياق: [أندرويد متوسط، 3G متقطع، عربي RTL، أرقام لاتينية]
## 3. النتيجة المرجوة — للمستخدم: [ما يتغيّر عنده] | للمنتج: [الرقم الذي يتحرك]
## 4. النطاق
داخل: - [بند]
خارج (لن يُنفَّذ في هذا الإصدار): - [بند]
## 5. رحلات المستخدم
المسار السعيد: 1. [خطوة] → [ما يراه]
المسارات البديلة: - [شرط] → [مسار]
## 6. قواعد العمل — [قاعدة برقم أو شرط]
## 7. نموذج البيانات المنطقي — [كيان: حقول، أنواع، إلزامي، قيود، صلاحيات]
## 8. الحالات الحدّية والفشل — جدول [الحالة | السلوك المطلوب]
## 9. نصوص الواجهة النهائية — جدول [الموضع | النص العربي]
## 10. معايير القبول — [ ] Given … When … Then …
## 11. المقاييس — المقياس الأساسي [اسم + قيمة حالية + هدف + مدة] | الأحداث المتتبَّعة
## 12. الافتراضات والأسئلة المفتوحة — سؤال + القرار الافتراضي إن لم يُجَب
## 13. حدود التغيير — يُلمس: [...] | لا يُمس: [...]
## 14. تعريف الانتهاء
- [ ] يبني بلا أخطاء ولا تحذيرات جديدة
- [ ] كل معايير القبول تمرّ يدوياً على جهاز حقيقي
- [ ] الحالات الأربع مغطّاة في كل شاشة جديدة
```

## أخطاء شائعة

- كتابة الحل قبل المشكلة، فتُقفل الخيارات قبل فهمها.
- ترك «خارج النطاق» فارغاً — هذا الحقل هو الذي يمنع التضخّم فعلياً.
- معايير قبول بصيغة «يعمل بشكل صحيح» بلا شرط ولا نتيجة قابلة للمشاهدة.
- وصف الشاشات بدل وصف السلوك، فتصير المواصفة رسماً لا عقداً.
- ترك نصوص الواجهة للتخمين، فتظهر رسائل إنجليزية أو ترجمة حرفية ركيكة.
- تجاهل الصلاحيات وافتراض أن إخفاء زر في الواجهة = حماية.
- عدم كتابة الأسئلة المفتوحة، فتُتخذ قرارات صامتة أثناء التنفيذ لا يعلم بها أحد.
- مواصفة من عشر صفحات لميزة من ثلاثة أيام.
- عدم تحديث المواصفة بعد قرار تغيير، فتصبح مضلّلة وأسوأ من غيابها.
- إهمال حالة النص العربي الطويل: الترجمة العربية قد تطول 20–30% أو تقصر، والتصميم الذي يفترض طول الإنجليزية ينكسر.

## قائمة تحقق

- [ ] المشكلة مكتوبة بجملة واحدة بلا ذكر الحل
- [ ] «خارج النطاق» مكتوب صراحة وليس فارغاً
- [ ] المسار السعيد مرقّم خطوة خطوة، ولكل خطوة ما يراه المستخدم
- [ ] كل معيار قبول بصيغة Given/When/Then بفعل واحد ونتيجة واحدة
- [ ] لا صفة مطاطة في المواصفة، وكل حد له رقم
- [ ] جدول الحالات الحدّية مملوء: شبكة، خطأ خادم، جلسة، فارغ، كبير، إدخال غير صالح
- [ ] الحالات الأربع (تحميل/فارغ/خطأ/نجاح) محددة لكل شاشة
- [ ] نصوص الواجهة العربية مكتوبة نهائية داخل المواصفة
- [ ] نموذج البيانات المنطقي فيه الحقول والقيود والصلاحيات
- [ ] المقياس الأساسي محدد مع قيمته الحالية وهدفه ومدة القياس
- [ ] الافتراضات والأسئلة المفتوحة مكتوبة مع قرار افتراضي لكل سؤال
- [ ] حدود التغيير وتعريف الانتهاء مذكوران قبل التسليم للتنفيذ
