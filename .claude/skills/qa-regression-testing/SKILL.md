# اختبار الانحدار

الانحدار هو أن يتوقّف عن العمل شيء **كان يعمل**، بسبب تعديل في مكان آخر. وهو أخطر أنواع الأعطال لأربعة أسباب: لا أحد يبحث عنه (الانتباه كله على الميزة الجديدة)، ويصيب مسارات مستقرة يستعملها كل المستخدمين، ويصل للإنتاج غالباً لأن الفحص اليدوي يتركّز على المتغيّر، ويُفقد ثقة المستخدم أسرع من أي عطل آخر — ميزة جديدة معطوبة مقبولة، أما تسجيل دخول توقّف فيعني تطبيقاً غير موثوق.

القاعدة المركزية: **كل تعديل يُفترَض فيه أنه كسر شيئاً حتى يُثبَت العكس بتشغيل.**

## حزمة الانحدار: ما هي وكيف تُبنى

حزمة الانحدار = مجموعة الحالات التي تتحقّق من أن **الوظائف القائمة** ما زالت تعمل. لا تختبر الجديد، بل تحمي القديم.

بذرتها الأولى (اكتبها في يوم واحد ولا تنتظر الكمال):

| الفئة | ما يدخل | العدد المبدئي |
|---|---|---|
| مسارات حرجة | تسجيل، دخول، خروج، بقاء الجلسة، الدفع، إنشاء/تعديل/حذف العنصر الرئيسي | 10–15 حالة |
| تكاملات | استدعاء الخادم الأساسي، رفع ملف، إشعار | 3–5 |
| بيانات دائمة | إعادة فتح التطبيق والبيانات موجودة كما هي | 2–3 |
| صلاحيات | مستخدم لا يصل لبيانات غيره | 2–3 |

ثم تنمو بقاعدة واحدة غير قابلة للتفاوض: **كل عطل يُصلَح يضيف حالة اختبار دائمة**. الحالة تُكتب قبل الإصلاح (تفشل)، ثم يُصلَح الكود (تنجح). هذه الحالة تحمل رقم العطل في وسمها وتبقى في الحزمة إلى الأبد.

لماذا هذه القاعدة تحديداً: العطل الذي حدث مرة يدلّ على منطقة هشّة في التصميم، واحتمال عودته أعلى من احتمال ظهور عطل عشوائي جديد في مكان سليم. الحزمة المبنية بهذه الطريقة تتشكّل تلقائياً حول نقاط ضعف مشروعك الحقيقية لا المتخيّلة.

ضبط النموّ: راجع الحزمة كل 3 أشهر. احذف فقط حالات لميزة **حُذفت من المنتج**. لا تحذف حالة لأنها "لم تفشل منذ زمن" — هذا بالضبط دليل نجاحها.

## ما الذي يُعاد اختباره بعد أي تعديل

ثلاث دوائر، بهذا الترتيب:

1. **الميزة المعدّلة نفسها** — حالاتها كلها.
2. **كل ما يشاركها**: البيانات (نفس الجدول/النموذج)، الحالة (نفس المتحكّم/المزوّد)، التنقّل (شاشة قبلها أو بعدها)، المكوّن المشترك (نفس الودجت/الدالة المساعدة)، والصلاحيات (نفس السياسة).
3. **مسار الدخان**: 5–8 حالات تغطّي أهم مسار في التطبيق، تُشغَّل بعد أي تعديل مهما بدا صغيراً.

المشاركات الأربع بالترتيب من الأخطر: **البيانات، ثم الصلاحيات، ثم الحالة المشتركة، ثم التنقّل**. تعديل في عمود قاعدة بيانات يمسّ كل شاشة تقرأه، وأغلبها لن يخطر ببالك.

## بناء خريطة الأثر

ملف واحد في المستودع `qa/impact-map.md` يربط الوحدة البرمجية بالميزات المتأثّرة. يُحدَّث عند إضافة أي ميزة.

```markdown
| الوحدة / الملف | يمسّها التعديل في | يجب إعادة اختبار |
|---|---|---|
| auth_service.dart | الدخول، التسجيل، الاستعادة، الخروج | TC-AUTH-*، TC-SESS-002 |
| جدول profiles + سياسات RLS | الملف الشخصي، قائمة الطلبات، لوحة الإدارة | TC-PROF-*، TC-ORD-003، TC-PERM-* |
| app_router.dart | كل التنقّل والروابط العميقة | حزمة الدخان كاملة |
| money_format.dart | السلّة، الفاتورة، سجل الطلبات، الإشعارات | TC-PAY-*، TC-ORD-007 |
| api_client.dart (اعتراضات/إعادة محاولة) | كل شاشة تجلب بيانات | حزمة الدخان + TC-NET-* |
```

كيف تستعملها من الجوال عملياً: اطّلع على قائمة الملفات المتغيّرة في الـPR (`git diff --name-only origin/main...HEAD` أو صفحة Files changed)، وقابِلها بأعمدة الخريطة، ونفّذ اتحاد الحالات الناتج. هذا تحويل قرار "بماذا أشعر أنه تأثّر" إلى إجراء ميكانيكي.

إشارات تستدعي **الحزمة كاملة** لا جزءاً منها: تعديل في المصادقة، أو في المسيّر، أو في العميل الشبكي، أو ترقية Flutter/حزمة أساسية، أو هجرة قاعدة بيانات، أو تغيير في السياسات.

## مثال ملموس: تعديل شاشة الدخول

التعديل: إضافة زر "إظهار كلمة المرور" وتغيير رسالة الخطأ.

يبدو معزولاً تماماً. ما يجب إعادة اختباره فعلياً:

| ما يُعاد اختباره | لماذا | الحكم المطلوب |
|---|---|---|
| الدخول بحساب صحيح | المسار الأساسي المعدَّل | يمرّ |
| الدخول بكلمة مرور خاطئة | الرسالة تغيّرت | نص الرسالة الجديد يظهر ولا يبقى القديم |
| التسجيل | غالباً يشارك نفس نموذج/تحقّق كلمة المرور | يمرّ بلا تغيّر في سلوكه |
| استعادة كلمة المرور | تشارك `auth_service` ومسار التنقّل | الرابط يصل والدخول بعده ينجح |
| الدخول الاجتماعي (Google/Apple) | يشارك شاشة الدخول ومسار ما بعد النجاح | يصل لنفس الشاشة الرئيسية |
| بقاء الجلسة بعد إغلاق التطبيق | يشارك تخزين الرمز | يبقى داخلاً |
| تسجيل الخروج ثم الدخول مجدداً | يشارك تنظيف الحالة | لا بيانات المستخدم السابق |
| مدير كلمات المرور / الملء التلقائي | تغيير حقل كلمة المرور يكسره كثيراً | يملأ الحقلين صحيحاً |
| RTL وحجم خط أكبر على شاشة الدخول | زر جديد داخل الحقل | لا تداخل ولا قصّ ولا أيقونة على الجهة الخاطئة |
| قارئ الشاشة على الزر الجديد | عنصر تفاعلي جديد | له تسمية منطوقة |

عشر إعادات اختبار لتعديل بسطرين. هذا هو حجم الانحدار الحقيقي، وهذا سبب وجود الحزمة الآلية: تنفيذ هذه القائمة يدوياً بعد كل تعديل صغير مستحيل عملياً.

## الآلي مقابل اليدوي

| ينتمي للحزمة الآلية | يبقى يدوياً |
|---|---|
| منطق الحساب والتحقّق والتحويل | التقييم البصري وRTL والتخطيط |
| مسارات API والاستجابات المتوقّعة | إحساس التنقّل وسلاسة الحركة |
| قواعد الصلاحيات (اختبار على مستوى الخادم) | التكامل مع بوّابات الدفع الحقيقية |
| مسارات الدخان الأساسية عبر E2E | حوارات النظام والأذونات على أجهزة حقيقية |
| كل حالة مشتقّة من عطل قابلة للأتمتة | ما تتغيّر واجهته كل أسبوع (أتمتته هدر) |

هدف واقعي: **70% من حزمة الانحدار آلية**، والباقي قائمة يدوية مكتوبة تُنفَّذ قبل الإصدار في أقل من 45 دقيقة. القائمة اليدوية غير المكتوبة تُنفَّذ بشكل مختلف كل مرة، فلا تكشف الانحدار.

## متى تُشغَّل

| المناسبة | ما يُشغَّل |
|---|---|
| بعد كل تعديل محلي | حالات الميزة المعدَّلة فقط |
| عند كل PR | الحزمة الآلية السريعة (وحدة + widget) + حزمة الدخان |
| ليلياً | حزمة الانحدار الآلية كاملة + E2E |
| قبل كل إصدار | الحزمة كاملة آلية + القائمة اليدوية كاملة |
| بعد إصلاح عاجل في الإنتاج | حالة العطل الجديدة + حزمة الدخان + حالات دائرة الأثر |
| بعد ترقية Flutter أو حزمة أساسية | الحزمة كاملة بلا استثناء، وعلى إصدارَي نظام مختلفين |

الإصلاح العاجل هو أخطر لحظة للانحدار: يُكتب تحت ضغط، ويُدمج بلا مراجعة، ويُنشر مباشرة. **لا يُنشر إصلاح عاجل بلا حزمة دخان.**

## توثيق ما انكسر ولماذا

لكل انحدار مكتشَف، سجّل صفاً في `qa/regression-log.md`:

| الحقل | مثال |
|---|---|
| رقم العطل | BUG-2026-057 |
| ما انكسر | استعادة كلمة المرور: الرابط يفتح شاشة فارغة |
| التعديل المسبّب | PR #214 — إعادة تنظيم المسيّر |
| كيف اكتُشف | حزمة انحدار ليلية / بلاغ مستخدم / جولة يدوية |
| لماذا لم تكتشفه الحزمة | لا حالة تغطّي الروابط العميقة بعد الخروج |
| الحالة المضافة | TC-AUTH-021 (وسم `regression`) |
| الوقاية | إضافة الروابط العميقة لخريطة الأثر تحت `app_router.dart` |

الحقل الحاسم هو **"لماذا لم تكتشفه الحزمة"**. الانحدار الذي وصل للإنتاج يكشف ثغرتين: في الكود وفي الحزمة. إصلاح الأول فقط يضمن التكرار. اقرأ هذا السجل كل ثلاثة أشهر — تكرار نفس الوحدة في عمود "التعديل المسبّب" يعني أن المشكلة معماريّة وأن الحل إعادة تصميم لا مزيد من الاختبارات.

## أخطاء شائعة

- اختبار الميزة الجديدة فقط والافتراض بأن الباقي بخير.
- إصلاح عطل بلا إضافة حالة تمنع عودته — العطل نفسه يعود بعد أشهر.
- حزمة انحدار طويلة بطيئة يدوية تماماً، فتُختصر تحت الضغط ثم تُلغى.
- حذف حالات "لم تفشل منذ زمن".
- تجاهل خريطة الأثر لأن التعديل "صغير جداً" — أخطر الانحدارات تأتي من تعديلات بسطر واحد في كود مشترك.
- عدم إعادة الاختبار بعد ترقية الحزم، وهي من أكبر مصادر الانحدار الصامت.

## قائمة تحقق

- [ ] حزمة انحدار موجودة تغطّي المسارات الحرجة والتكاملات والبيانات الدائمة والصلاحيات
- [ ] كل عطل مُصلَح أضاف حالة دائمة موسومة برقمه، تُكتب قبل الإصلاح وتفشل أولاً
- [ ] لا حالة تُحذف إلا بحذف الميزة نفسها من المنتج
- [ ] `qa/impact-map.md` موجود ويُحدَّث مع كل ميزة جديدة
- [ ] بعد كل تعديل تُنفَّذ الدوائر الثلاث: الميزة، ما يشاركها، حزمة الدخان
- [ ] قائمة الملفات المتغيّرة تُقابَل بخريطة الأثر لتحديد الحالات آلياً لا بالحدس
- [ ] تعديل المصادقة أو المسيّر أو العميل الشبكي أو الهجرات يستدعي الحزمة كاملة
- [ ] 70% على الأقل من حزمة الانحدار مؤتمتة
- [ ] القائمة اليدوية مكتوبة وتُنفَّذ في أقل من 45 دقيقة قبل كل إصدار
- [ ] الحزمة الآلية تعمل ليلياً وقبل كل إصدار
- [ ] لا إصلاح عاجل يُنشر بلا حزمة دخان
- [ ] إعادة اختبار كاملة بعد ترقية Flutter أو أي حزمة أساسية
- [ ] `qa/regression-log.md` يسجّل لكل انحدار سببه وسبب عدم اكتشافه والحالة المضافة
- [ ] مراجعة السجل كل 3 أشهر لكشف الوحدات المتكرّرة
