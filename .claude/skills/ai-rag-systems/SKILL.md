# أنظمة الاسترجاع المعزّز (RAG)

RAG ليس ميزة بل خط أنابيب بحث تُغذّى نتائجه لنموذج. **جودة النظام كلها تتحدد في خطوة الاسترجاع؛ النموذج لا يصلح استرجاعاً سيئاً.** أغلب "أخطاء الهلوسة" في أنظمة RAG هي في الحقيقة قطع خاطئة وصلت للنموذج.

## متى تحتاج RAG أصلاً

| الحالة | الحل الصحيح |
|---|---|
| المعرفة كلها تحت 30–50 ألف رمز وثابتة | ضعها في المطالبة مباشرة. لا RAG. |
| المستخدم يبحث عن مستند بعينه بكلمة يعرفها | بحث نصي كامل عادي (`tsvector`) — أسرع وأرخص وأدق |
| ترشيح ببيانات وصفية (التاريخ، الفئة، المؤلف) | `where` في SQL، لا تضمين |
| مئات إلى ملايين الفقرات، والسؤال بصيغة حرة لا تطابق ألفاظ المصدر | RAG |
| المحتوى يتغيّر ويجب أن يظهر التغيير فوراً | RAG مع إعادة استيعاب تزايدية |

الخطأ الأكثر شيوعاً: بناء RAG لعشرين صفحة PDF. تكلفة البنية والصيانة والتقييم أضعاف الفائدة، ومطالبة واحدة تحتوي المستند كله ستتفوق عليه دقةً. القاعدة: **لا تبدأ RAG قبل أن تعجز المطالبة الطويلة فعلاً**.

## خط الأنابيب

```
استيعاب → تنظيف وتطبيع → تقطيع → تضمين → فهرسة
                                              ↓
سؤال → تطبيع → [تضمين + بحث كلمات] → دمج → إعادة ترتيب → بناء السياق → توليد مع استشهاد
```

كل مرحلة تُقاس منفصلة. الفشل الشائع أن تُقاس النتيجة النهائية فقط فلا تعرف أين انكسرت.

## التقطيع

| نوع المحتوى | حجم القطعة | التداخل |
|---|---|---|
| مقالات ووثائق نثرية | 400–600 رمز | 10–15% |
| توثيق تقني ومقالات مساعدة | 300–500 رمز | 10% |
| نصوص قانونية/سياسات (بنود مستقلة) | البند كاملاً مهما كان طوله | 0 |
| أسئلة شائعة | السؤال + جوابه = قطعة واحدة | 0 |
| جداول | الجدول كاملاً + عنوانه، لا يُقطع أبداً | — |
| نصوص محادثات | 5–10 أدوار مع اسم المتحدث | دور واحد |

القواعد الحاكمة:
- **اقطع على حدود دلالية أولاً** (عنوان `##`، فقرة، بند مرقّم) ثم طبّق حد الحجم داخلها. التقطيع الأعمى كل 500 رمز يشطر الجملة الحاسمة نصفين.
- **كل قطعة تحمل سياقها**: أضف في أعلى نص القطعة عنوان المستند وسلسلة العناوين (`دليل الاسترجاع > الاسترجاع خلال 14 يوماً`). القطعة المعزولة "المدة 14 يوماً" لا معنى لها ولن تُسترجع ولن تُفهم.
- **التداخل يمنع القطع في منتصف المعلومة**، وليس بديلاً عن حدود دلالية. تداخل فوق 25% يعني تكراراً في النتائج وتضخّم الفهرس بلا مقابل.
- خزّن مع كل قطعة: `doc_id`, `chunk_index`, `heading_path`, `source_url`, `updated_at` — بدونها لا استشهاد ولا إعادة استيعاب تزايدية. وقطعة أقل من 50 رمزاً ضجيج، ادمجها بجارتها.

الخطأ الشائع: قطعة عملاقة (2000+ رمز). تضمينها يصير متوسطاً باهتاً لعدة مواضيع فلا يقترب من أي سؤال محدّد، ويستهلك سياقاً هائلاً عند التوليد.

## اختيار نموذج التضمين

معايير القرار بالترتيب: **دعم العربية فعلياً** ← البعد ← التكلفة ← الاستضافة.

- نماذج التضمين متعددة اللغات إلزامية للمحتوى العربي. نموذج مدرَّب على الإنجليزية أساساً يعطي نتائج تبدو تعمل ثم تفشل على المرادفات والصيغ الصرفية.
- الأبعاد الشائعة 768 و1024 و1536 و3072. البعد الأكبر ليس أفضل تلقائياً: 3072 يعني ضعف حجم الفهرس وذاكرته مقابل تحسّن هامشي عادة. **ابدأ بـ1024–1536.** بعض النماذج تسمح بتقليص البعد عند التوليد — استغلّه إن كان الفهرس كبيراً.
- خذ نموذجاً يدعم فهرسة غير متماثلة (تضمين مختلف للسؤال وللمستند) إن توفّر؛ يحسّن الاسترجاع بلا تكلفة إضافية.
- **لا تغيّر نموذج التضمين دون إعادة توليد كل التضمينات.** خلط نموذجين في فهرس واحد يعطي نتائج عشوائية، وهذا خطأ صامت لا يظهر كخطأ برمجي. وطبّع المتجه إلى طول 1 عند استعمال تشابه الجيب تمام (كثير من المزوّدين يفعلها أصلاً — تحقق مرة واحدة).

## pgvector والفهرسة

```sql
create extension if not exists vector;

create table chunks (
  id bigserial primary key,
  doc_id uuid not null references documents(id) on delete cascade,
  chunk_index int not null,
  heading_path text,
  content text not null,
  content_norm text not null,              -- نص مطبّع للبحث اللفظي
  embedding vector(1024),
  fts tsvector generated always as (to_tsvector('simple', content_norm)) stored,
  updated_at timestamptz not null default now(),
  unique (doc_id, chunk_index)
);

create index chunks_hnsw on chunks
  using hnsw (embedding vector_cosine_ops) with (m = 16, ef_construction = 64);
create index chunks_fts on chunks using gin (fts);
create index chunks_doc on chunks (doc_id);
```

المسافة تُطابق نوع الفهرس: `vector_cosine_ops` مع المعامل `<=>`، `vector_l2_ops` مع `<->`، `vector_ip_ops` مع `<#>`. **استعمال معامل لا يطابق فئة الفهرس يتجاهل الفهرس بصمت** ويمسح الجدول كاملاً — أشيع خطأ أداء هنا؛ تحقق بـ`explain` أنك ترى `Index Scan`.

| | HNSW | IVFFlat |
|---|---|---|
| الاستدعاء عند نفس السرعة | أعلى | أقل |
| زمن البناء | أبطأ | أسرع بكثير |
| حجم الفهرس/الذاكرة | أكبر | أصغر |
| يحتاج بيانات قبل البناء | لا | نعم — لا تبنه على جدول فارغ |
| الإدراج التزايدي | جيد | يتدهور، يحتاج إعادة بناء دورية |
| المعاملات | `m`, `ef_construction` + `hnsw.ef_search` | `lists` + `ivfflat.probes` |

**القرار الافتراضي: HNSW**، إلا إذا كانت الذاكرة أو زمن البناء قيداً حقيقياً.

معاملات عملية: `m = 16` يكفي حتى ملايين الصفوف (ارفعه إلى 24–32 لأبعاد عالية أو استدعاء غير كافٍ)، `ef_construction = 64` افتراضياً و128 لجودة أعلى بزمن بناء أطول. عند الاستعلام `set hnsw.ef_search = 40;` (الافتراضي) وارفعه إلى 100–200 لتحسين الاستدعاء بثمن زمن — يجب أن يكون **أكبر من عدد النتائج المطلوبة** دائماً. ولـIVFFlat: `lists ≈ عدد_الصفوف / 1000` حتى المليون وفوقه `≈ sqrt(عدد_الصفوف)`، و`probes ≈ sqrt(lists)` نقطة بداية وزيادته ترفع الدقة وتُبطئ.

ملاحظات تشغيلية: ابنِ الفهرس بعد تحميل الدفعة الأولى لا قبلها، وارفع `maintenance_work_mem` أثناء البناء، وحدود الفهرسة في pgvector تقف عند 2000 بُعد لنوع `vector` — إن تجاوزته استعمل `halfvec` أو قلّص البعد.

> عمق Postgres والفهارس عموماً: مهارة data-postgres-advanced.

## البحث الهجين

البحث الدلالي وحده يفشل على: أسماء المنتجات، أكواد الأخطاء، الأرقام، الأسماء العلَمية، والمصطلحات النادرة — لأن التضمين يقرّب المعنى ويطمس اللفظ الدقيق. والبحث اللفظي وحده يفشل على إعادة الصياغة والمرادفات. الهجين يتفوّق لأن أخطاء الطريقتين **غير مترابطة**.

الدمج بـReciprocal Rank Fusion: كل نتيجة تأخذ `1/(k + rank)` من كل قائمة وتُجمع، بـ`k = 60`. ميزته أنه يعمل على **الرتب** لا الدرجات، فلا يحتاج معايرة بين مقياسين مختلفي المقياس — وهذا سبب تفوّقه على الجمع الموزون الذي يتطلب ضبط وزن يتغير مع كل تعديل.

```sql
with semantic as (
  select id, row_number() over (order by embedding <=> $1) as rank
  from chunks where doc_id = any($3) order by embedding <=> $1 limit 50
),
lexical as (
  select id, row_number() over (order by ts_rank_cd(fts, q) desc) as rank
  from chunks, websearch_to_tsquery('simple', $2) q
  where fts @@ q limit 50
)
select c.id, c.content, c.heading_path, c.source_url,
       coalesce(1.0/(60 + s.rank), 0) + coalesce(1.0/(60 + l.rank), 0) as score
from chunks c
left join semantic s on s.id = c.id
left join lexical l on l.id = c.id
where s.id is not null or l.id is not null
order by score desc limit 20;
```

اسحب 40–60 مرشحاً من كل جانب لا 10؛ إعادة الترتيب لاحقاً تحتاج مادة تعمل عليها. وطبّق ترشيح الصلاحيات (`user_id`, `org_id`) **داخل** الاستعلام لا بعده — الترشيح بعد الاسترجاع يعني أن مستخدماً قد يرى صفراً من النتائج بينما توجد نتائج مسموحة له خارج الـ20 الأولى، وهو أيضاً تسريب محتمل عبر الدرجات. وللعربية استعمل `'simple'` مع عمود مطبّع مسبقاً بدل مجذّع عربي مدمج (التطبيع الذي تتحكم به أدق وأثبت)، وأضف فهرس trigram (`pg_trgm`) لمطابقة الأسماء والأخطاء الإملائية.

## إعادة الترتيب

نموذج إعادة ترتيب (cross-encoder) يقرأ **السؤال والقطعة معاً** فيحكم بدقة أعلى بكثير من تشابه متجهين مستقلين. عملياً هو أرخص تحسين للجودة في RAG بعد التقطيع الجيد.

الشكل: 40–60 مرشحاً من الهجين ← إعادة ترتيب ← أفضل 4–8 إلى النموذج. المكسب النموذجي في الدقة عند k صغير كبير ومحسوس؛ التكلفة زمن إضافي 100–400ms ومقابل مادي أقل بكثير من توسيع السياق.

بديل أرخص إن لم يتوفر: أعطِ نموذجاً صغيراً القطع العشر ودعه يختار المفيد منها قبل التوليد — أضعف من cross-encoder لكنه أفضل من إرسال العشرين خاماً. وفي كل الأحوال لا ترسل أكثر من 8–10 قطع للنموذج: الحشو يخفض الدقة (الوسط يُهمَل) ويرفع التكلفة والزمن معاً.

## الاستشهاد والرفض

في المطالبة، بصرامة:

```
أجب فقط مما ورد داخل <context>. لكل جملة تحمل معلومة، أضف [n] برقم القطعة.
إن لم توجد إجابة في السياق، أرجع: {"answer": null, "reason": "no_context"} ولا تستنتج.
```

كل قطعة تُرقَّم في السياق وتُرسل مع `heading_path` و`source_url`، وتُعرض للمستخدم كرابط. الاستشهاد ليس تزييناً: هو الوسيلة الوحيدة ليتحقق المستخدم، وهو ما يجعل الخطأ مكتشفاً بدل أن يكون مقنعاً. والرفض يجب أن يكون **مساراً مدعوماً في الواجهة** بنص مفيد واقتراح بحث أو تواصل؛ ونسبته مقياس تراقبه: صفر يعني أن النموذج يخترع، وفوق 30% يعني أن استرجاعك أو محتواك ناقص.

عتبة تشابه دنيا: إن كانت أعلى نتيجة أبعد من عتبة معايَرة على بياناتك، اعتبرها "لا سياق" ولا تستدعِ النموذج أصلاً. لا تنسخ رقم عتبة من مقال — عايره بنفسك على 50 سؤالاً معلوماً.

## تقييم الاسترجاع

قيّم الاسترجاع منفصلاً عن التوليد، وإلا خلطت السببين.

1. ابنِ 50–100 سؤالاً حقيقياً، لكل سؤال معرّفات القطع الصحيحة.
2. قِس **recall@k** (هل وصلت القطعة الصحيحة ضمن k؟ الأهم عندك) و**MRR** (رتبة أول نتيجة صحيحة) ونسبة الأسئلة بلا نتيجة صحيحة إطلاقاً. أهداف البدء: `recall@20 ≥ 0.90` قبل إعادة الترتيب و`recall@5 ≥ 0.85` بعدها.
3. كل تغيير (حجم القطعة، نموذج التضمين، `ef_search`، أوزان الدمج) يُقاس على نفس المجموعة.

recall@20 منخفض = مشكلة تقطيع أو تضمين. recall@20 عالٍ مع recall@5 منخفض = مشكلة ترتيب، والحل إعادة الترتيب لا تغيير نموذج التضمين.

> منهجية مجموعات الاختبار والحَكَم النموذجي: مهارة ai-evaluation.

## خصوصية المحتوى العربي

- **طبّع قبل التضمين وقبل الفهرسة اللفظية، وطبّع السؤال بنفس الدالة حرفياً.** اختلاف التطبيع بين الفهرسة والاستعلام سبب صامت لانهيار الاسترجاع.
- للجانب اللفظي: تطبيع كامل (إزالة التشكيل والتطويل، توحيد الهمزات والألف المقصورة والتاء المربوطة، توحيد الأرقام). للجانب الدلالي: تطبيع خفيف (تشكيل، تطويل، محارف تحكّم، مسافات، أشكال العرض) — التطبيع العنيف قبل التضمين قد يمحو تمييزاً يستعمله النموذج.
- العربية تستهلك رموزاً أكثر من الإنجليزية بمعنى مكافئ، فقطعة "500 رمز" عربية أقصر كلاماً مما تتوقع. قِس عدد الرموز فعلياً لا بعدد الكلمات.
- الأسئلة كثيراً ما تُكتب بلهجة والمحتوى بالفصحى. عالجها بتوسيع الاستعلام: اطلب من نموذج صغير إعادة صياغة السؤال بالفصحى وأضفه كاستعلام ثانٍ في الجانب اللفظي.
- المستندات المحوّلة من PDF عربي كثيراً ما تحمل حروفاً بأشكال العرض ومسافات مقلوبة الاتجاه؛ نظّفها في الاستيعاب لا في الاستعلام.

> دالة التطبيع الكاملة: مهارة ai-arabic-nlp.

## قائمة تحقق

- [ ] ثبت أن المطالبة الطويلة أو البحث النصي لا يكفيان قبل بناء RAG
- [ ] التقطيع على حدود دلالية، وكل قطعة تحمل عنوان مستندها وسلسلة عناوينها
- [ ] حجم القطعة 300–600 رمز بتداخل 10–15%، والجداول والبنود لا تُقطع
- [ ] نموذج تضمين متعدد اللغات، وبُعده مثبّت، وأي تغيير له يعني إعادة توليد كاملة
- [ ] فئة الفهرس تطابق معامل المسافة، و`explain` يُظهر استعمال الفهرس
- [ ] HNSW بـ`m=16, ef_construction=64`، و`ef_search` أكبر من عدد النتائج المطلوبة
- [ ] بحث هجين (دلالي + لفظي) مدموج بـRRF عند `k=60`
- [ ] ترشيح الصلاحيات داخل الاستعلام لا بعده
- [ ] 40–60 مرشحاً ثم إعادة ترتيب ثم 4–8 قطع فقط للنموذج
- [ ] كل قطعة في السياق مرقّمة، والاستشهاد يظهر للمستخدم كرابط
- [ ] الرفض عند غياب السياق مسار مدعوم، ونسبته مراقَبة
- [ ] عتبة تشابه دنيا معايَرة على بياناتك لا منقولة
- [ ] مجموعة تقييم 50–100 سؤالاً بقطع صحيحة معلومة، وrecall@k وMRR مقيسان قبل وبعد كل تغيير
- [ ] دالة تطبيع عربي واحدة تُستعمل حرفياً في الفهرسة والاستعلام
