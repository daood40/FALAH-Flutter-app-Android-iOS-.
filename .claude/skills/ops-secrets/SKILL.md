# إدارة الأسرار

سؤالان يسبقان كل شيء: **هل هذا سرّ؟** و**من يجب أن يراه؟** أغلب الكوارث تبدأ بإجابة خاطئة على الأول.

## ما هو سرّ وما ليس سرّاً

التعريف الحاسم: **السرّ ما يمنح حامله قدرة لا يملكها بدونه**. القيمة التي تُطبَع أصلاً داخل تطبيق يفتحه أي مستخدم ليست سرّاً — حمايتها تأتي من مكان آخر.

| القيمة | سرّ؟ | لماذا |
|---|---|---|
| مفتاح Supabase العام (`anon` / publishable) | **لا** | مصمَّم ليعيش في العميل، وحمايته RLS لا خفاؤه |
| `service_role` (أو المفتاح السرّي الجديد) | **نعم، وأخطرها** | يتجاوز RLS كلياً = القاعدة بأكملها |
| عنوان مشروع Supabase | لا | عام بطبيعته |
| مفتاح Firebase في `google-services.json` | لا | معرّف إعداد، والحماية بقواعد الأمان وتقييد المفتاح |
| `DSN` الخاص بـ Sentry | لا | يعيش في العميل، صلاحيته إرسال أحداث فقط |
| رمز CI لرفع الرموز إلى Sentry | نعم | صلاحية كتابة على المشروع |
| مفتاح OpenAI / أي مزوّد ذكاء اصطناعي | **نعم** | فاتورة مباشرة على حسابك |
| مفتاح المزوّد **السرّي** للدفع | نعم | حركة أموال |
| المفتاح **العلني** للدفع | لا | مخصّص للواجهة |
| كلمة مرور القاعدة / سلسلة الاتصال | نعم | وصول كامل |
| مفتاح توقيع التطبيق وكلمته | نعم، وفقده لا يُعوَّض | من يملكه ينشر تحديثاً باسمك |
| رمز وصول GitHub / رمز نشر | نعم | تعديل الكود والنشر |
| سرّ توقيع webhook | نعم | من يملكه يزوّر أحداثاً |

**الاختبار العملي**: افتح أدوات مطوّري المتصفّح على موقعك أو فُكّ حزمة تطبيقك. كل ما تجده هناك ليس سرّاً — سواء أردت ذلك أم لا. إن وجدت فيه ما يجب أن يكون سرّاً، فقد تسرّب فعلاً وليس "معرّضاً للتسريب".

الخطأ المعاكس شائع أيضاً: معاملة مفتاح `anon` كسرّ فتتعقّد البنية بلا فائدة، بينما الجهد الحقيقي يجب أن يذهب إلى سياسات RLS.

## أين تُخزَّن

| المكان | لماذا | يناسب |
|---|---|---|
| GitHub ← Secrets and variables ← Actions | مشفّر، مُقنَّع في السجلّ، لا يُقرأ بعد الكتابة | أسرار البناء والنشر |
| GitHub ← Environments ← secrets | نفس ما سبق + موافقة وتقييد فرع | أسرار الإنتاج تحديداً |
| متغيّرات البيئة في منصّة الاستضافة | تُحقَن وقت التشغيل للدوال | أسرار الخادم/الدوال |
| Supabase Vault | مشفّر داخل القاعدة، يُقرأ من SQL | سرّ تحتاجه دالة Postgres |
| مدير كلمات مرور | المصدر الوحيد الذي تعود إليه | نسختك الاحتياطية من كل سرّ |
| ملف `.env` محلي غير متتبَّع | — | التطوير المحلي فقط |

**السرّ في GitHub لا يُقرأ بعد كتابته** — لا واجهة تعرضه. من لا يحتفظ بنسخة في مدير كلمات مرور سيجد نفسه مضطراً لتدوير مفتاح لمجرّد أنه نسيه. ومفتاح التوقيع تحديداً: نسخة مشفّرة خارج جهازك وخارج المستودع، فقده يعني إصداراً جديداً بهوية جديدة.

القيم غير السرّية (عنوان API، معرّف المشروع، اسم البيئة) ضعها في **Variables** لا في Secrets — تقنيعها في السجلّات يعمي عنك التشخيص بلا فائدة.

## ما لا يدخل المستودع أبداً

`.env`، أي `*.pem` أو `*.key`، `*.jks` و`*.keystore`، أي ملف حساب خدمة JSON، ملفات تعريف التوفير، ملفات قواعد بيانات محلية، ولقطات إنتاج فيها بيانات مستخدمين.

بدلاً منها: `.env.example` يحوي **أسماء** المتغيّرات وقيماً وهمية واضحة (`SUPABASE_URL=https://xxxx.supabase.co`)، ملتزَم ومُحدَّث. هو التوثيق الوحيد الذي يمنع سؤال "أي متغيّرات يحتاجها المشروع؟" بعد ستة أشهر.

**الخطأ الأكثر شيوعاً**: ملف إعداد يحمل قيمة حقيقية "مؤقتاً للتجربة" ثم يُلتزم. ثاني أكثرها: `.gitignore` أُضيف **بعد** التزام الملف — والتجاهل لا يؤثّر على ملف متتبَّع بالفعل، فيبقى في التاريخ إلى الأبد.

## فحص المستودع من التسريبات

ثلاث طبقات، والأولى وحدها لا تكفي:

1. **Push protection من GitHub** — يرفض الدفعة التي تحوي نمط سرّ معروف قبل وصولها. مجاني للمستودعات العامة، ويجب تفعيله من Settings ← Code security. إنه الوحيد الذي يمنع الحادث بدل الإبلاغ عنه.
2. **Secret scanning** — يفحص التاريخ كله ويُنبّه على ما دخل سابقاً.
3. **فحص في CI** — أداة مثل `gitleaks` كخطوة في سير العمل تفحص كل PR وتفشل عند اكتشاف نمط. مفيدة لأنها تلتقط أنماطك الخاصة أيضاً عبر إعداد قواعد إضافية.

للفحص اليدوي السريع من الجوال، استعمل بحث المستودع في GitHub عن سلاسل مميّزة: `service_role`، `BEGIN PRIVATE KEY`، `password =`، `sk-`، `eyJ` (بداية أي JWT). البحث يشمل الشيفرة الحالية فقط، لا التاريخ.

## تنظيف التاريخ

قرار قبل العمل: **هل يستحق؟** إن كان المستودع خاصاً ولم يصل إليه أحد، فالتدوير وحده يكفي وتنظيف التاريخ مخاطرة زائدة. إن كان عاماً أو صار عاماً، فنظّف — مع فهم أن التنظيف تخفيف ضرر لا علاج.

الأدوات الحقيقية: `git filter-repo` (الموصى بها اليوم) أو BFG Repo-Cleaner. كلتاهما تعيد كتابة كل الالتزامات المتأثّرة، فتتغيّر معرّفات الالتزامات وتحتاج دفعاً بالقوة، وأي نسخة أو فرع أو PR مفتوح يصير غير متوافق.

قبل التنظيف: أنشئ نسخة احتياطية كاملة من المستودع، وأغلق أو ادمج كل PR مفتوح. بعده: نظّف مراجع الإصدارات القديمة، واطلب من دعم GitHub إزالة الالتزامات المخبّأة إن كان المستودع عاماً — لأن الالتزام القديم قد يبقى قابلاً للوصول بمعرّفه المباشر رغم اختفائه من التاريخ. وأي fork للمستودع يحتفظ بالنسخة الأصلية بلا سلطة لك عليه.

الخلاصة الواقعية: **افترض أن ما دخل مستودعاً عاماً قد التُقط خلال دقائق.** بوتات تفحص الدفعات العامة لحظياً وتجرّب المفاتيح آلياً.

## التدوير بعد التسريب

الترتيب إجباري، وأول خطوة هي الوحيدة التي توقف الضرر:

1. **ألغِ المفتاح المسرَّب فوراً** من لوحة المزوّد. لا تنتظر تجهيز البديل ولا تنظيف التاريخ.
2. أنشئ مفتاحاً جديداً.
3. حدّثه في كل مكان يستهلكه: GitHub Secrets، متغيّرات المنصّة، مدير كلمات المرور.
4. أعِد النشر وتحقّق من عمل كل شيء.
5. أزل السرّ من الكود وادفع.
6. **افحص السجلّات بحثاً عن سوء استخدام** خلال نافذة التعرّض: نداءات غير معتادة، استهلاك مفاجئ، وصول من مناطق غريبة، صفوف مُعدَّلة.
7. نظّف التاريخ إن لزم.
8. اسأل: كيف دخل؟ وأضف الحاجز المانع (push protection، فحص CI، `.gitignore` أدق).

حالات خاصة: تسريب `service_role` = تسريب القاعدة كاملة، فبعد التدوير راجع بيانات المستخدمين بحثاً عن تعديل أو تسريب وقرّر إن كان الإبلاغ واجباً. وتسريب مفتاح مزوّد ذكاء اصطناعي = فاتورة فورية، فاضبط حدّ إنفاق على الحساب كإجراء وقائي دائم لا كردّ فعل.

> إزالة السرّ من الالتزامات وسير عمل git: مهارة ops-git-workflow.

## الأسرار في CI بلا طباعتها

القاعدة: السرّ يُمرَّر عبر `env` لا عبر الاستيفاء المباشر داخل نصّ الصدفة.

```yaml
- name: نشر
  env:
    DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
  run: ./scripts/deploy.sh      # يقرأ المتغيّر من البيئة
```

الاستيفاء المباشر يضع القيمة حرفياً في سطر الأمر، فتظهر عند تفعيل التتبّع أو في رسالة خطأ من الصدفة، وتصبح عرضة لحقن عبر محتوى غير موثوق.

منصّة CI تُقنّع القيمة الحرفية في السجلّ تلقائياً، لكن التقنيع ينكسر في حالات واقعية: القيمة مُرمّزة base64، أو مقسّمة، أو مُضمَّنة في JSON مُصاغ، أو مطبوعة حرفاً حرفاً. لذا:

- لا `echo` ولا طباعة للبيئة كلها لتشخيص عطل.
- لا تمرير السرّ كمعامل في سطر أمر يظهر في السجلّ.
- استعمل `--silent` أو ما يعادله في أدوات الشبكة، ووجّه المخرجات المطوّلة إلى ملف لا إلى السجلّ.
- عند تفعيل السجلّ التفصيلي للتشخيص، تذكّر أنه يوسّع ما يظهر — راجع السجلّ بعده.
- **الأسرار لا تُمرَّر لسير عمل يُشغَّل من fork عبر `pull_request`** — قيد مقصود، ولا تحايل عليه بمحفّز أخطر.

وقصر نطاق كل سرّ: سرّ الإنتاج داخل Environment مقيّد بفرع `main` وبموافقة، لا سرّاً على مستوى المستودع تصل إليه كل الفروع.

## فصل التطوير عن الإنتاج

| القاعدة | التطبيق |
|---|---|
| مشروعان منفصلان | مشروع Supabase للتجربة وآخر للإنتاج، لا واحد |
| مفتاحان مختلفان لكل خدمة | مفاتيح اختبار المزوّدين في staging دائماً |
| لا نسخ بيانات حقيقية إلى التجربة | وإن لزم، تُعقَّم: أسماء وهواتف مستبدلة |
| صلاحيات أضيق للتطوير | لا حاجة لمفتاح إنتاج في بيئة تجريبية أبداً |
| كل سرّ يُدوَّر عند تغيّر من يصل إليه | حتى في مشروع فردي: تسريب staging لا يجب أن يمسّ الإنتاج |

أخطر ما يحدث عملياً: مفتاح إنتاج في بيئة التجربة، ثم هجرة تجريبية تمسح جدولاً حقيقياً. الفصل الفيزيائي — مشروعان مختلفان — هو الحاجز الوحيد الذي لا يعتمد على انتباهك.

## العميل مقابل الخادم

| الوصول | ما يُسمح | الحماية |
|---|---|---|
| العميل (تطبيق/متصفّح) | مفتاح عام فقط | RLS وقواعد الأمان وتقييد المفتاح بالنطاق/الحزمة |
| الخادم (دالة حافة، CI، خادم) | مفاتيح سرّية | لا تغادر بيئة التشغيل |

كل مفتاح تحتاج إخفاءه = عملية تحتاج وسيطاً على الخادم. النمط: العميل ينادي دالة حافة، الدالة تتحقّق من هوية المستخدم وصلاحيته، ثم تنادي المزوّد بالمفتاح السرّي وتُعيد النتيجة. وأضف حدّ معدّل على الوسيط، وإلا صار مفتاحك مفتوحاً للعالم بشكل غير مباشر.

قيّد ما يمكن تقييده حتى لو لم يكن سرّاً: مفاتيح الخرائط والخدمات العامة تُقيَّد بنطاق الموقع أو بمعرّف الحزمة وبصمة التوقيع، فتصبح عديمة القيمة خارج تطبيقك.

## قبل جعل مستودع عاماً

- [ ] فحص التاريخ كله بأداة أسرار، لا الشيفرة الحالية فقط
- [ ] لا `.env` ولا `*.key`/`*.pem`/`*.jks` ولا ملف حساب خدمة في أي التزام
- [ ] لا لقطات قاعدة بيانات ولا ملفات فيها بيانات مستخدمين حقيقية
- [ ] لا نقاط API داخلية ولا عناوين خوادم خاصة في التعليقات
- [ ] لا سجلّات ولا لقطات شاشة داخل المستودع تحوي رموزاً
- [ ] `README` لا يحوي بيانات دخول تجريبية حقيقية
- [ ] كل سرّ سبق أن دخل المستودع يوماً **مُدوَّر بالفعل**
- [ ] `.gitignore` مكتمل، وpush protection مفعّل، وفحص أسرار في CI

## قائمة تحقق

- [ ] كل قيمة مُصنَّفة: سرّ أو غير سرّ، والقرار مبني على القدرة التي تمنحها
- [ ] `service_role`/المفتاح السرّي غير موجود في أي بناء عميل ولا مستودع
- [ ] `.env.example` ملتزَم ومُحدَّث، و`.env` مُتجاهَل من قبل أول التزام
- [ ] كل سرّ له نسخة في مدير كلمات مرور، ومفتاح التوقيع منسوخ خارج الجهاز
- [ ] Push protection وsecret scanning مفعّلان، وفحص أسرار خطوة في CI
- [ ] الأسرار تُمرَّر عبر `env` فقط، ولا `echo` ولا طباعة بيئة في السجلّات
- [ ] أسرار الإنتاج داخل Environment مقيّد بفرع وبموافقة
- [ ] مشروعان منفصلان تماماً للتجربة والإنتاج بمفاتيح مختلفة
- [ ] كل مفتاح سرّي وراء وسيط خادمي عليه تحقّق هوية وحدّ معدّل
- [ ] المفاتيح العامة مقيّدة بالنطاق أو بمعرّف الحزمة
- [ ] ترتيب التدوير معروف ومكتوب: إلغاء ← إنشاء ← تحديث ← نشر ← فحص سوء الاستخدام
- [ ] حدّ إنفاق مضبوط على كل خدمة تُحاسب بالاستهلاك
