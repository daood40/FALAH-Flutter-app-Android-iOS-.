# بوابة الإطلاق

## القاعدة الصفرية

**لا يجوز قول "جاهز للإنتاج" إلا مع تقرير فيه بوابات وأدلة.** الجملة بلا تقرير رأي، والرأي لا يُطلق إصداراً.

الدليل المقبول: أمر شُغِّل ومخرجاته، رابط وظيفة CI ناجحة، لقطة من جهاز حقيقي، استعلام SQL ونتيجته، تاريخ ورقم إصدار. الدليل غير المقبول: "اختبرته وكان يعمل"، "الكود يبدو سليماً"، "لم تظهر مشاكل".

كل بوابة **PASS أو FAIL أو NOT RUN**. لا توجد درجات وسطى ولا "شبه جاهز". بوابة لم تُنفَّذ تُسجَّل NOT RUN وتُحسب كـ FAIL في القرار.

البوابة 13 هي الأكثر تخطّياً والأعلى كلفة: بناء debug يعمل وبناء release ينهار عند الإقلاع بسبب تصغير الكود أو أذونات ناقصة أو مفتاح توقيع مختلف. **اختبار الحزمة نفسها التي سترفعها، لا حزمة أخرى.**

البوابة 16 هي ما يمنع كارثة: إن انفجرت ميزة بعد النشر فمراجعة المتجر تستغرق يوماً أو أكثر، والمفتاح عن بُعد يوقفها في دقائق. أبسط شكل مقبول: جدول إعدادات في Supabase يقرأه التطبيق عند الإقلاع، وفيه `min_supported_version` و`features` معطّلة، مع سلوك افتراضي آمن عند فشل القراءة.

البوابة 17 خاصة بالمتاجر: نموذج سلامة البيانات في Google Play ونموذج الخصوصية في App Store يجب أن يطابقا الواقع — إعلان "لا نجمع بيانات" مع وجود تحليلات سبب رفض متكرر، والتصحيح يكلّف دورة مراجعة كاملة.

## معنى BLOCKED

الحالة الثالثة للتقرير كاملاً، لا لبوابة مفردة:

- **PASS**: كل البوابات PASS. الإطلاق مسموح.
- **FAIL**: بوابة أو أكثر FAIL بسبب عطل في المنتج. الإصلاح ثم إعادة الفحص.
- **BLOCKED**: البوابة لا يمكن الحكم عليها لسبب **خارج المنتج** — بيئة الاختبار معطّلة، حساب متجر معلّق، خدمة خارجية متوقّفة، لا جهاز اختبار متاح.

BLOCKED يُقبل بثلاثة شروط مجتمعة: السبب موثّق بدقة، وأثره محدود ومعروف، وله تاريخ رفع محدّد. وهذه الحالات لا تُقبل BLOCKED أبداً: البوابة 12 (الأسرار)، والبوابة 7 عند وجود عطل حرج، والبوابة 9 عند غياب RLS. هذه تُفحص أو لا يُطلق.

الخطأ الأكثر شيوعاً: استعمال BLOCKED كمهرب من FAIL. "الاختبار لم يعمل عندي" ليست BLOCKED — هي NOT RUN، وحكمها FAIL.

## من يملك القرار

في مشروع فردي، الأدوار منفصلة زمنياً لا شخصياً:

1. **بصفتك المطوّر**: تُصلح وتشغّل الفحوص وتجمع الأدلة.
2. **بصفتك المُختبِر**: تشغّل البوابات على حزمة الإصدار كما هي، بلا تعديل كود أثناء الفحص. أي تعديل يُبطل النتائج ويوجب إعادة الفحص من البوابة 1.
3. **بصفتك مالك الإصدار**: تقرأ التقرير وتقرّر، ثم توقّع القرار بالاسم والتاريخ في ملف الإصدار.

القاعدة: **من كتب الميزة لا يقرّر إطلاقها في نفس الجلسة.** افصل بيوم أو على الأقل بجلسة مستقلة تبدأ من التقرير لا من الكود.

الوكيل (Claude) لا يملك قرار الإطلاق. مهمّته إنتاج التقرير وتصنيف الأعطال، والقرار للمالك البشري وحده.

## سير عمل يُنتج التقرير آلياً

```yaml
name: release-gate
on:
  push:
    tags: ['v*']

jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: أسرار وإعدادات الإنتاج
        run: |
          ! git log -p --all | grep -qEi "service_role|sk_live|BEGIN [A-Z ]*PRIVATE KEY"
          ! git ls-files | grep -qEi "\.env$|\.jks$|\.keystore$"
          ! grep -rqn "http://\|localhost\|10\.0\.2\.2" lib/
          ! grep -rqn "android:debuggable=\"true\"" android/app/src/main/AndroidManifest.xml

      - name: تحليل واختبارات وبناء
        run: |
          flutter analyze
          flutter test --machine > test-results.json
          flutter build appbundle --release
          test "$(stat -c%s build/app/outputs/bundle/release/app-release.aab)" -lt 31457280  # 30MB

      - name: قاعدة البيانات وواجهات HTTP
        run: |
          psql "$STAGING_DB_URL" -v ON_ERROR_STOP=1 -f supabase/tests/rls_checks.sql
          ./scripts/api-suite.sh

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: release-gate-report
          path: |
            test-results.json
            reports/
```

الوظيفة تُنتج البوابات 1، 2، 3، 6، 9، 11، 12 آلياً. البوابات 8، 10، 13، 14، 16 تحتاج جهازاً حقيقياً وتبقى يدوية — تُسجَّل نتائجها في ملف التقرير في نفس الـ PR قبل الوسم. لا تُعلَن PASS بلا تنفيذ فعلي.

> إعداد الوظائف والأسرار: افتح مهارة ops-github-actions ومهارة ops-secrets.

## قائمة تحقق

- [ ] لا جملة "جاهز للإنتاج" بلا تقرير بوابات مكتمل
- [ ] كل بوابة PASS أو FAIL أو BLOCKED — بلا حالات وسطى
- [ ] كل PASS مرفقة بدليل قابل للفحص (أمر، رابط، لقطة، استعلام)
- [ ] بوابة لم تُنفَّذ مسجَّلة NOT RUN ومحسوبة FAIL
- [ ] البوابات السبع عشرة موجودة في الجدول ولم تُحذف أي منها
- [ ] حزمة الإصدار نفسها (release موقّعة) اختُبرت على جهاز حقيقي
- [ ] لا عنوان تطوير ولا debuggable ولا وجهة staging في الحزمة
- [ ] فحص الأسرار شمل تاريخ git والحزمة المبنية
- [ ] تقارير الأعطال مفعّلة وعطل تجريبي وصل فعلاً
- [ ] النسخة الاحتياطية استُعيدت خلال 30 يوماً
- [ ] مفتاح الإيقاف عن بُعد موجود ومُختبَر بتفعيل حقيقي
- [ ] سياسة الخصوصية منشورة ونموذج سلامة البيانات يطابق الجمع الفعلي
- [ ] أي تخفيف لبوابة مكتوب صراحة مع سببه
- [ ] كل BLOCKED له سبب خارجي وأثر محدود وتاريخ رفع
- [ ] لا BLOCKED على الأسرار ولا على عطل أمني حرج ولا على غياب RLS
- [ ] لا تعديل كود أثناء جولة الفحص؛ التعديل يوجب إعادة الفحص من البوابة 1
- [ ] القرار موقّع بالاسم والتاريخ، والوكيل لم يتّخذه
- [ ] التقرير محفوظ في المستودع مع وسم الإصدار
- [ ] سير عمل release-gate يعمل عند الوسم ويرفع التقرير كمُخرَج
