# كتابة خطة الاختبار وحالات الاختبار

حالة الاختبار المكتوبة جيداً ينفّذها شخص لم يبنِ الميزة ويصل لنفس الحكم. إن احتاجت تخميناً، فهي ليست حالة اختبار بل تذكير غامض. الهدف ليس كثرة الحالات بل **أقل عدد يغطّي أكبر مساحة خطر**.

## بنية حالة الاختبار

سبعة حقول، لا أقل:

| الحقل | القاعدة |
|---|---|
| المعرّف | ثابت لا يتغيّر أبداً، مثل `TC-AUTH-012` |
| العنوان | جملة تصف ما يُختبر، لا "اختبار الدخول" بل "دخول بكلمة مرور خاطئة ثلاث مرات" |
| الشرط المسبق | حالة النظام والبيانات قبل الخطوة الأولى — حساب موجود، جلسة مغلقة، رصيد 50 |
| الخطوات | مرقّمة، كل خطوة فعل واحد بقيمة محدّدة، بلا "املأ النموذج" |
| النتيجة المتوقّعة | ملاحَظة من الخارج ومحدّدة: نص الرسالة، الشاشة التالية، الصف في قاعدة البيانات |
| النتيجة الفعلية | تُملأ وقت التنفيذ، لا قبله |
| الحكم | `اجتاز` / `فشل` / `محجوب` / `غير قابل للتنفيذ` — بلا "تقريباً" |

حقول اختيارية مفيدة: الأولوية (P0/P1/P2)، رقم متطلّب القبول، نوع التنفيذ (آلي/يدوي)، البيئة. والقيمة تُكتب صراحة: ليس "أدخل بريداً غير صالح" بل `أدخل a@` — الحالة بلا قيم محدّدة تُنفَّذ بشكل مختلف كل مرة فلا تُقارَن نتائجها.

## الاشتقاق من معايير القبول

كل معيار قبول يولّد **ثلاث عائلات** من الحالات على الأقل:

1. **المسار الموجب** — المعيار يتحقّق كما كُتب.
2. **المسار السالب** — المعيار لا يتحقّق (المدخل خاطئ، الشرط غير مستوفى).
3. **الحدود** — قيم على حافة الشرط.

مثال معيار: «يستطيع المستخدم إنشاء طلب إذا كان مسجّلاً وسلّته غير فارغة وقيمتها 20 د.ل فأكثر».

الشروط الثلاثة: مسجّل، سلّة غير فارغة، القيمة ≥ 20. منها:

| المعرّف | الحالة |
|---|---|
| TC-ORD-001 | مسجّل، سلّة بعنصرين، 45 د.ل → ينجح الطلب |
| TC-ORD-002 | غير مسجّل، سلّة صالحة → يُوجَّه لشاشة الدخول وتبقى السلّة |
| TC-ORD-003 | مسجّل، سلّة فارغة → زر الطلب معطّل ورسالة "السلّة فارغة" |
| TC-ORD-004 | مسجّل، القيمة 19.99 → رفض برسالة تذكر الحد 20 |
| TC-ORD-005 | مسجّل، القيمة 20.00 بالضبط → ينجح |

معيار قبول لا يمكن اشتقاق حالة قابلة للملاحظة منه هو معيار سيّئ الكتابة — أعده للمواصفة قبل الاختبار.

> كتابة معايير القبول أصلاً: مهارة product-spec-writing.

## تقليل عدد الحالات بلا فقدان تغطية

### تقسيم التكافؤ

قسّم مجال المدخل إلى فئات تتصرّف داخلها كل القيم بنفس الطريقة، ثم اختبر **قيمة واحدة من كل فئة**. اختبار كلمة مرور بطول 20 ثم 21 ثم 22 هدر؛ كلها في فئة واحدة.

كلمة مرور 8–64 محرفاً:

| الفئة | تمثيل | متوقّع |
|---|---|---|
| أقصر من الحد | `abc123` | رفض |
| ضمن النطاق | `Passw0rd!` | قبول |
| أطول من الحد | 70 محرفاً | رفض |
| فارغة أو مسافات فقط | `` / `      ` | رفض |

أربع حالات بدل عشرات.

### تحليل القيم الحدّية

الأعطال تتجمّع على الحواف. لكل حدّ اختبر: `min-1`, `min`, `max`, `max+1`. أضف `min+1` و`max-1` فقط للحدود عالية الخطر (مال، كميات، صلاحيات).

لطول 8–64: `7, 8, 64, 65`. للمبلغ ≥ 20: `19.99, 20.00, 20.01`. لقائمة تعرض 20 عنصراً في الصفحة: `0, 1, 20, 21`. هذه التقنية مع سابقتها تغطّيان عملياً أغلب أعطال المدخلات.

### جدول القرار

يُستعمل حين تتفاعل عدة شروط منطقية معاً وتنتج مخرجات مختلفة. اكتب الشروط صفوفاً والحالات أعمدة.

مثال: خصم على الطلب.

| الشرط | ح1 | ح2 | ح3 | ح4 | ح5 |
|---|---|---|---|---|---|
| مستخدم جديد | نعم | نعم | لا | لا | لا |
| قيمة السلّة ≥ 100 | لا | نعم | لا | نعم | نعم |
| كوبون صالح | لا | لا | نعم | نعم | منتهٍ |
| **النتيجة المتوقّعة** | 10% | 10% | قيمة الكوبون | الأكبر من الاثنين | لا خصم + رسالة |

بثلاثة شروط ثنائية يوجد 8 تركيبات نظرياً؛ الجدول يحذف المستحيل والمكرر ويترك ما يستحق التنفيذ. **كل عمود يصير حالة اختبار بمعرّف.** أهم قيمة للجدول أنه يكشف تركيبات لم يقرّرها أحد أثناء التصميم — تلك أسئلة للمواصفة قبل أن تكون أعطالاً.

### انتقال الحالات

يُستعمل حين للكائن حالات وانتقالات: طلب، اشتراك، رفع ملف، جلسة.

حالات الطلب: `جديد → مؤكَّد → قيد التوصيل → مُسلَّم`، و`ملغى` من `جديد` أو `مؤكَّد` فقط.

اختبر ثلاث فئات: كل **انتقال مشروع** مرة واحدة (تغطية 100% للانتقالات المسموحة، هدف قابل للقياس)؛ و**الانتقالات الممنوعة** (إلغاء بعد التسليم، تأكيد طلب ملغى، تسليم بلا توصيل) والمتوقّع رفض واضح لا تغيّر صامت؛ و**الانتقالات المتزامنة** (نفس الطلب يُلغى من الجوال ويُؤكَّد من لوحة التحكم في اللحظة نفسها).

## تغطية المسارات البديلة ومسارات الفشل

لكل ميزة اكتب حالات لهذه المحاور، وإلا فالخطة ناقصة:

| المحور | مثال حالة |
|---|---|
| مسار بديل للوصول | نفس النتيجة عبر البحث بدل القائمة |
| فشل شبكة | انقطاع أثناء الإرسال → رسالة + إمكانية إعادة المحاولة بلا تكرار السجل |
| فشل خادم | استجابة 500 → رسالة عربية مفهومة لا رمز تقني |
| فشل صلاحية | رمز جلسة منتهٍ → توجيه للدخول مع حفظ الوجهة |
| بيانات مفقودة | حقل اختياري فارغ في السجل → عرض بديل لا فراغ مكسور |
| تنافس وإلغاء | نفس السجل يُعدَّل من جهازين؛ رجوع في منتصف الحفظ → لا سجل نصف مكتمل |

نسبة صحية: **40–50% من الحالات لمسارات الفشل والحدود**. خطة كلها مسارات سعيدة لا تكشف شيئاً.

## الترقيم والربط

`TC-<الميزة>-<رقم>` بثلاث خانات: `TC-AUTH-003`, `TC-PAY-017`, `TC-ORD-004`.

قواعد لا تُخالَف:
- المعرّف **لا يُعاد استخدامه** بعد حذف الحالة، ولا يُعاد ترقيم الحالات.
- كل حالة تحمل مرجع معيار القبول أو رقم العطل الذي ولّدها (`AC-2` أو `BUG-2026-041`)، والمشتقّة من عطل تُوسَم `regression` وتبقى للأبد.
- ملف واحد لكل ميزة تحت `qa/plans/<feature>.md` أو `.yaml`.

## ماذا يعني "اجتاز" بدقة

**اجتاز** = كل النتائج المتوقّعة في الحالة تحقّقت حرفياً، على البيئة المحدّدة، بلا خطوات إضافية غير مكتوبة، وبلا أعراض جانبية (سجل خطأ في وحدة التحكم، وميض، تأخّر غير مبرّر).

هذه كلها **فشل** وليست اجتيازاً: تحقّقت بعد إعادة المحاولة؛ تحقّقت لكن الرسالة بصياغة مختلفة عن المكتوب (إلا إذا كان النص خارج نطاق الحالة صراحة)؛ تحقّقت مع تحذير في السجل؛ تحقّقت على جهاز واحد من اثنين.

`محجوب` = تعذّر التنفيذ بسبب عطل آخر أو بيئة غير جاهزة. لا تُسجَّل `فشل` — وإلا تلوّثت الإحصاءات.

## قالب جاهز

```yaml
# qa/plans/checkout.yaml
feature: إتمام الطلب
version: 1.4.0
environment: staging — Android 13، جهاز متوسط، شبكة 4G
data_setup: مستخدم test01@example.com، سلّة بعنصرين بقيمة 45 د.ل

cases:
  - id: TC-ORD-004
    title: رفض الطلب حين تقلّ قيمة السلّة عن الحد الأدنى
    ref: AC-3
    priority: P0            # P0 | P1 | P2
    type: manual            # manual | automated
    tags: [boundary, negative]
    preconditions: [مستخدم مسجّل دخوله, السلّة فيها عنصر واحد بقيمة 19.99 د.ل]
    steps:
      - افتح شاشة السلّة
      - اضغط "إتمام الطلب"
    expected:
      - لا يُنشأ طلب جديد
      - تظهر رسالة "الحد الأدنى للطلب 20 د.ل"
      - يبقى المستخدم في شاشة السلّة والعناصر كما هي
    actual: ""
    result: ""      # pass | fail | blocked | n/a
    bug: ""
```

وللحالات اليدوية السريعة يكفي سطر markdown مضغوط بنفس الحقول:

```markdown
### TC-ORD-005 — طلب بقيمة تساوي الحد الأدنى بالضبط  (P0, AC-3)
**مسبقاً:** مستخدم مسجّل، سلّة بقيمة 20.00 د.ل
**الخطوات:** 1) افتح السلّة  2) اضغط "إتمام الطلب"  3) أكّد الدفع عند الاستلام
**المتوقّع:** طلب بحالة "جديد"، شاشة تأكيد برقم الطلب، السلّة فارغة
**الفعلي:**   **الحكم:**
```

## أخطاء شائعة

- خطوات مثل "سجّل الدخول ثم أكمل" بدل خطوات ذرّية بقيم، ونتيجة مثل "يعمل بشكل صحيح" غير قابلة للحكم.
- خلط عدة أهداف في حالة واحدة، فلا تعرف أيها فشل.
- إعادة ترقيم الحالات عند إعادة التنظيم، فتنكسر كل الروابط بالأعطال.
- خطة بلا شرط مسبق للبيانات: تنجح عندك وتفشل عند إعادة التنفيذ.

## قائمة تحقق

- [ ] كل حالة بمعرّف ثابت من الشكل `TC-<الميزة>-<رقم>` لا يُعاد استخدامه
- [ ] الحقول السبعة موجودة، والقيم مكتوبة صراحة لا موصوفة
- [ ] كل معيار قبول ولّد حالة موجبة وأخرى سالبة وحالات حدّية
- [ ] تقسيم التكافؤ مطبّق: قيمة واحدة لكل فئة، لا تكرار داخل الفئة
- [ ] لكل حدّ رقمي حالات `min-1`, `min`, `max`, `max+1`
- [ ] جدول قرار لكل ميزة بثلاثة شروط متفاعلة فأكثر، وكل عمود صار حالة
- [ ] تغطية 100% للانتقالات المشروعة، وحالات للانتقالات الممنوعة
- [ ] 40–50% من الحالات لمسارات الفشل والحدود
- [ ] حالات لفشل الشبكة والخادم والصلاحية والتنافس والإلغاء
- [ ] كل حالة مربوطة بمعيار قبول أو رقم عطل
- [ ] حالات الانحدار موسومة `regression` ولا تُحذف
- [ ] تعريف "اجتاز" مطبّق بصرامة، و`محجوب` منفصل عن `فشل`
- [ ] الشرط المسبق للبيانات مكتوب بحيث تُعاد الحالة على جهاز آخر بنفس النتيجة
- [ ] الملفات تحت `qa/plans/` وتُقارَن في git
