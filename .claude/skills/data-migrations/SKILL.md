# الهجرات وتطوّر المخطط

القاعدة الأولى: **لا تعديل يدوي في لوحة تحكم Supabase على الإنتاج، أبداً.** التعديل اليدوي غير مُسجَّل، غير قابل لإعادة التطبيق، ولا يوجد في نسخة التطوير — وستكتشف الفارق عند أول انتشار.

## لماذا ملف مرقّم في المستودع

كل تغيير على المخطط ملف SQL واحد في `supabase/migrations/` باسم `<timestamp>_<وصف>.sql`.

| المشكلة بلا هجرات | ما تحلّه الهجرات |
|---|---|
| لا تعرف حالة الإنتاج الحالية | الملفات هي الحالة، مرتّبة زمنياً |
| بيئة التطوير تختلف عن الإنتاج | نفس الملفات تُطبَّق على الاثنين |
| لا مراجعة على تغيير المخطط | التغيير يمرّ في Pull Request |
| لا تعرف من غيّر ولا متى | git blame |
| لا تستطيع إعادة بناء القاعدة | `supabase db reset` يبني كل شيء |

قواعد ملفات الهجرة: ملف واحد = تغيير منطقي واحد، ولا تجمع خمسة تغييرات غير مرتبطة. و**لا تعدّل ملف هجرة طُبّق على الإنتاج** — التصحيح هجرة جديدة، وتعديل القديم يجعل مجاميع التحقق غير متطابقة ويكسر البيئات الأخرى. اجعل الملف قابلاً لإعادة التشغيل قدر الإمكان (`create table if not exists`, `create or replace function`, `drop policy if exists` قبل `create policy`). وسياسات RLS ودوال الـ RPC تعيش في الهجرات أيضاً، لا في إعدادات لوحة التحكم. وملف البذور `seed.sql` منفصل ولا يُشغَّل على الإنتاج.

سير العمل من الهاتف: أنشئ ملف الهجرة في المستودع، افتح PR، ثم يطبّقها GitHub Actions بـ `supabase db push` على الإنتاج بعد الدمج — بلا أي خطوة يدوية.

## الأمامية فقط مقابل التراجع

`down` migration فكرة جذابة تفشل عملياً: التراجع عن `drop column` يعيد العمود فارغاً — البيانات ذهبت.

الموقف العملي: اكتب `up` فقط، واجعل كل هجرة صغيرة وآمنة بحيث لا تحتاج تراجعاً. خطة التراجع الحقيقية **هجرة تصحيح أمامية** تُكتب بسرعة، لا سكربت `down`. والاستثناء الوحيد الهجرات المدمّرة (`drop column`, `drop table`): لا تُنشر إلا بعد أن يكون العمود بلا استعمال منذ إصدارين، ومع نسخة احتياطية موثّقة في نفس الـ PR. واستعمل معاملة صريحة حيث تستطيع — Postgres يدعم DDL معامَلاتياً فأغلب الهجرات إما تنجح كلها أو لا شيء، باستثناء `CREATE INDEX CONCURRENTLY` و`ALTER TYPE ... ADD VALUE`.

## التغييرات الآمنة مقابل الكاسرة

| التغيير | القفل | آمن على الإنتاج |
|---|---|---|
| `add column` بلا default | ACCESS EXCLUSIVE لحظي | نعم |
| `add column ... default <ثابت>` | لحظي (PG 11+) | نعم |
| `add column ... default <دالة volatile>` | إعادة كتابة الجدول كاملاً | لا |
| `drop column` | لحظي (العمود يُخفى فقط) | نعم تقنياً، كاسر للعملاء |
| `alter column type` (توسيع varchar/int→bigint) | إعادة كتابة | لا على جدول كبير |
| `rename column/table` | لحظي | **كاسر فوراً لكل عميل قديم** |
| `add not null` على عمود قائم | مسح كامل تحت قفل | لا مباشرة |
| `add check` | مسح تحت قفل | لا مباشرة — استعمل `not valid` |
| `add foreign key` | قفل على الجدولين | لا مباشرة — `not valid` ثم `validate` |
| `create index` | يحجب الكتابة | لا — استعمل `CONCURRENTLY` |
| `add default` | لحظي | نعم |

معيار "الكاسر" هنا ليس القاعدة وحدها: تطبيقك على المتاجر لا يُحدَّث فوراً. **إعادة تسمية أو حذف عمود يكسر كل نسخة منشورة تستعمله.** هذا القيد يحكم كل ما يلي.

قبل أي DDL على الإنتاج:

```sql
set lock_timeout = '3s';   -- بدونها تنتظر alter table خلف معاملة طويلة
set statement_timeout = '30s';
```
وكل الطلبات الجديدة تصطف خلف ذلك الانتظار — توقف كامل من تغيير كان يفترض أن يأخذ جزءاً من الثانية.

## expand / contract لإعادة تسمية عمود بلا توقّف

إعادة تسمية `phone` إلى `phone_e164` بينما نسخ قديمة من التطبيق ما زالت تعمل:

**المرحلة 1 — توسيع (هجرة 1، تُنشر مع أي إصدار):**
```sql
alter table public.profiles add column phone_e164 text;
```

**المرحلة 2 — مزامنة مزدوجة (هجرة 2):**
```sql
create or replace function public.sync_phone() returns trigger
language plpgsql as $$
begin
  if new.phone_e164 is distinct from old.phone_e164 then
    new.phone := new.phone_e164;
  elsif new.phone is distinct from old.phone then
    new.phone_e164 := new.phone;
  end if;
  return new;
end $$;
create trigger profiles_sync_phone before insert or update on public.profiles
  for each row execute function public.sync_phone();
```

**المرحلة 3 — ملء البيانات القديمة (هجرة 3، على دفعات):**
```sql
update public.profiles set phone_e164 = phone
where phone_e164 is null and phone is not null
  and id in (select id from public.profiles
             where phone_e164 is null and phone is not null limit 5000);
-- تُكرَّر حتى صفر صفوف، أو تُنفَّذ عبر مهمة pg_cron
```

**المرحلة 4 — نشر إصدار التطبيق الذي يقرأ ويكتب `phone_e164` فقط.**

**المرحلة 5 — انتظار.** لا تُقدِم على المرحلة 6 قبل أن تُظهر تحليلاتك أن نسبة الاستعمال للإصدارات القديمة تحت 1–2%. عملياً 30–90 يوماً في متاجر التطبيقات.

**المرحلة 6 — انكماش (هجرة 4):**
```sql
drop trigger profiles_sync_phone on public.profiles;
drop function public.sync_phone();
alter table public.profiles drop column phone;
```

نفس النمط يُطبَّق على تغيير نوع عمود، تقسيم عمود إلى عمودين، ونقل عمود إلى جدول جديد. القاعدة الثابتة: **لا مرحلة تعتمد على نشر متزامن للعميل والقاعدة.**

## إضافة عمود NOT NULL على جدول كبير

`alter table t add column x text not null` على جدول قائم يفشل مباشرة إن وُجدت صفوف. والحل الساذج (`default` ثم `not null`) يمسح الجدول تحت قفل حصري.

الطريقة الآمنة، أربع خطوات:

```sql
-- 1) عمود قابل لـ NULL — لحظي
alter table public.orders add column channel text;
-- 2) قيد غير مُتحقَّق منه: لا يمسح الجدول، يُطبَّق على الصفوف الجديدة فقط
alter table public.orders add constraint orders_channel_not_null
  check (channel is not null) not valid;
-- 3) ملء على دفعات (خارج القفل، معاملات قصيرة)
update public.orders set channel = 'app'
where channel is null
  and id in (select id from public.orders where channel is null limit 10000);
-- 4) التحقق: قفل خفيف (SHARE UPDATE EXCLUSIVE) لا يحجب القراءة والكتابة
alter table public.orders validate constraint orders_channel_not_null;
```

في Postgres 12+ يمكن بعدها تحويله لـ `NOT NULL` حقيقي بسرعة لأن المخطِّط يستعمل قيد CHECK المتحقَّق منه لإثبات عدم وجود NULL.

ملاحظة مهمة: `add column ... default 'app'` بقيمة **ثابتة** لا يعيد كتابة الجدول منذ PG 11 — لكن `default gen_random_uuid()` أو `now()` يعيد كتابته كاملاً لأن القيمة تختلف لكل صف.

## الفهارس المتزامنة

```sql
-- ينشئ الفهرس بلا حجب الكتابة، لكن:
create index concurrently if not exists orders_tenant_created_idx
  on public.orders (tenant_id, created_at desc);
```

قيود يجب معرفتها: **لا يعمل داخل معاملة** — ضع كل `CREATE INDEX CONCURRENTLY` في ملف هجرة منفصل لا يحوي غيره، أو تأكد أن أداة الهجرة لا تلفّه في معاملة. وهو أبطأ 2–3× ويمسح الجدول مرتين. وإن فشل يترك فهرساً بحالة `INVALID` يشغل مساحة ولا يُستعمل، فاكشفه وأعد المحاولة (والحذف كذلك بـ `drop index concurrently`):

```sql
select indexrelid::regclass from pg_index where not indisvalid;
```

على جدول أصغر من ~100 ألف صف، `create index` العادي ينتهي في أجزاء من الثانية ولا يستحق التعقيد.

## هجرة البيانات مقابل هجرة المخطط

| | هجرة مخطط | هجرة بيانات |
|---|---|---|
| المحتوى | DDL | `UPDATE`/`INSERT` |
| المدة | ثوانٍ | دقائق إلى ساعات |
| القفل | حصري لحظي | صفوف فقط |
| في نفس الملف؟ | **لا** | ملف منفصل |

افصلهما دائماً: `UPDATE` على 5 ملايين صف داخل نفس الملف يجعل الهجرة كلها تجلس على قفل DDL. وكل هجرة بيانات على دفعات (5–10 آلاف صف) بمعاملة لكل دفعة، لأن معاملة واحدة على ملايين الصفوف تُنتج WAL هائلاً وتوقف VACUUM. واجعلها **قابلة لإعادة التشغيل** — الشرط `where x is null` يجعل إعادة التنفيذ آمنة.
- بعد أي هجرة بيانات ضخمة: `ANALYZE <table>;` وإلا تبقى الإحصاءات قديمة وتنهار خطط الاستعلام.
- سجّل عدد الصفوف قبل وبعد في وصف الـ PR.

## الاختبار على نسخة من الإنتاج

هجرة نجحت على قاعدة تطوير فيها 40 صفاً لا تعني شيئاً عن جدول فيه 4 ملايين.

الترتيب الإلزامي: (1) `supabase db reset` محلياً أو في CI يطبّق كل الهجرات من الصفر ويثبت أن السلسلة كاملة ومتسقة. (2) استعادة نسخة حديثة من الإنتاج إلى بيئة staging. (3) تشغيل الهجرة هناك مع **قياس الزمن**. (4) إن تجاوزت 30 ثانية أو أخذت قفلاً حصرياً على جدول ساخن، أعد تصميمها لا تنشرها. (5) تشغيل اختبارات RLS بعدها، لأن سياسة صحيحة قبل الهجرة قد تصير خاطئة بعد إضافة عمود.

في GitHub Actions اجعل الخطوات: `supabase db reset` على قاعدة نظيفة، ثم `supabase db lint`، ثم فحص أن كل جدول public عليه RLS، ثم `supabase db push` على الإنتاج فقط عند الدمج في الفرع الرئيسي.

## قبل النشر: قائمة الأسئلة الخمسة

1. هل تكسر أي إصدار منشور من التطبيق؟ إن نعم، هل هي مرحلة expand فقط؟
2. ما أطول قفل تأخذه، وعلى أي جدول؟ وهل يمكن إعادة تشغيلها بأمان لو انقطعت في المنتصف؟
3. كم استغرقت على نسخة بحجم الإنتاج؟
4. ما هجرة التصحيح الأمامية لو ظهرت مشكلة بعد ساعة؟

إن لم تكن تملك إجابة رقمية للسؤال 3، فأنت لم تختبر.

## قائمة تحقق

- [ ] لا تغيير على الإنتاج إلا عبر ملف هجرة مرقّم في المستودع
- [ ] لوحة تحكم Supabase مستعملة للقراءة والمراقبة فقط، لا للتعديل
- [ ] لا ملف هجرة مُطبَّق تم تعديله لاحقاً — التصحيح دائماً ملف جديد
- [ ] سياسات RLS والدوال والمشغّلات كلها داخل الهجرات
- [ ] `set lock_timeout` و`statement_timeout` في مقدمة أي هجرة DDL
- [ ] لا `rename` ولا `drop column` بلا دورة expand/contract كاملة
- [ ] مرحلة الانكماش لم تُنفَّذ قبل نزول استعمال الإصدارات القديمة تحت 2%
- [ ] `NOT NULL` على جدول قائم عبر `check ... not valid` ثم `validate constraint`
- [ ] `create index concurrently` في ملف هجرة منفصل، وفحص `indisvalid` بعده
- [ ] هجرات البيانات منفصلة، على دفعات، وقابلة لإعادة التشغيل
- [ ] `ANALYZE` بعد كل هجرة بيانات ضخمة
- [ ] `supabase db reset` يمرّ من الصفر في CI
- [ ] الهجرة مُقاسة زمنياً على نسخة بحجم الإنتاج قبل النشر
- [ ] اختبارات RLS أُعيد تشغيلها بعد الهجرة
